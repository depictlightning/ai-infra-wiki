# OSDI 2026：AI 基础设施论文

> 从会议的 136 篇正式论文中筛出 49 篇，其主要问题直接涉及 AI 模型的训练、推理、检索或这些工作负载所需的硬件与集群系统。

## 筛选口径

纳入条件是：论文的核心问题、设计机制或主要评测围绕 AI/ML 工作负载，且贡献位于系统层，包括运行时、调度、编译器、存储与内存路径、网络、故障恢复或可观测性。判断依据是论文正文的问题定义与主实验，而不是标题里有没有“AI”“LLM”“GPU”。因此 [[Strata-OSDI26]]、[[Helmsman-OSDI26]]、[[Umap-OSDI26]] 和 [[MoonBright-OSDI26]] 都在本页：它们分别处理长上下文 KV 缓存、向量检索、文件后备矩阵访问和 GPU 内存管理。Umap 的评测横跨 AI、金融与科学计算，属于本次纳入的边界案例。

被排除的边界案例也有明确原因：ECO、SMARTTalk、Neuro-Symbolic Proof 与 S4-FIFO 主要用 AI 改进通用系统；OBASE、SPADE、POEGA 主要研究通用内存、数据处理或图分析，AI 不是其核心工作负载。本页只统计上述 49 篇，`paper_count` 不代表 OSDI 2026 全会论文数。

## 概览

这批论文有两条清晰主线。第一条是把模型执行切成更细的可调度阶段：[[BatchGen-OSDI26]] 在序列协程边界重组批次，[[EcoServe-OSDI26]] 在实例之间错开预填充与解码，[[Tessera-OSDI26]] 联合选择流水线分区和重叠计划，[[RollArt-OSDI26]] 把智能体强化学习的生成、环境交互和奖励处理拆到适合的资源上。它们都利用阶段差异，但各自增加了状态搬运、预测或调度成本。

第二条是把模型状态当作跨设备、跨时段存在的数据对象。[[Strata-OSDI26]]、[[ECHO-OSDI26]] 与 [[DirectKV-OSDI26]] 改造 KV 缓存的搬运和预取；[[Prism-OSDI26]] 让模型权重与 KV 缓存弹性占用显存；[[MoonBright-OSDI26]] 处理 GPU 动态分配与虚拟内存管理。相同“缓存命中率”可能对应完全不同的 I/O 完成时间和请求尾延迟，因此需要同时看数据位置、传输带宽和调度时机。

生产证据在可靠性和集群论文中尤其重要。[[AEGIS-OSDI26]] 基于 3,500 万 GPU-hours 的部署观察，[[Alibaba-ASI-OSDI26]] 使用 15.5 万 GPU 的生产集群轨迹，[[StriaTrace-OSDI26]] 面向在线推理的大规模追踪，[[SDCHunter-OSDI26]] 分析真实故障 GPU。这类数据能证明问题确实在生产环境发生，但不同组织的模型、硬件和故障分布并不自动相同。

## 研究趋势

**更小的执行边界带来更大的调度空间，也带来额外状态成本。** [[BatchGen-OSDI26]] 的序列协程允许在注意力与 MoE 之间重新组批；[[MPK-OSDI26]] 则把多算子任务装进持久化 kernel，并在 SM 级调度；[[Syncopate-OSDI26]] 通过分块重叠计算与通信。三者优化粒度不同，分别承担协程状态、编译计划或分块同步开销，不能只比较最高加速比。

**长上下文服务的关键在“命中何时可用”。** [[Strata-OSDI26]] 发现慢层命中的碎片 KV 仍可能卡在搬运和布局转换；[[ECHO-OSDI26]] 针对原生稀疏注意力规划无损预取；[[DirectKV-OSDI26]] 减少卸载路径中的额外缓冲和复制。比较时需要固定模型注意力形式、缓存容量、命中距离与主机链路，否则“更高命中率”不能推出更低 TTFT。

**RL 训练系统从静态角色分配走向细粒度编排。** [[DynaRL-OSDI26]]、[[RLinf-OSDI26]]、[[RollArt-OSDI26]]、[[Weave-OSDI26]] 和 [[Seer-OSDI26]] 都针对 rollout、训练及同步之间的空转，但采用不同的调度边界与异步程度。[[RobustRL-OSDI26]] 提醒我们：阶段拆开后，故障恢复边界也必须重新定义。横向比较应同时记录训练完成时间、模型质量、轨迹陈旧度和故障后的恢复损失。

**可靠性从发现异常走向定位首次错误。** [[AEGIS-OSDI26]] 用训练期在线传感器捕捉可疑计算，[[SDCHunter-OSDI26]] 以真实训练数据诊断故障 GPU，[[OpGuard-OSDI26]] 对齐重复执行中的算子边界，[[StriaTrace-OSDI26]] 追踪在线推理的性能问题。它们处理的故障语义不同；检测率、定位粒度、运行开销和故障覆盖区应分开报告。

## 共同观察

- **硬件并行性常被软件粒度限制。** [[CoPilotIO-OSDI26]] 看到 GPU I/O 轮询占用 SM，[[FlowANN-OSDI26]] 看到图搜索的逐轮依赖限制访存重叠，[[Helmsman-OSDI26]] 看到图式近邻检索的串行 SSD 读取链。三篇的解决机制不同；共同点是先改变可并行工作的组织方式，再追求设备峰值。该观察仅覆盖其测试的 I/O 与检索负载。
- **模型与系统的状态生命周期逐渐成为主要调度对象。** [[Prism-OSDI26]] 管理多模型权重与 KV 缓存，[[Strata-OSDI26]] 管理分层 KV 及正在生成的前缀，[[TrainMover-OSDI26]] 管理训练迁移时的运行时状态。状态迁移在短任务或低复用场景中未必划算，需测量字节数、停顿时间和恢复成本。
- **生产轨迹强化了问题定义，却不能替代公开可复现实验。** [[Alibaba-ASI-OSDI26]]、[[AEGIS-OSDI26]]、[[StriaTrace-OSDI26]] 给出大规模工作负载或故障分布；[[OpenTela-OSDI26]] 报告长期部署。对外部环境的适用性还取决于模型组合、网络拓扑和运维策略。

## 互相冲突的假设

- **按时间错峰还是按空间分离推理阶段？** [[EcoServe-OSDI26]] 在普通网络上保持完整模型副本并错开阶段，[[DCP-OSDI26]] 在 PCIe 多卡中调整流水线 chunk，[[Prism-OSDI26]] 在显存中弹性共享多个模型。它们对网络带宽、显存余量和请求混合的要求不同。需要在相同硬件和到达轨迹上比较总成本、TTFT/TPOT 尾部指标及模型切换开销。
- **扩大批量还是保护单请求延迟？** [[BatchGen-OSDI26]] 以离线批完成时间为目标，[[LMetric-OSDI26]] 优化在线请求路由，[[Sereno-OSDI26]] 还要保护手机前台应用。三者的最优调度不能共用一个吞吐指标；应把每类服务的 SLO 与公平性放进同一负载记录。
- **容忍异步陈旧度还是保持同步训练？** [[RollArt-OSDI26]] 通过有界陈旧的异步权重同步重叠阶段，[[Seer-OSDI26]] 则关注同步 RL 的上下文学习，[[Weave-OSDI26]] 在分离资源上协同调度。是否值得允许陈旧轨迹，应由训练质量曲线、总 GPU-hours 和故障后的数据重用共同裁决。

## 值得关注的方向

- **小集群上的跨层瓶颈测量。** 以 2–8 张 GPU 复现 [[Strata-OSDI26]]、[[CoPilotIO-OSDI26]] 与 [[MoonBright-OSDI26]] 的关键测量：KV 到达延迟、SM 被 I/O 占用的比例和显存分配停顿。先建立同一负载下的瓶颈分解，再决定是否组合机制；无需复现论文的大规模生产部署。
- **RL 调度的统一实验口径。** 选一个公开可运行的后训练框架，用固定模型、奖励、失败注入和 GPU 预算比较 [[DynaRL-OSDI26]]、[[Weave-OSDI26]]、[[RLinf-OSDI26]] 与 [[RobustRL-OSDI26]] 提出的调度/恢复边界。重点记录训练质量达到阈值所需的时间，而不只看 rollout 吞吐。
- **缓存命中与尾时延的联合控制。** 在相同前缀重用轨迹上组合 [[LMetric-OSDI26]] 的路由信号与 [[Strata-OSDI26]] 的缓存到达时间，测试延迟命中、热点迁移和多租户突发时的 P95/P99。关键问题是路由器能否准确知道“命中的 KV 何时真正可用”。
