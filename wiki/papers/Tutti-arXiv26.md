# Tutti：由 GPU 主导的 SSD KV 缓存（arXiv 2026）

> **原题**：Tutti: Making SSD-Backed KV Cache Practical for Long-Context LLM Serving

> **一句话总结**：针对前缀 KV 从 SSD 恢复时的小 I/O 和 CPU 控制开销，Tutti 组合 GPU 原生对象存储、GPU 侧异步 I/O 和资源空档调度；在论文测量的 LEval 负载下，相比 GDS 版 LMCache，最高负载点 TTFT 降低 78.3%，这一结果依赖具体硬件、负载和基线配置。[^paper]

**阅读范围**：作者 arXiv v1 全文及 PDF；当前会话未提供 MinerU 服务，因此以论文 HTML 全文核对，尚无 MinerU Markdown 和图片。文中的多 GPU 结果存在明显数值矛盾，见实验分析。[^paper]

## 问题与动机

前缀缓存把历史 token 的 KV 保留起来，后续请求可跳过重复 prefill。长上下文和并发增长后，显存与主存不一定能保存足够多的前缀，SSD 的大容量有助于保留更多历史，但从 SSD 加载过慢时，缓存命中也可能比重算更慢（§1–2）。

论文观察到两个互相叠加的瓶颈。第一，推理引擎将 KV 分成不连续的小块，恢复前缀会形成大量 I/O；传统路径还经过主机缓冲区和 CPU–GPU 复制。第二，即便用 GPU Direct Storage（GDS）让数据绕过主机缓冲，I/O 发起仍需 CPU 参与。随着推理内核变快，CPU 控制与 I/O 等待在端到端时间中的占比可能变大（§2.2、图 1–2）。

GPU 直接控制 SSD 并不能自动解决问题：推理引擎需要按 KV 块查找和共享，底层存储则需要有效合并传输；I/O 内核又会与模型计算争用 GPU 资源，SSD 同时读写也可能相互干扰。Tutti 围绕对象组织、异步 I/O 和调度提出三项设计（§2.4、§3）。

## 关键观察 / 隐含假设

- **观察 1：SSD 命中率提高并不保证恢复比重算更快。** 图 2 比较不同层级和 vLLM 版本，较新的推理引擎缩短了计算时间，暴露出 SSD 恢复成本（§2.2）。
  - **依赖假设**：前缀足够长、复用频率足够高，SSD 的容量收益可以抵消读取和管理成本；短前缀或低复用率时结果可能相反。
- **观察 2：直接数据通路仍有 CPU 发起 I/O 的成本。** 作者区分 GDS 的 GPU–SSD 数据直达与 CPU 侧 I/O 控制；Tutti 按层准备批量工作，将逐条命令提交移至 GPU（§1、§3.1–3.2）。
  - **依赖假设**：硬件允许 P2P 访问，GPU 并行提交足以摊薄额外的内核、映射和资源管理开销。
- **观察 3：读写与计算的重叠可能引入资源争用。** 作者在所测 SSD 上用 FIO 发现并发读写使总带宽下降约 60%；GPU I/O 内核也可能占用计算所需的 SM（§3.3、图 6）。
  - **依赖假设**：离线画像可以预测部署时的可用 SM 和时间窗口，且该设备的读写争用行为具有稳定性；不同 SSD 或混部负载可能改变结果。
- **观察 4：引擎通常预分配并长期复用 KV 显存池。** Tutti 在启动时构建 P2P 映射表，避免每次 I/O 重建地址映射（§3.1）。
  - **依赖假设**：显存池地址和注册关系在运行期间保持有效；动态扩容或迁移需要更新映射并保证同步。

## 核心方法

### 1. GPU 原生 KV 对象存储

Tutti 建立在 GPU 文件系统 GeminiFS 之上，保留 CPU 侧索引及引擎可见的管理逻辑，将大量数据访问的执行下放到 GPU。系统按引擎的 KV 块粒度组织 GPU file；对每个块，按模型层分别组织 K、V 对象，并映射到 SSD 物理文件。跨多个 GPU file 的数据按轮转方式分布到多块 SSD。系统预分配文件池，运行时选择空闲文件并建立缓存键到文件的映射，减少关键路径上的文件创建和元数据操作（§3.1、图 4）。

系统初始化时为固定显存池构建 P2P 地址映射。为了描述连续物理地址区间，论文使用 scatter-gather list（SGL），减少逐页描述的开销。一次逐层调用可以准备一批 I/O 上下文，而不是由 CPU 对每个 KV 小块单独发起一次访问。索引和存储管理仍需要 CPU，GPU 主导指数据传输和逐条 I/O 控制的关键路径，并非 CPU 完全退出系统（§3.1）。

### 2. GPU io_uring 与异步执行

CPU 从映射生成 I/O 控制块，并将 I/O 内核和计算内核提前提交；请求与完成队列位于 GPU 显存并映射到 CPU。队列中的一个控制块可包含一批 I/O 上下文；CUDA event 约束数据依赖，GPU 内核生成并提交 SSD 命令，完成后更新完成队列（§3.2、图 5）。

系统使用 NVIDIA green context 将部分 SM 分给 I/O 控制，其余用于模型计算，降低长期运行的 I/O 内核阻塞计算的风险。资源分区本身消耗 GPU 资源，合理数量依赖硬件与工作负载；异步操作的正确性仍依赖数据依赖、完成事件和缓冲区生命周期被正确维护（§3.2）。

### 3. 识别可用空档并分开读写

系统按输入长度和可复用前缀长度离线画像每层的执行空档，记录可用时长与 SM 数量，以及不同数量 I/O 控制块的执行开销。运行时查询该表，选择能放入窗口的 I/O 批次（§3.3、图 7）。

前缀恢复位于关键路径，因此 prefill 优先安排读取；没有合适空档时立即发起必要读取，避免让计算一直等待。写入在读请求之后安排，无法放入当前空档的写入延后到 decode 或后续请求。这个策略优化的是 I/O 内核调度，不是按缓存命中对用户请求重新排序。

### 4. 引擎集成与多设备

Tutti 对接 vLLM 的 KVConnector，暴露逐层读取与保存接口，并保留引擎原有的 KV 块管理。多 GPU 时每个 GPU 进程对应一个实例，本地守护进程为 GPU 分配独立 NVMe 队列。论文还描述用 Mooncake 管理跨节点位置和副本：本地副本走 Tutti；远端路径当前仍经过 CPU 和主机内存后使用 RDMA，作者将更直接的远程路径留作后续工作（§3.4）。

## 设计取舍

- **绕过逐条 CPU 提交换取 GPU 控制开销**：批量 I/O 降低 CPU 压力，但占用 SM、显存队列与地址映射，并引入事件和生命周期管理。
- **预分配换取关键路径简单**：预先建立文件池和地址映射减少运行时工作，但依赖空间、注册及映射更新机制。
- **延迟写入换取读取和计算优先**：可减少读写争用，但写入队列可能积压，故障时尚未完成的缓存如何恢复需要明确。
- **离线画像换取在线决策成本**：查表快速，但硬件、模型、并发和共租负载改变后可能需要重新画像。

## 实验与结果

**实验设置**：服务器为 64 核 Xeon 6530、512 GB 内存、两张 80 GB H100 和四块 Solidigm D7-PS1010 SSD；分层基线为每 GPU 配置 256 GB pinned DRAM 和 14 TB SSD。主要模型为单 GPU Llama3-8B，另用两张 GPU 运行 GLM-4-9B-Chat-1M。LEval 和 LooGLE 请求以泊松分布合成到达；比较 HBM、LMCache 的 DRAM、SSD 和 GDS 方案以及 Tutti（§4）。

- **命中率**：表 1 的 LEval/LooGLE 下，HBM 分别为 8%/4%，DRAM 为 53%/24%，SSD 为 84%/86%；容量和负载配置变化会影响这些命中率。
- **端到端 TTFT**：vLLM 0.17.0 的 LEval 高负载点，相对 LMCache-DRAM-LW 和 LMCache-GDS，Tutti TTFT 分别降低 69.1% 和 78.3%；在 1 秒 TTFT 目标下，可承受请求率相对 GDS 增加 100%（图 8、§4.1）。
- **带宽**：两盘 RAID-0 的接口微基准中，较长上下文的 Tutti 读取带宽最高为 25.9 GB/s，LMCache-GDS 约饱和在 11.9 GB/s；128K token 写入约 9.8 GB/s，GDS 约 7 GB/s（图 9、§4.2.1）。
- **地址描述**：单 GPU 线程、每次 500 MB 微基准中，SGL 读写带宽分别为 8.891/2.922 GB/s，PRP 为 0.287/0.032 GB/s；该微基准倍数不能直接视为端到端加速（图 10、§4.2.2）。
- **复用比例与重叠**：固定 128K 总输入、112K 已缓存前缀时，Tutti TTFT 为 3.43 秒，LMCache-SSD 为 7.84 秒；前缀超过 96K 后，DRAM 在该实验中重新领先，Tutti 最多落后 20.6%（图 11、§4.2.3）。
- **成本**：LooGLE、0.5 QPS 下，论文依据给定的 GPU、DRAM 和 SSD 单价估计，Tutti 相对 LMCache-GDS 的单位 token 成本降低约 27%；价格和吞吐变化会改变结果（图 14、§4.3）。

## 批判性分析

### 论证链条

论文从小粒度访问与 CPU 控制成本出发，将对象管理、GPU 提交及 I/O 调度逐层连接到端到端效果。图 9 和图 10 支撑存储接口及描述符优化，但端到端收益还受更高 SSD 命中率和具体基线流水线能力影响；不能把全部加速归因于单一设计。

### 假设压力测试

P2P DMA 的可用性、PCIe 拓扑、SSD 队列及 green context 支持影响部署。短前缀、低复用或高速重算可能使读取不划算；混部与其他 SSD 流量也可能使离线画像失准。延迟写入时若新请求提前访问未完成的缓存，需要依靠队列依赖和正确同步。

### 实验可信度

到达时间是合成的，结果不能直接代表真实智能体服务的到达和复用模式。图 13 排除 GDS 基线，因而不构成相同逐层流水线下对 GDS 的直接调度消融。§4.2.4 报告 128K 前缀 Tutti 为 155.743 秒，却又称 640K 前缀为 1.2 秒；正文未解释这种差异，不能据此可靠比较两个数字。需要核对图 12、实验代码和作者更正。

### 系统性缺陷

论文未充分评估延迟写入队列的持久性、异常退出后的缓存一致性、多租户 SSD 干扰和重画像成本。跨节点远端路径仍经过主机内存，不能将本地 GPU 直达结果直接外推到远程缓存。

## 局限与后续工作

- 在真实多轮与智能体轨迹下，对固定设备数量和相同缓存容量比较加载与重算交叉点、P95/P99 TTFT 和写入积压。
- 核实图 12 与 §4.2.4 的时间单位和数值，并独立测量多 GPU 的 PCIe、NVMe 共享瓶颈。
- 测试负载或模型变化时离线画像的失效程度，以及动态重画像的成本。
