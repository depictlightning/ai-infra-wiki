# ThunderServe：异构云环境中的 P/D 分配与弹性重调度（MLSys 2025）

> **原题**：ThunderServe: High-performance and Cost-efficient LLM Serving in Cloud Environments

> **一句话总结**：云 GPU 的计算、显存、价格和网络带宽不一致，ThunderServe 联合选择 GPU 分组、P/D 角色、并行方式与请求路径；在作者的指定租价和工作负载下，异构云实验相对同价位机内 DistServe 达到 1.5–2.1 倍吞吐（§5.2、图 9）。[^paper]

**阅读状态**：基于 MLSys 2025 会议版 PDF 和 MinerU 全文，已回看图 6–12 和表 2–4；附录细节与源码未逐项复核。这里报告作者实验，没有复现。[^paper]

## 问题与动机

P/D 分离允许 prefill 和 decode 各自使用合适的并行度，但云上的 GPU 并不一定同型号，也未必连接在同一高速网络内。一个实例可能便宜但内存小，另一实例拥有更大带宽却与其他节点之间的连接较慢。因此阶段配比不是单独选择“几张 P 卡、几张 D 卡”，还要决定哪些 GPU 共同装下一个模型副本、这些副本之间如何传送 KV，以及其租用成本（§1–2）。[^paper]

对于相同总资源，短输出的代码工作负载与长输出的对话工作负载，可能分别受 prefill 和 decode 限制。云资源上下线又可能改变可用设备。论文研究首次部署时如何选择组合，以及负载或 GPU 数量变化后，如何在不中断所有服务的前提下调整角色（§3）。[^paper]

## 关键观察 / 隐含假设

- **资源异构可能有价值。** 作者在当时的价格与硬件条件下，以 A40 的计算能力与 3090Ti 的内存带宽说明两个阶段可能偏好不同设备；这一选择依赖实际租价、核函数与模型，不能推广为固定硬件排名（图 1、表 1）。[^paper]
- **阶段配比受负载和集群规模影响。** 图 6 在 LLaMA-13B、8/12/16 张 A5000 下扫描 P/D 副本比例：代码工作负载更偏好 prefill 容量，对话工作负载更偏向 decode。每个副本使用两张 GPU；图中的比例是副本比例，不直接代表所有部署的 GPU 比例。[^paper]
- **网络路径影响放置。** KV 从 prefill 传到 decode，跨实例带宽异构时不能只按单实例计算速度配对。论文在模拟器中显式估计各 P/D 配对的传输代价（§3.3）。[^paper]

## 核心方法

### 先决定哪些 GPU 属于哪一侧

一个部署方案包含四项决定：GPU 分组、每组承担 prefill 还是 decode、每组的模型并行配置，以及 P/D 副本之间的请求路由。分组要满足模型权重显存约束；不同组可以使用不同硬件和并行方式。论文将搜索拆成上下两层（§3.1）。[^paper]

上层用禁忌搜索探索 GPU 组及其角色。邻域操作包括翻转某组的 P/D 角色、拆分或合并组、在组之间移动 GPU；显存不足以容纳模型的方案提前淘汰。初始分组参考设备间带宽。搜索是启发式方法，论文将找到的方案用于比较，不意味着已证明全局最优（§3.2、算法 1）。[^paper]

### 再决定并行方式和请求路径

给定分组和阶段，下层为各副本选择模型并行方式。作者避免把通信频繁的 TP 跨低带宽节点部署，同时允许流水线各阶段承载不同数量的层，以适配异构设备（§3.3）。这使两个副本即使运行同一模型，也可能拥有不同的 GPU 组合与 PP 配置。[^paper]

接着，系统枚举 prefill 与 decode 副本配对，用包含网络启动延迟、KV 数据量和带宽的模型估算通信时间，并结合推理模拟器估算每对副本的 SLO 达成率。路由优化决定进入各 prefill 副本的请求份额和转交 decode 副本的份额；因此同一 P/D 数量在不同网络拓扑和配对策略下可能有不同表现（§3.3、图 5）。[^paper]

### 运行后怎样调整配比

如果负载或设备可用性变化，完整重新搜索可能改变分组和并行配置，进而需要重载模型。轻量重调度只翻转已有副本的 P/D 角色并重新计算路由，保留 GPU 分组和并行配置，从而省去模型权重重载。它受限于原有分组：在新工作负载下可能不如从头搜索灵活（§3.4）。[^paper]

例如预先形成四个模型副本时，可以把其中一个从 decode 改为 prefill；是否有收益仍要看剩余 decode 能否消费新增的 prefill 请求，以及所选副本之间的传输成本。这是依据论文机制构造的例子，具体配置由搜索决定。[^paper]

### 较慢网络下的 KV 交接

作者借鉴 KV cache 量化，将 prefill 侧的 16-bit KV 压缩为 4-bit 后传输，在 decode 侧解包并反量化，再用反量化后的值执行计算（§4）。压缩减少网络字节，但已经发生的量化误差不会因反量化而消失。表 2 的 CoQA、TruthfulQA、GSM8K 测试显示不同任务指标有升有降；这些结果支持所测任务的质量变化有限，不能证明输出逐 token 无损。[^paper]

## 设计取舍

- **阶段专用与副本成本**：分离能分别配置批量和并行度，但每组需容纳模型，且 KV 需要跨组传输。
- **完整搜索与重调度速度**：全量搜索可改变分组及并行方式；轻量方式节约重载，但只能在原有分组内修改角色和路由。
- **压缩带宽与模型质量**：低精度传输减少字节和部分传输时间，但带来量化误差及编解码开销，需按模型和任务验证。

## 实验与结果

主要实验使用 LLaMA-30B 和 Azure 代码、对话工作负载的长度分布，以泊松过程生成到达。异构云侧租用 32 张 A6000、A5000、A40、3090Ti，论文列出的总价为 13.542 美元/小时；不支持异构的 vLLM 和 DistServe 对照运行在 8×A100 机内服务器，按当时租价约 14.024 美元/小时估算。两组是近似等租价比较，并非同 GPU 数、型号或互连（§5.1、表 1）。[^paper]

- 图 9 中，相对同一云环境的 HexGen，ThunderServe 在代码和对话负载下分别达到 1.5 倍和 1.3 倍吞吐；相对机内 DistServe 分别达到 1.5 倍和 2.1 倍。这些比较同时改变硬件与部署方式，不能把全部收益归因于某个调度组件（§5.2）。[^paper]
- 图 6 的配比扫描固定每副本两张 A5000，在 4、6、8 个副本及两种负载上比较 token 吞吐。它支持“比例应随需求调整”，但指标是总 token 吞吐，不能直接替换成单位 GPU 请求 goodput 或尾延迟（§3.4）。[^paper]
- 表 4 中，从头重调度的搜索、模型重载与总时间分别为 54±5、103±10、157±13 秒；轻量重调度为 13±2 秒且无模型重载。论文在 32 张 GPU 中移除四张的场景比较两种策略（§5.4、图 11、表 4）。这里的重调度时间不是所有情况下的恢复时间上界。[^paper]
- 两张 A5000、40 Gbps 的 LLaMA-7B 测试中，论文报告从 16-bit 到 4-bit KV 传输后，通信占端到端时间比例由 16%–30% 降至 4%–9%（§4）。比例下降并不等价于端到端延迟按同一百分比下降。[^paper]

### 读成本与结果时要注意什么

作者在相似小时租价下比较不同 GPU 集群，异构云侧可以放置更多模型副本；与八卡 A100 对比的结果包含硬件、资源数量、价格和部署策略的共同作用。价格是论文实验条件，随地区、供需与时间变化。图 7–8 的 SLO scale 是相对于 A100 执行延迟设定的门槛倍数，不是固定毫秒数（§5.1–5.2）。[^paper]

论文表 3 给出代码与对话工作的不同 P/D 组合，说明搜索确实改变角色和设备分配；它不证明输入输出长度的比例足以唯一确定配置。规划器对带宽和阶段性能的估算准确性会影响搜索质量，附录 J 仅在所测微基准上比较模拟估计与实测。[^paper]

## 批判性分析

### 论证链条

论文先展示阶段与设备异构，再设计分层搜索和轻量角色切换，以配比扫描、端到端对照与设备下线实验检验。图 12 联合移除压缩和路径编排，说明通信优化重要，但不能把组合差距全部归于单一机制。

### 假设压力测试

异构 GPU 的实际价格、可获得性、设备间带宽和模型结构改变后，静态画像与候选分组可能失效。轻量重调度保留原分组，若变化需要重新切分模型或改变 PP，其搜索空间可能无法覆盖更好的方案；这是从算法约束得到的推断。

### 实验可信度

工作负载长度来自生产数据，但到达经泊松过程生成。核心端到端模型为 LLaMA-30B；同价位异构云和同构机内比较适合研究当时的成本取舍，不适合声称同硬件上的纯算法加速。KV 量化评测覆盖有限任务和模型；模型质量不能仅由网络吞吐判断。

### 系统性缺陷

轻量角色切换需要现有模型副本可继续服务新角色。论文测试设备减少后的配置调整，但没有充分覆盖多租户价格竞争、长时间网络拥塞、可抢占实例中断及失败恢复的一致性语义。

## 局限与后续工作

- 在固定 GPU 小时、不同网络带宽与租价下，同时测量阶段 SLO、有效请求速率和 KV 传输开销。
- 在相同设备组合下分别关闭角色调整、路由优化和 KV 压缩，观察各项机制与负载变化速度的关系。
- 对长上下文和不同模型复测低精度 KV 的质量、吞吐及编解码代价，检查能否接受生成结果变化。
