# Octopus / Swarm：利用多 SSD 并行回载稀疏 KV（ATC 2026）

> **会议题目**：Octopus: Unlocking SSD Parallelism for Sparse KVCache Retrieval

> **一句话总结**：作者预印本 Swarm 根据 KV 的共同激活关系聚类，把一个簇的条目分布到多块 SSD，并在读取时去重、均衡副本和重叠计算；它依赖稀疏选择与离线共访问画像，收益和质量均需结合多盘拓扑、数据分布和版本理解。[^preprint]

**版本与阅读状态**：ATC 2026 会议日程列出的题目为 **Octopus**，作者主页将该条目的论文链接指向题为 **Swarm** 的 arXiv:2603.17803v1，作者顺序一致；这建立了作者提供的关联，但目前没有会议终稿可逐项对照。本页所有机制、数字和疑点均针对 Swarm 预印本，不能直接断言 Octopus 终稿完全相同。全文及部分图表正在核对，MinerU 解析待补，维持待复核状态。[^schedule][^authors][^preprint]

## 问题与动机

单块 SSD 容量远大于主机内存，但带宽和随机读延迟难以满足逐层 decode。多块盘理论上可以累加带宽，前提是一次查询真正把读取均匀分散到设备上；如果被选条目集中在某一块盘，最慢盘仍决定完成时间。另一方面，相同大小的连续块未必与注意力真实需要的数据一致，过粗会多读，过细又可能产生大量小 I/O（§1–3）。[^preprint]

Swarm 把共同被选中的 KV 组织成簇，再把每簇拆分到多个 SSD；DRAM 保留簇代表、近期 token 和一部分热簇。它要解决的是活跃计算的动态稀疏取回，与只在后续请求启动时恢复完整前缀的多级缓存工作不同。[^preprint]

## 关键观察 / 隐含假设

- **观察 1：部分 KV 条目经常在同一查询中共同被激活。** 作者以不同模型和数据集记录共同选择关系，认为这些关系可形成可复用的簇（§3.1、图 4–5）。[^preprint]
  - **依赖假设**：离线画像得到的共激活关系能够迁移到实际前缀和请求；相关性变化、任务域漂移或新 token 频繁产生时，聚类可能选错或带来大量多余读取。
- **观察 2：多块 SSD 的总带宽只有在请求负载均衡时才可利用。** 作者比较顺序放置、不平衡放置及分簇后分散放置，图 13 显示布局会影响最长设备的完成时间（§5.2、§8.3）。[^preprint]
  - **依赖假设**：设备各自有足够 PCIe 通道及控制器带宽，且主机根端口、内存、文件系统和其他任务不会先饱和。多盘总标称带宽不能视为应用实际带宽。
- **观察 3：允许条目属于多个簇有利于表达交叠共激活。** 若 A 经常与 B、C 分别共同出现，但 B 和 C 很少共同出现，复制 A 可以避免为每次查询都读取整组 A/B/C（§5.1、图 7）。[^preprint]
  - **代价假设**：副本增加的 SSD 容量、写入和元数据小于省下的读放大；当多个含 A 的簇同时命中，调度器必须去重，否则可能重复搬运。
- **观察 4：把簇代表与近期窗口放在 DRAM 可减少选择时的磁盘访问。** 表 4 中 Qwen3-32B 的 1M 前缀配置报告代表索引占 0.412 GB，选择延迟从 12.15 ms 降至 0.999 ms（§8.3）。[^preprint]
  - **依赖假设**：所报内存口径覆盖实际需要的索引；不同 batch、层数、模型及缓存副本会增加总资源。代表向量能否可靠代表其余成员仍需任务质量验证。
- **观察 5：少量随机 I/O 与大量 I/O 的瓶颈不同。** 随上下文或 batch 增长，作者观察到系统从 IOPS 受限逐步转为带宽受限（§8.4、图 16–17）。[^preprint]
  - **依赖假设**：工作负载可提供足够独立读请求，且 I/O 的排队不会超过延迟目标；batch 1、短上下文或后台争用可能无法发挥多盘并行。

## 核心方法

### 1. 根据共同激活关系构造簇

离线画像统计两个 KV 条目在注意力中共同激活的次数，构造加权关系图；先选择共同激活密度高的条目作为 medoid（簇代表），再把与现有簇平均距离低于阈值的候选逐步加入。一个条目可以出现在多个簇，以表达重叠访问模式（§5.1、算法 1）。[^preprint]

预印本给出的 `d(i,j)=1−P(i,j)` 与后文“`d=1` 表示总是共同激活”的文字相矛盾：依该定义，`d=1` 对应 `P=0`。实现前应向作者确认概率归一化和距离定义，不能替作者悄悄修正；作者所述基于长度 `N` 的两两关系矩阵在长上下文下也可能有 `O(N²)` 状态，预印本未清楚交代百万 token 的构图成本与稀疏化方式。[^preprint]

### 2. DRAM 保存索引、近期项和热簇，SSD 分布完整簇

每个簇的 medoid 留在 DRAM，用于与新 query 比较并定位需要取回的簇；最近窗口保留新 token，一部分热簇也按“访问频率 × 节省的读取时间 / 簇大小”评分留在 DRAM。簇数据按轮转方式跨 SSD 放置，让读取一个簇也可以并行使用多块盘（§5.2、图 8）。[^preprint]

与按连续 token 组成的 [[SolidAttention-FAST26]] 块不同，Swarm 的簇由历史共同激活关系决定；两者都可能整块读入不需要的条目。两种划分的质量和 I/O 收益需要在相同模型、稀疏率与硬件下实测。[^preprint]

### 3. 在线去重、选副本与发起读取

系统合并所有被选簇，从集合中排除已在 DRAM 中的数据，并对跨簇重复项去重；随后按条目副本数从少到多分配到对应 SSD 的请求桶。有多个副本的条目分配给当前负载较轻的桶，再批量提交异步读。这样副本不必全部读取，同时可用于均衡设备（§6.1、图 9）。[^preprint]

关键代价是请求集合合并、设备桶构造和簇到位置的元数据管理。预印本对去重和负载均衡做了消融，但不同设备队列长度、慢盘和共享 PCIe 拓扑会影响最佳策略。[^preprint]

### 4. 新 token 更新与跨层预取

新 KV 先留在 DRAM 近期窗口，系统在窗口内观测其与现有簇代表的共同激活，再将其加入满足阈值的一个或多个簇并写入相应 SSD。缓存分数随运行中的激活与未激活更新，以适应工作集变化（§6.2、图 10）。[^preprint]

实现使用 Linux `io_uring` 异步读取到预分配 pinned host 内存，再以 CUDA stream 搬往 GPU；执行第 L 层时，CPU 用其 embedding 预测第 L+1 层需要的簇并提前读取（§7）。这是 **SSD→主机→GPU** 的流水线；预印本称省去 CPU 复制，不应误写成 SSD 直接到 GPU 的 GPUDirect Storage。跨层预测和稀疏簇选择都是近似，是否对实际选中集合做最终补齐还需要终稿和实现核查。[^preprint]

## 设计取舍

- **聚类换画像与迁移成本**：共激活可提升读取相关性，但离线构图、不同任务迁移以及在线新增条目维护均需要资源。
- **多副本换均衡与空间**：复制让调度有可选盘，却增加写入、地址元数据及去重工作。
- **并行带宽换拓扑资源**：多盘可聚合读带宽，但 PCIe lane、根端口和主机内存也是有限资源。
- **稀疏选择换精度风险**：即便完整数据存在 SSD，未选簇不会参与当前 attention；图中的相对精度不等于原模型逐请求无损。
- **预测预取换争用**：提前读可隐藏延迟，预测不准会消耗 SSD 和 PCIe 带宽，并可能干扰真正需要的 I/O。

## 实验设置

预印本使用 64 核 Xeon Gold 6530、8×H20 96 GB、1 TB DDR5 和最多 8 块 NVMe，测试 Samsung PM9A3 与 Intel Optane 900P；模型包括 Qwen3、Llama3.1 和 GPT-OSS，数据集包括 WikiText、LongBench、MMLU、GSM8K，并拼接样本构造最长至 1M token 的输入（§8.1）。[^preprint]

作者比较无聚类、InfLLM 和 PQCache，报告所有方法采用 10% 稀疏配置。无聚类基线将全量 KV 分块读入 DRAM 以计算选择；作者称仅计入部分选择及必要传输时间。预印本文字称测试六个模型，而表 2 显示五行模型配置，这一不一致需结合最终论文或代码确认。[^preprint]

## 批判性分析

论文的技术链条由“共同被选中的条目 → 按关系聚类 → 每簇分散到多盘 → 合并、去重并为副本选择负载较轻的盘 → 计算和读取重叠”组成。聚类质量和多盘调度分别有消融，但整体吞吐提升同时包含索引、缓存、布局和预取；不能只归因于增加 SSD 数量。[^preprint]

预印本至少有两处值得带着问题阅读：其一，距离公式与 `d=1` 的解释冲突；其二，论文将完整上下文的两两共激活建模为图，但没有充分量化百万 token 情况下的统计、存储和预处理成本。此外，报告的归一化精度应结合各任务绝对分数、查询级失败和与 dense attention 的差距；保持磁盘副本不意味着本步访问语义无损。[^preprint]

作者主页给出 Octopus→Swarm 的直接链接，说明二者存在作者认可的关系；但正式论文可能修改名称、算法和结果，当前不应把预印本每一项数值直接标成会议终稿。取得终稿后应逐项复核版本差异、作者公式以及每项实验的真实硬件路径。[^authors]

## 可继续研究的问题

1. 对真实请求的新前缀，构建和更新共激活图需要多少 GPU 时间、内存和写入？可否用稀疏图或在线采样替代完整矩阵？
2. 对任务迁移、突发热点和生成阶段变化，簇半径和缓存分数多快失效？
3. 在受限 PCIe root complex、冷热盘混用和多租户 I/O 竞争下，多盘聚合收益如何变化？
4. 如果引擎提供原生精确稀疏选择，能否区分预取失误与实际选择误差，并给未命中项提供确定性补齐？
