# FlexGen：在单张 GPU 上利用多级存储运行大模型（ICML 2023）

> **原题**：FlexGen: High-Throughput Generative Inference of Large Language Models with a Single GPU

> **一句话总结**：当模型权重和 KV cache 超过显存时，FlexGen 联合安排 GPU、CPU 内存和 SSD 上的张量放置、批次遍历及计算；在单张 16 GB T4 上运行 OPT-175B、输入 512 和输出 32 token，四位压缩配置以约 4072 秒处理 144 条请求，生成吞吐为 1.122 token/s（§4–6、表 19）。[^paper]

## 问题与动机

单 GPU 装不下大模型时，权重、激活和历史 KV 都可能被放到 CPU 内存或 SSD。生成每个 token 需要跨模型层反复读取这些数据，存储容量足够并不意味着带宽也足够。若每个小批次单独遍历所有层，同一层权重会被重复加载，慢层 I/O 很容易盖过 GPU 计算（§1、§4.1–4.2）。[^paper]

作者关注可以等待较长时间的离线生成。对固定数据集使用较大的有效批次，让一次权重加载服务多个 GPU 批次，可以摊薄权重 I/O。代价是需要同时保留更多请求的 KV 和激活，单个请求也要等待整个执行块。它不是针对在线聊天首 token 延迟设计的系统。[^paper]

## 关键观察 / 隐含假设

- **观察 1：增大批次可以复用权重，但也会扩大 KV 容量。** 图 2 中同一层的多个批次共享一次权重加载；OPT-175B、512 输入、32 输出、批量 512 时，论文估算 KV 约 1.2 TB，高于 325 GB 权重（§3、图 2）。[^paper]
  - **依赖假设**：存在足够多可以一起执行的请求，且其他层能容纳批次产生的 KV 和激活。在线低到达率、长度长尾或紧张的 CPU／SSD 容量会削弱批次收益；上述体积不是所有模型的固定比例。
- **观察 2：历史 KV 的搬运量随序列长度增加。** 在论文的简化模型中，把 CPU 上的完整 KV 移到 GPU 约需 $4bsh$ 字节，而交换 CPU 注意力所需激活约需 $4bh$ 字节（§4.2）。[^paper]
  - **依赖假设**：CPU 内存带宽和注意力计算能够跟上 GPU 工作，跨设备同步与其他流量足够小；通信字节少 $s$ 倍不意味着端到端时延也少 $s$ 倍。
- **观察 3：固定形状下可以画像和搜索放置策略。** 论文给出 GPU、CPU、磁盘容量约束及计算／I/O 时间估算，并在枚举批次后用线性规划选择放置比例（§4.3）。[^paper]
  - **依赖假设**：输入输出长度、硬件带宽和可用内存接近画像，计算与 I/O 能充分重叠。动态到达、碎片、多租户竞争和不完美重叠都可能使搜索结果偏离实际表现。

## 核心方法

### 计算顺序：用多个 GPU 批次复用一层权重

FlexGen 按生成步和层遍历计算图：一层权重载入后，对执行块中的多个 GPU 批次依次处理，再转入下一层。**有效批次 = GPU 批次大小 × 一个执行块中的 GPU 批次数**。它同时安排下一层权重、下一批缓存及激活的读取，上一批缓存及激活的写回与当前批次计算重叠（§4.2、算法 1）。[^paper]

假设 GPU 一次只能处理 4 个请求，但系统为 32 个请求保留了慢层缓存，可以将它们分为 8 个 GPU 批次。对当前层，系统加载一次权重并依次处理这 8 批，之后才进入下一层；代价是其他批次的激活和 KV 要跨越层间等待。若先让第 1 批独自完成所有层，再处理第 2 批，就需要重新读取模型权重。这里增加的是**有效批次**，不是把 32 个请求同时塞入显存。[^paper]

算法的内层还并发发起六类工作：当前批次计算，下一层权重读取，下一批的缓存与激活读取，以及上一批的缓存与激活写回；各任务在同步点汇合后推进。论文依靠操作系统和 CUDA 调度底层资源，逻辑并发不代表 SSD、CPU 内存和 PCIe 一定能同时达到各自峰值。尤其是读写共用设备时，重叠收益需要实际测量（算法 1）。[^paper]

论文证明所选块遍历的 I/O 复杂度在其形式化模型内不超过最优值的两倍；更优的对角遍历未被实现。这个理论界限不是端到端延迟或吞吐的两倍保证，不能忽略真实硬件并发、内存碎片与运行时开销（定理 4.1、附录 A.2）。[^paper]

### 张量放置与策略搜索

系统分别为权重、激活和 KV 指定 GPU、CPU 和磁盘上的放置比例。权重按层切分，激活和 KV 在张量内切分。代价模型估计每层的计算、CPU–GPU 和磁盘–CPU 传输时间以及峰值容量；枚举有限的批次配置，再用线性规划选择张量放置（§4.2–4.3）。[^paper]

可以把策略写成三组比例：权重 $w_g,w_c,w_d$、激活 $h_g,h_c,h_d$、KV $c_g,c_c,c_d$，每组内部之和均为 1，下标分别指 GPU、CPU 和磁盘。固定 GPU 批次大小与有效批次后，模型在三层存储容量约束内选择这九个比例。它分别估计一层 prefill 和一层 decode 的时间：

$$
T_{\mathrm{pre/gen}}\approx\max(T_{C\to G},T_{G\to C},T_{D\to C},T_{C\to D},T_{\mathrm{compute}}),\quad
T\approx L\bigl(T_{\mathrm{pre}}+(n-1)T_{\mathrm{gen}}\bigr).
$$

这里 $L$ 是层数，$n$ 是输出长度；四条 I/O 路径的费用分别由张量体积、放置比例和画像带宽估计。搜索目标是降低一个有效批次的 $T/\text{有效批次}$，而不是最小化单个请求的首次响应时间。它先枚举批次组合，再将放置比例视为连续变量求解线性规划（§4.3、式 1）。[^paper]

模型使用理想重叠近似，将不同路径的时间以最大值估计。论文承认放置比例的连续化和峰值内存估计可能导致实际 OOM，需要手动调整；手工调参也可能找到更好的方案。因而策略搜索的结果是受模型假设限制的候选，不是硬件最优性证明。[^paper]

### CPU 计算与近似选项

当 KV 位于 CPU 时，FlexGen 可以把对应的解码注意力交给 CPU，减少整段 KV 的反复传输；其他操作仍可由 GPU 执行。这个设计早于 [[NEO-MLSys25]]，但两者的目标和调度不同：NEO 面向在线负载，以请求为单位在 CPU、GPU 间分配并安排非对称流水线。[^paper]

论文用批次 $b$、历史长度 $s$ 和隐藏维度 $h$ 估算：把 FP16 K、V 全部传往 GPU 的量约为 $4bsh$ 字节，而把注意力所需的激活在 CPU 和 GPU 间传递约为 $4bh$ 字节；在该简化模型下通信量可相差 $s$ 倍。它只比较这两类数据移动，并不把 CPU 计算、同步和其他传输算成零，实际时延也不必降低 $s$ 倍（§4.2）。[^paper]

论文还提供两类可选近似：将权重和 KV 按 64 个元素分组量化至 4 bit，以及只读取注意力得分最高的一部分 Value。量化数据在计算前反量化；开启量化时作者关闭 CPU 计算委派以避免压缩开销。**基础卸载不要求量化，但论文的 1.122 token/s 配置使用了有损量化。**“准确率接近”只覆盖论文测试，不保证输出逐位一致（§5–6.2）。[^paper]

两种近似节省的对象不同。分组量化根据每组最小值和最大值映射到 4 bit，主要减少权重与 KV 的存储和 I/O，不依赖低比特矩阵乘法；稀疏选项仍须利用 K 计算注意力分数，再只读取 top-k 对应的 V。后者并不是先预测并只读取少量 K，也不能把只读 10% V 解释为所有 KV 流量减少 90%（§5）。[^paper]

### 多 GPU 与单 GPU 的策略边界

论文还讨论将模型层均分到多张 GPU 的流水线并行：每个设备处理自己的层，单设备放置搜索可以复用，额外的流水线负责在设备之间传递中间结果。它选择流水线而不是把每层矩阵跨设备做张量并行，是因为本文优先考虑吞吐和通信成本，而非单请求延迟（§4.4）。[^paper]

更多 GPU 不仅提供算力，也改变每台机器的容量约束。例如模型被拆开后，原先要放到磁盘的权重可能只需放到 CPU 内存，或可选更大批次；因此 decode 吞吐有可能出现超过设备数线性比例的增长。论文也指出 prefill 流水线存在气泡，32 token 输出下统计了 prefill 的整体生成吞吐并未达到线性扩展。不能将解码阶段的超线性结果直接当作端到端超线性扩展（§6.1、表 3）。[^paper]

## 设计取舍

- **复用权重换更长批次等待**：权重读取摊薄，但活跃 KV 和激活需在其他层长期驻留。
- **CPU 计算换 CPU 内存带宽**：避免搬回完整 KV，却会引入 CPU 注意力计算和较小张量的跨设备传输。
- **压缩换容量与 I/O**：四位量化减小存储和读取量，也增加量化误差、压缩／反量化成本。
- **静态搜索换在线适应性**：离线画像可快速筛选，但输入输出长度、带宽或可用内存变化后需要重新评估。

## 实验与结果

主平台是单张 T4 16 GB、208 GB CPU DRAM 和 1.5 TB SSD；主要模型为 OPT-6.7B 至 OPT-175B。吞吐定义为**生成 token 数除以 prefill 与 decode 的总时间**。合成吞吐实验使用占位权重，准确率实验使用真实权重；部分耗时过长的基线用较少生成步外推（§6）。[^paper]

| 对照 | 数据与条件 |
|---|---|
| 离线吞吐与延迟 | OPT-175B、512 输入、32 输出时，未压缩 FlexGen 有效批次 256，0.687 token/s、11916 秒；四位配置批次 144，1.122 token/s、4072 秒。两者的批次和量化不同（表 19）。 |
| 同量级延迟比较 | 同一模型与长度下，未压缩 FlexGen 批次 64 为 0.421 token/s、4864 秒；DeepSpeed 批次 1 为 0.006 token/s、5024 秒。基线仅能使用很小批次，比较依赖当时实现（表 19）。 |
| 消融 | OPT-30B 未压缩设置中，全优化为 7.32 token/s；去掉计算与 I/O 重叠为 5.86，去掉 CPU 计算为 4.03；175B 对应为 0.69、0.59、0.62。各行策略需要结合表中的实际放置阅读（表 23）。 |
| 存储路径 | 175B、原始本地 SSD 配置为 0.69 token/s；控制 OS page cache 的对应测试为 0.49。使用较慢持久 SSD 时约 0.30，说明磁盘与页缓存状态会改变测得吞吐（表 24）。 |
| 可变长度 | HELM 的 MMLU 例子有效 token 吞吐为填充后吞吐的 75%；不同长度按最长序列填充会浪费计算，效果随长度分布变化（表 25）。 |
| 近似质量 | OPT-175B 在 Lambada 上 FP16、4-bit、4-bit 加稀疏 Value 分别为 0.758、0.756、0.756；WikiText 困惑度分别为 10.82、10.94、10.94。作者也指出 3-bit 未能保持准确率；这些任务不能替代其他应用的质量评估（表 5、§6.2）。 |

主结果中的压缩配置不仅减少读取字节，还改变了能放进主机内存的工作集：作者指出 OPT-175B 的压缩版本可以避免慢磁盘交换，同时有效批次从未压缩方案的 256 变为 144。因此表 19 的 1.122 与 0.687 token/s 差异是**精度、批次和数据放置共同变化**的结果，不是纯粹的 4-bit 算子加速（§6.1、附录 A.4）。[^paper]

## 批判性分析

### 论证链条

论文从权重重复读取和 KV 容量冲突出发，提出块遍历、联合放置和重叠，再分别做组件消融。实验支持这些设计在离线、内存受限配置中有效；它没有证明当前在线推理引擎在相同负载下也能获得同样收益。

### 假设压力测试

请求到达稀疏或长度差异很大时，难以组成固定有效批次；更快 GPU 可能进一步放大慢存储瓶颈。CPU 委派能否有效取决于内存带宽和并发争用。模型架构、精度和 KV 规模变化后，原来的放置策略和质量实验都需要重测。

### 实验可信度与系统性缺陷

论文提供了参数、基线、消融和 page cache 敏感性，但部分性能数据使用占位权重或外推，且基线来自 2023 年。论文的主要指标不覆盖在线 P99、服务隔离和混合工作负载；多级异步调度的故障恢复也没有作为主实验评估。把理论 I/O 界限直接外推到在线吞吐是不成立的。[^paper]

## 局限与后续工作

- 对照 [[InfiniGen-OSDI24]]、[[DirectKV-OSDI26]] 和 [[NEO-MLSys25]] 时，应固定模型、精度、完整历史保留方式与硬件，分别测量 GPU、CPU 和互连时间。
- 测试变长请求、不同磁盘缓存状态及并发 I/O；除吞吐外报告首 token、每 token 延迟和所占 DRAM、SSD 容量。
- 将完整计算、四位量化和稀疏选择分开比较，不能把一个配置的速度和另一个配置的正确性合并。
