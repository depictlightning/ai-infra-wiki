# Stream2LLM：重叠上下文检索与预填充（MLSys 2026）

> **原题**：Stream2LLM: Overlap Context Streaming and Prefill for Reduced Time-to-First-Token

> **一句话总结**：当检索上下文分批到达或不断被替换时，Stream2LLM 提前执行 prefill，并结合前缀失效、请求优先级和成本驱动的 KV 抢占，减少等待完整上下文后的计算延迟；收益取决于检索模式和资源压力。[^paper]

**阅读状态**：已阅读会议正式版 MinerU 全文和附录，回看 TTFT 图及内存压力实验表。[^paper]

## 问题与动机

检索增强生成需要先取得外部上下文。若等待检索全部结束再开始 prefill，检索与 GPU 计算串行；若直接用不完整内容生成答案，又可能损失质量。一个折中方案是在检索期间提前计算已有上下文，同时等待最终输入确定后再完成请求（§1–2）。[^paper]

多请求并发使问题更复杂：到达较早的部分 KV 会占用显存，后到的内容可能改变已经计算的前缀，内存不足还会迫使系统选择重算或交换。Stream2LLM 修改 vLLM 的预填充调度与缓存管理，处理这些交互（§3–5）。[^paper]

## 关键观察 / 隐含假设

- **可流式输出的检索过程**：追加模式中结果按最终顺序陆续到达；更新模式中候选结果可能被替换。需要检索侧提供分块、更新和结束信号（§2.4、§5）。[^paper]
- **因果前缀可复用**：先前 token 一旦改变，其后的 KV 不能直接视作有效；越靠前的位置发生变化，最长公共前缀越短，重算越多（§4.2）。[^paper]
- **性能模型依赖硬件和负载**：实现采用空闲系统离线测得的静态重算与交换成本；PCIe 竞争和实际并发可能使预测偏离（§4.3）。[^paper]
- **评测集中在 prefill**：论文假设 prefill/decode 分离，未评测 decode 的 TPOT，不能据此认定完整 P/D 服务没有额外开销（§4、§6.1）。[^paper]

## 核心方法

### 输入变化与 KV 失效

追加模式逐步增加文档，更新模式可替换既有文档。系统比较旧、新 token 序列的最长公共前缀，保留前缀对应的缓存，使之后的缓存失效并重新计算。如果上下文插在问题文本之前，即使是新增文档，原问题对应的后缀也可能需要重算（§4.2）。[^paper]

被换出到 CPU 的请求收到更新时，系统也要使 CPU 上过期部分失效；恢复时先换入仍有效的前缀，再从变化位置重算。这样防止旧上下文对应的 KV 被误用（§4.2）。[^paper]

### 两阶段调度与抢占

第一阶段按策略为未完成请求排序，并分析 token 预算与 KV 块需求；第二阶段分配资源，内存不足时从未安排请求中按优先级反向选择牺牲者。两阶段将请求排序与具体的缓存分配、抢占动作分开（§4.1）。[^paper]

系统离线测量不同 token 数的 prefill 与 KV 块交换成本，抢占时选预测成本较低的重算或 CPU 交换。重算释放 KV、恢复时重新 prefill；交换保留状态但消耗主机内存与传输带宽（§4.3）。[^paper]

论文比较 FCFS、MCPS 与 LCAS：前者优先已收齐输入的请求；MCPS 优先已计算 token 较多的请求；LCAS 根据最近分块到达时间排序，也优先完成输入的请求。LCAS 可能让很久没有新分块的请求长期等待；MCPS 在前缀被更新后可能使进度回退的请求优先级下降（§4.4）。[^paper]

## 设计取舍

- **提前计算换等待重叠**：如果上下文后续频繁变化，提前工作可能失效并增加总计算量。
- **保留 KV 换显存压力**：延迟较长的检索请求长期持有缓存，会挤占其他请求。
- **交换与重算依赖成本条件**：前者消耗传输和主机内存，后者消耗 GPU 计算；静态空闲测量不能捕捉所有争用。

## 实验与结果

论文以 Llama-3.1-8B-Instruct、张量并行度 2 在 H100/H200 上测试。爬虫负载使用 SimpleQA 问题和逐页过滤的检索轨迹；更新负载采用 FineWeb-Edu、SQuAD 和渐进式近邻检索。请求以不同 QPS 重放（§6.1）。[^paper]

| 结果 | 条件与边界 |
|---|---|
| 爬虫负载中位 TTFT 最多改善 10.8–11.0 倍 | H200、4 QPS，流式方案对非流式 vLLM 基线；这是流式体系相对等待完整输入的收益，不是某个新调度策略单独贡献（§6.2、图 8）。 |
| 同一爬虫负载中不同策略差异明显 | 4 QPS 时 FCFS、LCAS 的 P95 相对默认流式调度分别为 3.16、2.64 倍；MCPS 为 0.71 倍，反而变慢（§6.2）。 |
| 更新负载存在明显失效开销 | 在所测 QPS 下，超过 10% 的请求累计使超过 1 万个 token 的缓存失效；这不是说同时有 1 万个 token 常驻（§6.2、图 11）。 |
| 默认流式策略可能产生长尾退化 | 为制造内存压力，论文将爬虫分块延迟放大 10 倍、近邻检索放大 30 倍；默认流式方案的 P99 相对非流式为 0.71 倍和 0.19 倍，后者约慢 5.3 倍（§6.4、表 3）。 |
| 成本策略并非所有情况下最优 | 同一压力爬虫实验中，FCFS 的 P99：纯重算为 10.03 倍，成本策略为 8.62 倍，纯交换为 6.69 倍，均相对非流式基线（表 3）。 |

论文以整条轨迹完成时间作为吞吐代理，在所测场景下报告策略曲线接近；该指标受请求到达和检索时间影响，不能单独证明所有负载下 GPU token 吞吐完全相同（§6.3、附录 A.2）。[^paper]

## 批判性分析

### 论证链条

论文将流式架构相对非流式的收益，与不同调度和抢占策略之间的收益分开，内存压力实验也给出不佳的策略结果。最长公共前缀机制保证缓存复用边界，但不能消除更新导致的全部重复工作。[^paper]

### 假设压力测试

若检索结果必须全局重排、频繁修改早期文档，或系统的 CPU–GPU 链路拥塞，论文中的追加顺序和静态交换成本可能不再成立。LCAS 的饥饿风险也需要服务级公平性约束；这些是部署时需验证的问题，不是论文已测得的结果。[^paper]

### 实验可信度

工作负载来自作者构建并记录的检索流程，再以多种 QPS 重放；内存压力场景进一步人为放大分块间隔。最终结果依赖模型、检索延迟、上下文布局与硬件，论文未测完整 decode 路径或输出质量变化。[^paper]

## 局限与后续工作

- 在端到端 P/D 部署中测量 KV 交接、TPOT、实际 GPU 吞吐及完整用户延迟。
- 比较动态链路争用、更早位置的上下文变更和长期公平性，并核实流式预填充与最终输入的一致性。
