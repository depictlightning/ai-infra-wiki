# InfiniGen：用动态 KV 选择减少长上下文推理的数据搬运（OSDI 2024）

> **原题**：InfiniGen: Efficient Generative Inference of Large Language Models with Dynamic KV Cache Management

> **一句话总结**：在完整 KV 放在主机内存、CPU–GPU 传输成为瓶颈时，InfiniGen 利用前一层的输入和下一层的部分 Key 预测重要 token，只提前取回所选 KV；在 OPT-13B、单张 RTX A6000、总长 2048 的实验中，它随批量增加获得高于 FlexGen 基线的吞吐，但预测和稀疏注意力会改变原模型的计算。[^paper]

**阅读状态**：已阅读 OSDI 2024 会议版全文，重点对照公式 2–3、图 8–11、13–17 和表 2。MinerU 的文本输出包含图像占位符，架构与结果图使用原 PDF 核对；未运行作者代码或复现实验。[^paper]

## 问题与动机

生成每个新 token 时，解码注意力需要访问此前所有 token 的 Key 和 Value。KV cache 随序列长度、层数和并发请求数增长，可能超过显存。把 KV 存入 CPU 内存可以扩大容量，但在每一层、每一步都把完整 KV 搬回 GPU，会让 PCIe 传输成为瓶颈（§3.1、图 2–3）。[^paper]

一种处理方式是永久删除不常被关注的历史 token。论文指出，某个 token 在当前步不重要，不意味着以后也不重要：一旦它的 KV 被彻底删除，未来需要时无法直接召回。固定保留比例也无法体现不同层和不同生成步骤所需 token 数的差异（§3.2）。[^paper]

InfiniGen 的核心问题是：**能否保留较大的历史候选池，但只为当前注意力计算跨 CPU–GPU 互连传输少量 KV？** 它在 GPU 上提前估计下一层需要哪些 token，再从主机内存取回所选 Key、Value。它是一种分层存储与近似注意力方案，不是让 CPU 承担主要模型层计算的异构计算引擎。[^paper]

## 关键观察 / 隐含假设

- **注意力重要性会随时间和层变化。** 在 OPT-6.7B、PG-19 的一个 2000 token 例子中，论文比较只能保留 200 个 token 的 H2O 与每一步都能从完整历史中选择 200 个 token 的理想选择器；超出缓存预算后，前者的注意力相似度下降更明显（§3.2、图 4）。理想选择器需要完整信息，是分析上界，不是可直接部署的基线。[^paper]
- **需要的 token 数不是固定比例。** 论文按累积注意力权重达到 0.9 的规则分析 OPT-6.7B：第 0 层需求分布较宽，第 18 层更集中；第 18 层不同生成步需要的 token 数也不同（图 5）。这是特定模型和样本上的测量，不能推断所有新模型都具有相同稀疏度。[^paper]
- **相邻层输入具有可利用的相似性。** 表 1 使用 PG-19 的一个 2000 token 样本，报告相邻 Transformer 块输入的平均余弦相似度：OPT 系列为 0.95–0.97，Llama-2 为 0.89–0.91。论文用残差连接、异常值通道及归一化解释这一现象；输入相似不直接保证注意力排序相同，因此预测仍需质量实验验证（§4.2）。[^paper]
- **资源假设是主机内存够用且传输可被部分隐藏。** GPU 必须容纳用于预测的部分 Key 和 Query 权重，CPU 内存必须容纳历史 KV；选择器与预取也要足够快。低带宽互连更容易让搬运成为瓶颈，但复杂访问、带宽饱和和额外索引会降低收益。[^paper]

## 核心方法

### 先分清三份数据在哪里

InfiniGen 将每层历史的完整或大部分 KV 放在 **CPU 内存池**；保留用于轻量预测的 **部分 Key 和部分 Query 权重**在 GPU；每步选中的 **完整 Key 和 Value**从 CPU 内存取回 GPU，供当前注意力计算。预测阶段主要在 GPU 执行，主机侧负责保存和提供数据（图 6、8、§6.2）。[^paper]

例如，历史有 2048 个 token 时，系统可以先在 GPU 上用每个 token 的少量 Key 通道估计分数，选出本次有可能重要的 token，再只搬这些 token 的完整 KV。它保留的是**每个 token 的部分 Key 通道**作为索引，不是只为少数预先确定的 token 保存完整索引。最终参与注意力的是被选 token 的完整 Key 和 Value。[^paper]

不把某个 token 取回 GPU，只意味着它在这次注意力计算中被跳过；当 CPU 内存池没有触发容量淘汰时，它仍可在后续步骤重新被选中。这与彻底删除历史 KV 的方案不同（§4.1、4.4）。[^paper]

### 离线变换：让少量通道更适合做预测

若直接只用 Query 和 Key 的一部分通道，可能漏掉决定注意力排序的信息。InfiniGen 先用样本输入运行一次模型，按层收集 Query 矩阵并做奇异值分解（SVD），得到用于重排信息方向的正交矩阵 `A`；随后将该矩阵并入对应层的 Query 和 Key 权重（§4.2–4.3）。[^paper]

设原始查询和键为 `Q`、`K`，完整维度的数学变换为：

```text
Q' = Q A，K' = K A，且 A Aᵀ = I
Q' K'ᵀ = Q A Aᵀ Kᵀ = Q Kᵀ
```

这个等式说明：**只看完整维度的正交变换，注意力点积在精确数学运算下不变**。作者希望让变换后少数通道更能代表原始信息，从而在下一步用少量通道估计分数。等式不证明后续删去通道、预测下一层输入或跳过 token 后仍与完整注意力一致；有限精度也需要单独验证（式 2–3）。[^paper]

这一步是离线改写权重，需要样本和预处理；论文把修改后的权重直接用于运行时，不在每一步额外执行完整矩阵变换。作者将通道分布的稳定性归因于模型性质，但只用有限模型和任务评估了效果。[^paper]

### Prefill：选取部分通道并建立预测材料

处理输入提示时，系统观察每层变换后的 Query 和 Key，取各元素绝对值并合并，对每列求和，选择列得分最高的部分通道。相同的列索引用于 Query 权重与 Key cache，确保两侧相乘时对应同一特征。论文实验使用 **30% 的通道**（§4.3、图 9）。[^paper]

这里要区分两个比例：**30% 是预测时使用的特征通道比例**；后文“平均少于 10%”指每层注意力实际取回并使用的 **token KV 条目比例**。这两个分母不同，不能推导出总显存只剩完整 KV 的 3%，也不能把 30% 解释为只在 CPU 保存 30% 历史 token。[^paper]

### Decode：提前一层预测并按阈值取回

在执行第 `i−1` 层时，InfiniGen 用该层的注意力输入近似下一层输入，并与第 `i` 层的部分 Query 权重相乘，得到预测 Query；再与第 `i` 层的部分 Key cache 相乘，得到历史 token 的**预测注意力分数**（图 8、10）。选出的 token 索引交给主机侧，系统预取这些 token 在第 `i` 层的完整 Key 和 Value，并尝试让传输与前一层计算重叠。[^paper]

对预测得分 `ŝ`，论文选择分数大于 `max(ŝ) − α` 的 token。`α` 越大，通常会选择更多 token，传输与注意力计算开销增加，预测遗漏可能减少。实验中 OPT 使用 `α = 4`，Llama-2 使用 `α = 5`；作者将每层取回数量限制为最多完整 KV 的 20%，并报告跨层平均使用比例低于 10%（§4.3、§5.1）。[^paper]

阈值中一个 token 比最高分低 5，意味着它的 softmax 权重相对最高项约为 `e⁻⁵`。这只是**单项相对最高项**的比例：许多低分项累积后仍可能有较大总权重，更不能保证预测分数排序与真实排序一致。论文的质量结果是经验性证据，不是误差上界。[^paper]

多头注意力需要批量执行，论文说明会根据各头超过阈值的 token 数求平均，使同一层的各头取回数量一致；这会使实际选择受到批处理形状的约束。预测从第 1 层开始，论文认为利用相邻层输入相似性所需的异常值在第 0 层计算后才出现（§4.3）。[^paper]

### CPU 内存不足时：可选的永久淘汰

主机内存同样有限。系统支持为 KV 池设置容量上限：达到上限时，选择一个条目作为牺牲者，用新 KV 覆盖，并同步更新 GPU 上对应的部分 Key。此时被淘汰的历史 KV **不能再直接召回**；因此“始终保留完整历史”只适用于主机池未发生淘汰的条件（§4.4）。[^paper]

论文比较 FIFO、LRU 和计数器策略。计数器对每次被预取的条目加一，选择计数最小者淘汰，计数器饱和时统一减半。作者选择它，是因为所测质量与 LRU 接近，同时避免 LRU 链表更新可能带来的同步开销；这不是对任意访问模式都最优的证明。[^paper]

## 设计取舍

- **少搬数据与预测成本**：部分 Key 扫描、额外 Query 投影、筛选索引和主机侧不规则读取均有成本；选中集合太分散时，字节数减少未必等比例变成有效带宽提升。
- **可召回与主机容量**：保留历史让临时不重要的 token 有机会重新进入注意力，但 CPU 内存随请求数和上下文长度增长；启用池上限后仍会永久删除部分历史。
- **预测质量与显存占用**：30% 的部分 Key 通道提高预测信息量，却需要长驻 GPU；论文估算它约占完整 KV 大小的 15%，而部分 Query 权重约占模型参数大小的 2.5%（§6.2）。两者不是全部系统开销。[^paper]
- **精度与延迟**：较大的 `α` 一般取回更多 KV、增加耗时；较小阈值可能漏掉重要 token。选择错误会改变 softmax 的分母与输出，系统并不进行完整注意力核验。[^paper]
- **预取与依赖**：在前一层预测下一层可隐藏部分 PCIe 等待，但仍必须等选中 KV 到达才能使用。预测过晚、传输未完成或其他流量争抢链路时，等待会留在关键路径。[^paper]

## 实验与结果

### 设备、模型和比较对象

论文主要使用一张 **NVIDIA RTX A6000 48 GB**、Intel Xeon Gold 6136、96 GB DDR4-2666 主机内存，CPU–GPU 互连为 **PCIe 3.0 ×16**。模型为 OPT-6.7B/13B/30B 和 Llama-2-7B/13B；质量评估使用五个 5-shot 任务，以及 WikiText-2、PTB 困惑度。性能使用 FlexGen 或 CUDA UVM 作为卸载环境，并比较 H2O 及 KV 量化（§5.1）。[^paper]

论文报告推理总墙钟时间，包含 prefill 与 decode；不同图使用不同输入、输出、批量与基线，不能把所有倍数当成同一条件下的速度排名。[^paper]

### 消融和长上下文

图 13 在 OPT-6.7B、固定 20% KV 预算下比较是否使用正交变换：不变换时多个任务准确率下降，变换后更接近完整缓存。这个消融支持变换能改善所测预测效果，但不能单独证明每个被选 token 都正确（§5.2）。[^paper]

在 OPT-6.7B、1920 输入、128 输出和批量 8 的实验中，作者改变 `α` 与部分通道比例。`α` 增大时，准确率先提高，之后收益趋于平缓而延迟继续增长；部分通道比例超过 0.3 后，所测准确率改善不明显，但其显存占用仍随比例上升（§6.1、图 17）。该结论针对所测 WinoGrande 与硬件配置。[^paper]

论文还用 Llama-2-7B-32K、WikiText-2 测 32K 窗口下的困惑度，以及用 Llama-3-8B-1048K 分析百万 token 场景下的注意力分布（§6.3、图 19–20）。后者是注意力模式分析，**不能当成已经完成百万 token 端到端部署的延迟或吞吐实验**。[^paper]

## 批判性分析

### 论证链条

论文先以固定 KV 预算下的注意力变化说明永久淘汰可能遗漏后续重要 token，再以相邻层输入相似和正交变换支持提前预测，最后用语言任务、困惑度、速度和消融实验验证取舍。图 13 支持变换有助于该模型的预测；图 15–16 支持在指定卸载栈中减少传输可改善速度。[^paper]

链条中仍有两个近似：前一层输入并非下一层的真实输入；部分通道打分也不是完整 Query–Key 点积。即使离线旋转数学上保持完整点积，也不能把整个系统描述成无损推理。主机池触发淘汰时，可召回窗口还会进一步缩小。[^paper]

### CPU–GPU 协同的边界

InfiniGen 的 CPU 主要提供**容量和数据来源**，GPU 运行预测与注意力；图 8 的 CPU 时间线体现的是预取数据路径。作者在 §6.2 提到可以把部分 Key 放到 CPU，让 CPU 根据从 GPU 取回的部分 Query 做预测，以减少显存占用，但这是一项替代设计建议，论文主实验没有据此给出 CPU 预测的端到端收益。[^paper]

[[KTransformers-SOSP25]] 则将 MoE 专家的实际计算安排在 CPU，并让 GPU 处理其他模型部分；两者在 CPU 的角色、传输方向和模型结构上不同。要比较它们的资源效率，应分别测 CPU 计算、主机内存带宽、PCIe 流量、GPU 空档和输出质量，而不能只看“卸载比例”。[^paper]

### 假设压力测试

相邻层相似性和注意力稀疏度可能随模型架构、上下文任务、位置编码、输入分布及层而变化。长文检索、需要追溯久远上下文、同一层大量小权重累积，或低频 token 在后续突然变重要时，都需要测量预测召回和任务准确率；这些是基于机制的风险判断，不是论文已证明的失败案例。[^paper]

当主机内存不足、批量过大、权重也需要走 PCIe，或互连升级为高速 CPU–GPU 链路时，瓶颈可能改变。特别是 GPU 长驻的部分 Key 仍随上下文和请求数增长，主机池、索引、预测计算及元数据都应计入资源预算。[^paper]

### 实验可信度与后续比较

论文比较了相同卸载环境中的完整 KV、INT4 和 H2O，并测了质量、性能和变换消融；但主要实验是旧版 OPT、Llama-2 和单 GPU，未覆盖新的 GQA/MoE 模型、现代多卡互连、多租户和真实在线请求的 P99 TTFT/TPOT。相关性不等同于模型质量保证，也没有验证所有生成 token 与完整注意力一致。[^paper]

[[OPKV-MLSys26]] 将 InfiniGen 作为可接入选择器之一，研究稀疏选择后的分页聚合与回载；它关注**被选数据怎样搬**，InfiniGen 关注**哪些数据值得提前搬**。OPKV 的实验是作者对 InfiniGen 的移植和不同设备配置，不能把其加速直接当作原始 OSDI 原型的结果。[[DirectKV-OSDI26]] 则研究 GPU 经高速互连直接访问主机 KV，传输路径和适用硬件与本文不同。[^paper]

## 局限与后续工作

- 在统一 CPU、GPU、互连和内存预算下，比较 InfiniGen 的 GPU 预测、作者提出的 CPU 预测替代设计、完整搬运与直接访问主机内存，分别测预测时间、互连字节数、CPU 带宽和端到端 TPOT。
- 记录索引占用、完整 CPU KV、GPU 热数据、元数据和预取缓冲区，避免只以被选 token 比例估算总内存。
- 跨模型和长上下文任务测预测 token 的召回率、遗漏注意力质量、生成差异与任务准确率；特别区分单项权重阈值和被遗漏 token 的总权重。
- 改变主机池预算与访问突发，比较 FIFO、LRU、计数器和无淘汰时的质量及实际管理开销。
- 在真实在线到达、多请求、不同 PCIe/NVLink 拓扑和权重同时卸载时，测吞吐、TTFT、P99 TPOT 及预取等待，而非将离线批量结果直接外推。
