# TensorHub：弹性 RL 训练中的权重传输（SOSP 2026）

> **原题**：TensorHub: Scalable and Elastic Weight Transfer for LLM RL Training

> **一句话总结**：RL 训练中新版权重需要周期性送到大量 rollout worker；TensorHub 把已有 worker 上的权重副本当作可读“存储”，用引用、拓扑感知传输和一致性协议组织更新。论文报告独立 rollout 的 GPU 停顿最高减少 6.7 倍、弹性 rollout 的更新最高加速 4.8 倍、跨数据中心停顿最高减少 19 倍（摘要、§6）。

## 问题与动机

大模型 RL 在训练器更新权重后，必须让生成样本的 rollout worker 使用新版本。规模达到数千 GPU 时，权重可能是 TB 级，传统做法需要训练器向多个消费者推送，或先存一份完整权重再由消费者读取。前者容易形成扇出瓶颈，后者增加写入和存储成本；集群弹性扩缩还会使消费者集合不断变化（§1–§2）。

论文区分三类真实使用场景：稳定训练器与独立 rollout 之间每步更新；spot GPU 临时加入/退出后需要拉取当前权重；远端数据中心有空闲 rollout 算力但跨域链路慢（§2、§5.2–§5.4）。三者的瓶颈依次偏向协调停顿、动态源选择和跨域重复传输。因此只调快一次 RDMA copy，不足以解决整个 RL 闭环的 GPU 闲置。

## 关键观察 / 隐含假设

- **rollout worker 已天然复制了权重**：多数时候无需另建完整持久副本，可以把 worker 上的权重视为受管理的引用源（§3、图 2）。这要求在读取期间源 worker 的相应版本不可被无序覆盖。
- **传输开销受拓扑和分片布局控制**：同机、跨机、跨数据中心有不同带宽和故障域；模型并行时还需确认所取各分片属于同一版本（§4–§5、图 5–6）。
- **弹性下可用源会变化**：元数据只能提供当前引用，不能保证源始终存活。因此恢复和源选择是存储抽象的一部分，而非传输失败后的临时补丁。
- **权重版本短命但不能随意消失**：RL 常只需最新或最近若干版本，长期持久性不在热路径；若最后一个可用副本在新 rollout 拉取前被覆盖，训练仍会短暂卡住（§3.3）。
- **模型并行组必须做一致决策**：同组不同 shard 若分别把 `latest` 解析成版本 12 与 13，SPMD 控制流可能分叉并挂起（§4.4、图 6）。这不是字节传输正确性问题，而是控制面版本一致性问题。

## 核心方法

Reference-Oriented Storage（ROS，引用式存储）提供 `publish`、`replicate`、`unpublish` 等操作。引用服务器只保存哪个 worker 持有哪个版本及其分片，不接收权重字节；读者拿到源引用后直接从 GPU 内存发 RDMA 读取，读完后自己也成为可服务的副本（§3.1、图 2、表 2）。命名层级是模型→版本→副本→分片；除了绝对版本号还支持 `latest` 与 `latest-k`，适配允许有限陈旧权重的异步 RL（§4.1、图 3）。

这种“存储”必须自行维护两个性质。可变性契约要求发布后的数据不可修改；调用 `unpublish` 时服务器先隐藏该源，再等已有传输完成才允许覆写，防止消费者读到新旧混合权重（§3.2）。保留协议允许指定最近若干版本；如果一个保留版本只剩最后一个源，撤销前先在 CPU 内存保一份临时副本。论文测得 PCIe 卸载约 48 GB/s、整个 GPU 权重卸载导致的 `unpublish` 延迟低于 2 秒；这条罕见回退路径说明“零额外副本”只在正常路径成立（§3.3）。

TensorHub 在 ROS 之上分配传输源并依拓扑做流水复制。服务器优先挑同数据中心的源，再按当前正在服务的请求数选择较空闲副本；数据面保持去中心化，可走直接注册 GPU 缓冲区的 RDMA read、避免频繁注册的 RDMA copy，或跨域 TCP（§4.3）。新副本无需等全部 tensor 收齐才转发，已完成部分可作为下游源，形成流水复制（图 5）。因此一个训练器面对多个 rollout 时，不会独自承担全部扇出。

同一个模型并行副本的 shard 调用由引用服务器作为事务整体解析；图 6 中两个 shard 即使请求先后跨过版本 13 的发布，也都得到同一快照版本 12。不同副本之间不强制一致，适合论文的异步 off-policy RL；要求所有 rollout 同步换版的训练框架，仍须上层广播确切版本（§4.4）。心跳失联时整个副本失效、在途读取改从另一源恢复；spot 副本不计入版本保留的可靠副本。引用服务器故障后切到空状态备服，客户端重新发布，模型并行组用屏障避免部分 shard 已切换、部分仍在旧服（§4.5）。这与 [[TrainMover-OSDI26]] 的整任务迁移不同，TensorHub 的对象是反复发布的权重版本。

## 设计取舍

- **省存储副本换取引用有效性管理**：若所有源同时淘汰旧版本，ROS 无法再提供旧权重。版本保留需要显式策略。
- **多源分发换取复杂一致性**：不同分片到达时间不同，不能因部分传输完成就开放新版本推理。
- **拓扑优化依赖网络信息**：跨地域策略与本地 RDMA 路径的成本模型不能混用。
- **异步副本间陈旧度换性能**：组内事务保证同版，组间可看到不同新旧版本；同步 RL 必须在上层补一次版本协调。
- **软状态备服换短暂不可读**：引用服务器失效后新服不回放旧状态，而等 worker 再发布；已有权重可继续推理，新的复制请求可能暂时失败。

## 实验与结果

- 微基准每 shard 传 50 GB 时，TensorHub 用 2.2 秒、22 GB/s，约为 25 GB/s RDMA 理想值的 88%；NCCL、UCX 为 18.8、18.1 GB/s。1–8 组 rollout 同时拉取时，流水复制使总 GPU 停顿近似随组数线性增长，关闭流水则因源端带宽竞争接近平方增长（§5.1、图 7）。
- 独立 rollout 评测包括 9B、36B、260B，以及复制 260B 层权重构造的 **mocked 1T** 压力配置；后者动用 768 个训练 GPU、256 个 rollout GPU，不能当作真正 1T 模型训练性能。TensorHub 相对 NCCL/UCX 总 GPU 停顿最高减少 6.7/5.2 倍；集成改动约 40 行，对照 NCCL 约 450 行、UCX 约 1200 行（§5.2、图 8–9、表 3）。
- 260B 模型的 spot 弹性实验在一个稳定机器和最多三个弹性机器上运行。UCX 的末批弹性 GPU 最多等 7.2 秒，TensorHub 约 1.5 秒，最高 4.8 倍改进；论文明确指出图 11 的 UCX 停顿只算 rollout，额外训练器停顿没有计入，故比较对 UCX 还偏宽松（§5.3、图 11）。
- 跨数据中心 9B 模型实验使用 200 Gbps VPC TCP：UCX 每 GPU 等 7.8 秒，TensorHub 只让首个副本跨域拉取 2.5 秒，其他副本本地 RDMA 约 0.45 秒；加 CPU offload 种子后首副本只等 0.21 秒。总 rollout GPU 停顿最高少 19 倍，训练步从 68 降到 60 秒，改善 13%。这说明“19 倍停顿”不等于“19 倍训练加速”（§5.4、图 12）。

## 批判性分析

### 论证链条

“现有副本已存在”支撑 ROS 的核心抽象；不变性契约、保留协议、组级事务与失败恢复分别补齐完整性、可用性、并行正确性和弹性。图 7 的直接带宽微基准与图 9、11、12 的三种系统场景能区分“传得快”和“少停 GPU”。跨域 19 倍 GPU 停顿减少只对应 13% 训练步收益，更清楚地显示端到端闭环由计算和其他阶段共同决定。

### 假设压力测试

如果 rollout worker 很少、频繁全部回收，或版本保留窗口短，引用源可能不足；保留协议会回退到 CPU offload。若训练迭代频率快于一次跨域传输完成时间，旧版与新版堆积会增加显存占用。若算法要求所有 rollout 同步看到完全相同的版本，论文只提供组内一致性，额外跨副本屏障可能吃掉异步收益。这些情况需要单独测量版本积压与失效比例。

### 实验可信度

三类 rollout 和生产部署使问题具有实际代表性；峰值加速分别来自不同配置。微基准使用 50 GB/shard，跨域用 9B，弹性用 260B；1T 是模拟权重数据。NCCL/UCX 基线实现需要 Ray driver 协调，其停顿中有框架工程成本；论文的 40/450/1200 行集成差异说明易用性优势，但也使对照不完全隔离纯传输算法。读者应回到 §5 的具体拓扑与版本大小。

### 系统性缺陷

ROS 元数据与 worker 生命周期耦合，源失效、网络分区和训练器回滚时需保持版本可见性的清晰语义。备服空状态重建虽简单，但在重发完成前无法提供可读引用；最后一个非 spot 源失效时，论文允许返回“版本不可用”并等下一训练版本。长期存储或审计需求仍需传统 checkpoint，引用式存储不能替代持久备份。

## 局限与后续工作

- 在故障注入下测量所有源同时失效的概率、恢复时间与训练步重做量。
- 报告版本保留窗口、权重副本显存占用和跨数据中心出口流量的成本曲线。
- 在同步 RL 或严格版本一致性的训练中加入跨副本屏障，再比较 TensorHub 与 NCCL/UCX 的训练步吞吐。
