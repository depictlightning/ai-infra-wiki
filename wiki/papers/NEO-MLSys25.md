# NEO：将解码注意力和 KV 交给 CPU 的在线推理（MLSys 2025）

> **原题**：NEO: Saving GPU Memory Crisis with CPU Offloading for Online LLM Inference

> **一句话总结**：NEO 按请求将部分完整 KV 和解码注意力放到本机 CPU，以非对称子批次重叠 GPU 线性层与 CPU 注意力，并用逐轮调度决定是否卸载；在 A10G、Llama-3.1-8B 和 Azure 代码请求分布下，图 6 报告相同平均每输出 token 延迟为 2 秒时，请求吞吐相对 vLLM 高 6.4%（§3、§5.2）。[^paper]

**阅读范围**：复用仓库已有 MLSys 2025 会议 PDF 与 MinerU 全文，核对架构、非对称流水线、在线结果、CPU 敏感性和附录调度伪代码，回看图 5、6 和 10。未运行代码；原文报告的延迟口径见下文。[^paper]

## 问题与动机

在线服务希望批量处理请求，又需要控制用户等待。显存保存权重及每个请求不断增长的 KV，容量不足会限制批次。把 KV 放到 CPU 后，如果每一层、每一步都搬回整段历史，PCIe 很容易成为瓶颈；全部请求的解码注意力都放在 CPU，又可能让 CPU 内存带宽成为新瓶颈（§1–2）。[^paper]

NEO 的问题是：**哪些请求的 KV 和解码注意力适合留在主机，怎样让 CPU 的计算与 GPU 的其他工作重叠？**它关注带动态请求长度的在线服务，区别于以固定大批次摊薄 I/O 的 [[FlexGen-ICML23]]。[^paper]

## 关键观察 / 隐含假设

- **观察 1：解码注意力对内存带宽敏感。** 作者举例比较 A10G 的 600 GB/s 与一类 x86 服务器约 200 GB/s 内存带宽，二者带宽差距小于算力差距；其 CPU 内核也围绕连续访问和并行读取设计（§2.2、§4）。[^paper]
  - **依赖假设**：CPU 有可用内存带宽，且注意力计算及 Q/K/V 通信能与 GPU 的其他工作重叠。上述规格对比不证明任意 CPU 都能跟上 GPU。
- **观察 2：全部卸载可能让 CPU 成为瓶颈。** 图 8 的作者实现 FastDecode+ 在输出变长时吞吐降至 GPU-only 基线的 60% 以下；NEO 同时保留 GPU 驻留请求，并能选择 GPU-only 轮次（§3.1、§5.3）。[^paper]
  - **依赖假设**：有足够的请求和显存可在两侧分配，并能形成重叠流水线；负载太轻或迁移太频繁时，额外队列和通信可能带来负收益。
- **观察 3：画像可以估算每轮不同算子的耗时。** 调度器对典型形状离线测量并插值；图 9 中很长输出时收益回落，作者指出不准确的预测可能造成次优选择（§3.2、§5.4）。[^paper]
  - **依赖假设**：运行时形状、设备负载和带宽与画像相近。CPU 被其他任务占用、NUMA 访问变化或请求形状超出画像范围时，重叠条件可能不再成立。
- **观察 4：同一 GPU 搭配不同主机资源时收益不同。** 四种 A10G g5 实例的峰值收益分别为 12.2%、13.3%、29.7%、79.3%，但 CPU 核数、内存和带宽同时变化（§5.5、图 10）。[^paper]
  - **代价假设**：主机内存、CPU 核与带宽可供推理使用，且其机会成本可接受；共享主机或自建集群不能只按“GPU 实例自带 CPU”计算成本。

## 核心方法

### 一条请求的 KV 和注意力在哪里

每个已完成预填充的请求被视为 GPU 请求或 CPU 请求：前者的 KV 在 GPU cache，解码注意力在 GPU；后者的 KV 在 CPU cache，解码注意力在 CPU。GPU 仍执行线性层、前后投影和预填充，CPU 请求需要传递当前层的 Q/K/V 和注意力输出。调度器可迁移请求的 KV；“卸载到 CPU”不等于整个模型或预填充都在 CPU 运行（§3.1、图 3–5）。[^paper]

预填充由 GPU 逐层产生 KV，系统可在后续层计算时把已产生的层缓存发往 CPU。生成时 CPU 侧读取本机 KV 计算注意力，不必为每层每步把整段历史搬回 GPU；它仍需跨设备同步数据和依赖。[^paper]

### 非对称流水线

单纯把所有注意力交给 CPU 会让 GPU 等待；均匀划分两个子批次也可能让较慢的 CPU 阶段阻塞。NEO 将预填充和 GPU 解码请求集中在主要使用 GPU 的子批次，另一个子批次主要包含 CPU 解码请求；少量 CPU 请求也可放入前者。这样 GPU 的线性层和预填充尽可能与另一批 CPU 注意力并行（§3.1、图 5）。[^paper]

非对称指两个子批次的工作组成不同，并不意味着 CPU 和 GPU 分别独立完成两个完整请求：CPU 请求的线性层仍在 GPU，层间存在投影、通信和注意力输出依赖。[^paper]

对比三种组织方式有助于理解这个选择：

| 方式 | 每轮如何安排 | 主要瓶颈 |
|---|---|---|
| 全部卸载的直接实现 | 所有请求的解码注意力在 CPU，其他算子在 GPU | 两侧交替等待，CPU 带宽也可能先饱和。 |
| 对称双批 | 两批规模和组成相近，一批线性层与另一批 CPU 注意力交错 | 两批若都偏重 CPU，流水线容易在同一阶段堵塞；GPU 注意力也需要多次启动。 |
| NEO 非对称双批 | batch-0 聚集 prefill、GPU 解码及少量 CPU 解码；batch-1 主要是 CPU 解码 | 利用 batch-0 较长的 GPU 工作掩盖 batch-1 的 CPU 注意力，但需要控制两批的规模和同步。 |

预填充同样并入 batch-0 的 GPU 工作，使另一批 CPU 注意力有更长的重叠窗口；新产生的各层 KV 可以逐层传回主机，不必等整个 prefill 结束才开始传输。这是论文的流水线设计，不表示所有通信都能被完全隐藏（§3.1、图 3–5）。[^paper]

### 按每轮状态选择卸载

调度器维护预填充等待队列、GPU 解码队列和 CPU 解码队列。每一轮先考虑 GPU 请求和显存可容纳的预填充，再加入 CPU 解码请求，约束估计 CPU 注意力时间不超过可重叠的 GPU 工作；随后构造 GPU-only 和双子批次两个候选，选择估计单请求平均迭代代价较小者（§3.2、附录 A）。[^paper]

估计量使用离线画像和插值，目标是平衡流水线、减少 GPU 等待，同时利用可用显存。论文报告调度每轮少于 3 ms，所测迭代则为数百毫秒；这个开销比例不能假定适用于更短迭代或新硬件。[^paper]

更具体地，令 $T_{l0},T_{l1}$ 为两批一层的线性算子时间，$T_{ga0}$ 为 batch-0 的 GPU 注意力时间，$T_{ca0},T_{ca1}$ 为两批的 CPU 注意力时间。调度器按离线画像和插值估计这些值，尝试满足：

$$
T_{ca0}\le T_{l1}+T_{ga0},\qquad T_{ca1}\le T_{l0}.
$$

前者要求 batch-0 的 CPU 注意力能够被另一段 GPU 工作掩盖，后者要求 batch-1 的 CPU 注意力能够被 batch-0 的线性阶段掩盖。条件是基于预估时长的调度目标，不是实际运行时永不产生流水线气泡的保证（§3.2）。[^paper]

每轮候选的构造顺序也有实际含义（附录 A）：[^paper]

1. 先将 GPU 解码队列放入 batch-0，显存不足则迁出部分 KV，有余量则尝试迁入。
2. 从 prefill 队列加入请求，直到 GPU 激活内存成为约束；新 KV 可按容量保留在 GPU 或发往 CPU。
3. 扫描 CPU 解码队列，把请求分配给符合上述重叠约束的子批次；暂时无法容纳的请求留待后续轮次。
4. 在仍满足约束时，移除部分需要写出 KV 的 prefill 请求，使两侧时间更平衡；再用相同状态构造 GPU-only 候选。
5. 分别估算单轮耗时 $T$ 与处理请求数 $x$，选择 $T/x$ 较小的方案。预测的吞吐更高不意味着该轮每个请求的等待时间都更短。

当流量不够、CPU 忙不过来或显存可容纳的子批过小时，GPU-only 可能更合适。这个回退机制是部分卸载方案的一部分；如果把所有能卸载的请求都放到 CPU，就失去了论文试图维持的平衡。[^paper]

### CPU 侧实现

作者基于 SwiftLLM 构建系统，编写支持分页 KV 的 CPU 注意力内核，用 ISPC 生成向量化代码，将请求按 KV 块分给多个 CPU 线程，再合并部分注意力结果。GPU 侧把部分 Triton 内核改为 CUDA C++，降低 Python 调用和启动成本；多 GPU 版本使用张量并行，每个分片管理对应的 CPU KV（§4）。[^paper]

PACPU 需要通过页表访问不连续的缓存块，因此不能直接假定普通 CPU 注意力库已经支持此布局。它在核内尽量连续读取并利用 SIMD，在核间划分块并归并局部结果；块大小、线程数和 NUMA 亲和性都会影响可用带宽。论文还报告 Llama-3-8B 每层 GPU 内核启动开销从 1.2 ms 降至 0.6 ms，说明流水线细化后，框架启动和控制开销本身也可能暴露在关键路径上（§4）。[^paper]

## 设计取舍

- **更大批次换主机资源**：GPU 显存压力下降，但每个 CPU 请求仍消耗 DRAM 容量、带宽、计算和跨设备通信。
- **只卸载部分请求换调度复杂度**：CPU 不容易因全部请求过载，但必须动态迁移 KV、维护多个队列并画像两侧时间。
- **保留完整注意力换精度稳定**：论文声称不引入稀疏近似；浮点实现与执行顺序变化是否逐位一致并未在本文单独证明。
- **在线选择换预测误差**：工作负载与设备行为偏离画像时，卸载及迁移本身可能带来负收益。

## 实验与结果

作者使用 AWS 的 T4、A10G 实例和本地 H100 服务器，测试 Llama-2-7B、Llama-3.1-8B/70B。Azure 代码轨迹与公开摘要数据提供请求长度；在线实验按泊松过程生成到达时间。图 6 的延迟是**每个请求完整延迟除以输出 token 数，再对请求取平均**，包含 prefill 和排队，不应等同于纯 decode 的 token 间隔（§5.1–5.2）。[^paper]

三组在线结果分别是 2×H100 / Llama-3.1-70B / Azure 代码，A10G / Llama-3.1-8B / Azure 代码，以及 T4 / Llama-2-7B / 摘要数据；前两者比较 2 秒的平均每输出 token 延迟，T4 比较 1 秒。合成负载则固定输入和输出长度的中心值，并在各自的 90%–110% 区间均匀采样。在线曲线的横轴是请求到达率，容量点随延迟门槛变化；不能用 563% 直接代表不同设备或任意 SLO 的收益（§5.1–5.2、图 6）。[^paper]

| 实验 | 对照与结果 |
|---|---|
| 在线负载 | 相对 vLLM，图 6 在指定延迟点报告 H100 高 14.3%、A10G 高 6.4%、T4 高 563% 的可承载请求吞吐；分别使用不同模型、数据和延迟点，不能横向归因于 GPU 型号（§5.2）。 |
| 中间负载 | 作者指出 NEO 某些中等请求率下延迟略高，原因包括额外调度／迁移及两套实现优化程度不同（图 6、§5.2）。 |
| 全部卸载对照 | FastDecode+ 是作者以 NEO 流水线和调度实现的全 CPU 注意力变体，不是原系统的直接部署；长输出下其吞吐可降至 GPU-only 基线的 60% 以下（图 8、§5.3）。 |
| CPU 资源 | 同为 A10G 的不同 g5 规格，峰值相对 GPU-only NEO 分别高 12.2%、13.3%、29.7%、79.3%；CPU 核数、内存容量和带宽同时变化，不能把差异全部归因于单一因素（图 10、§5.5）。 |
| 输出长度 | 合成负载中，收益先随输出长度增长而上升，再因 CPU 压力和退回 GPU-only 调度而下降；短输出或画像不准时可能略逊于基线（图 9、§5.4）。 |
| 基线实现差异 | Azure 代码轨迹一次性到达时，SwiftLLM 与 vLLM 在单张 A10G 的吞吐接近；作者的双 H100 SwiftLLM 实现低约 8.8%，说明多 GPU 在线结果还受到实现成熟度影响（图 10b、§5.5）。 |

全 CPU 注意力对照中的 FastDecode+ 与 NEO 共用作者的非对称流水线和调度基础，但要求把所有请求的解码注意力放在主机。图 8 固定 2000 输入 token、改变输出长度：输出变长后，CPU 工作越来越重，即使 GPU 仍有能力也不能像 NEO 一样改用 GPU-only 方案。这一消融支持“分配位置需要适应负载”，而不单独证明作者的调度预测已经最优。[^paper]

CPU 敏感性测试还应考虑资源定价：四种 g5 规格除了内存带宽，也同时改变 CPU 核数和可用内存，作者还按核数调整 CPU KV 容量。云实例自带 CPU 的账单不因使用这些核而改变，但自建集群、多模型共享主机和能耗的机会成本并未由此消失；论文没有给出完整的跨部署成本与能效对照（§5.5–6）。[^paper]

论文摘要列出 T4 的“7.5× higher throughput”，§5.4 则写 750% throughput gains；百分比增量与倍数表述存在歧义。这里保留可定位的在线结果和趋势，不把两种写法强行当成同一个倍数。[^paper]

## 批判性分析

### 论证链条

从 CPU 带宽与 GPU 容量的互补出发，论文分别引入部分卸载、子批次重叠和在线调度。图 8 的全卸载变体支持“不能盲目把所有注意力交给 CPU”；它与原始 FastDecode 的实现和硬件并不相同，结果应视作受控设计对照。[^paper]

### 假设压力测试

流量不足以填满 GPU、输出很短、CPU 需运行其他任务或 NUMA 访问不均匀时，搬运与调度成本可能超过额外并发收益。图 9 已显示短输出和长输出下收益下降。大模型的张量并行还要考虑 CPU 分片、同步和跨 GPU 通信，不能只按单 GPU 内存容量推断。[^paper]

### 实验可信度与系统性缺陷

与 vLLM 的比较包含两种实现的差异；作者还报告 SwiftLLM 在 2 GPU 设置下吞吐比 vLLM 低 8.8%。请求长度来自真实数据，但在线到达使用泊松过程。图 7 给出一个配置下的延迟分布，不能代表所有负载的 P99。CPU 在云实例中的资源成本、同机多租户争用、故障恢复和能耗没有系统量化（§5–6）。[^paper]

## 局限与后续工作

- 对照 [[DirectKV-OSDI26]] 时，固定 CPU 内存带宽、互连、模型和批次，分别统计 CPU 计算、GPU 直接读取与通信；两篇论文的数值不能直接排序。
- 在同一在线轨迹中加入突发到达、变长输出和其他 CPU 任务，记录 P95/P99、主机资源与调度误差。
- 使用相同精度和模型核对 CPU 注意力的数值误差；“无额外近似”不自动意味着所有实现逐位一致。
