# LAPS：按输入长度组织 LLM 预填充（MLSys 2026）

> **原题**：LAPS: A Length-Aware-Prefill LLM Serving System

> **一句话总结**：长短预填充混合时存在资源干扰和批次填充浪费，LAPS 分别组织长短请求，并为短请求复用 CUDA Graph；论文在所测负载中报告更低 TTFT 和违约率，但预填充与解码混合时收益受限（§3–4）。[^paper]

**版本与阅读状态**：已保存会议论文集提供的 PDF，并调用 MinerU 解析；图表和全文仍需核对。会议网页标题写作“PLA-Serve: A Prefill-Length-Aware LLM Serving System”，但链接到的 PDF 标题及正文使用 **LAPS**，这里保留 PDF 标题，并明确记录这一差异。[^paper]

## 问题与动机

多轮对话中的后续输入可能很短，却仍要读取已有 KV cache；长输入和短输入在计算、内存访问及批次组成上可能不同。论文研究在预填充阶段将两类工作分开，而不是只划分 prefill 与 decode（§1–2）。[^paper]

作者对 LMsys-Chat-1M 的统计显示首轮约 63% 的输入少于 256 token，后续轮次平均约 81% 少于 256 token；具体比例取决于负载，不能假定适用于所有服务（§2.1、图 2）。[^paper]

## 关键观察 / 隐含假设

- **长短混合可能产生填充与资源干扰**：论文构造 7 条 64 token 请求和 1 条 2048 token 请求，并将所有序列填充到 2048；该例的 GEMM 填充浪费为 84.8%。这是特定填充执行方式的微基准，不代表所有变长批处理引擎都会产生同等浪费（§2.2、表 2）。[^paper]
- **短请求的执行形状可聚合**：为常见形状捕获 CUDA Graph 可减少启动开销，但等待相近请求也会增加排队时间，收益依赖到达率与长度分布（§3.1、图 6）。[^paper]
- **分开预填充与解码有利于短请求批处理**：作者在混合 decode 的实验中观察到额外批间等待；不能将预填充分离模式的收益无条件推广到混合部署（§4.1、图 10）。[^paper]

## 核心方法

LAPS 按长度组织短和长预填充请求：单个预填充实例可分时处理，多实例可按空间分配。两类请求没有 prefill 与 decode 之间那样的前后依赖，但仍要在资源分配和请求队列之间权衡（§3.2）。[^paper]

针对短请求，系统按形状分桶并重用 CUDA Graph，通过等待窗口聚集批次；等待时间与更大批次降低的执行开销之间存在折中（§3.1、图 6）。对多轮会话，系统使用已有 KV 处理新增上下文，而不是把所有历史重新计算为一个全新提示（§1）。[^paper]

## 设计取舍

- 长短隔离减少混合干扰，但池的容量分配和短请求等待窗口都可能造成空闲或排队。
- CUDA Graph 减少部分执行开销，需要预先捕获形状，并可能为对齐分桶引入填充。
- P/D 分离便于专门处理预填充，但系统仍要考虑阶段间 KV 搬运及独立实例成本。

## 实验与结果

论文比较 SGLang 的 P/D 分离方案以及只启用部分机制的版本，评测 Qwen2.5-7B/14B/32B、单实例和多实例设置（§4.1）。图 7 的正文与图注对使用的对话数据集表述不一致，具体口径仍需回 PDF 和实验产物核验。[^paper]

| 测量 | 结果与边界 |
|---|---|
| 批次填充微基准 | 7 条 64 token 加 1 条 2048 token、填充到统一长度时，7B/32B 的延迟分别为 567.1/2289.3 ms；短请求单独批次为 19.4/73.7 ms（§2.2、表 2）。 |
| SLO 测试 | 图 9 使用 0.4 秒 TTFT SLO 和建模的到达过程；作者报告 8 实例设置下 LAPS 违约率为零，对照 SGLang router 为 4.7%，该结果受负载和阈值限制（§4.1）。 |
| 离线蒸馏 | 4 prefill + 4 decode 实例下，相对 SGLang 的端到端耗时在 LMSys/ShareGPT 数据上分别减少 7.3%/8.3%（§4.1、表 4）。 |
| 混合部署限制 | prefill 与 decode 混合时，预填充吞吐下降；作者指出批间额外延迟削弱了 CUDA Graph 的收益（§4.1、图 10）。 |

## 批判性分析

### 论证链条

论文从负载长度分布与微基准干扰推导长短分离，再用端到端和单机制对照评估。微基准中大量填充能解释该实验的浪费，但需要进一步确认对使用变长内核或不同批处理方式的服务是否同样成立。[^paper]

### 假设压力测试

短请求到达稀疏时，等待填批可能超过计算收益；长请求比例突然变化时，预分配实例也可能失衡。混合 decode 的负结果说明具体执行架构会改变结论。[^paper]

### 实验可信度

正文和图 7 图注的数据集描述不一致；会议网页和 PDF 标题也不一致。两处都应继续核对，不将它们自行解释成确定事实。[^paper]

### 系统性缺陷

图缓存、队列分离和多实例角色分配增加管理复杂度；请求公平性、动态负载下的资源浪费和阶段间带宽应与 TTFT 一起衡量。[^paper]

## 局限与后续工作

- 对照不同变长注意力与批处理实现重跑长短混合微基准，分离填充浪费与计算/带宽争用。
- 在不同短请求到达率下扫描等待窗口，记录 P95/P99 TTFT、GPU 利用率和各队列饥饿时间。
