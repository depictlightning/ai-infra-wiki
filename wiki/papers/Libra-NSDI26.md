# Libra：按请求切分与调度应对动态阶段负载（NSDI 2026）

> **原题**：Libra: Flexible Request Partitioning and Scheduling for Serving Unbalanced and Dynamic LLM Workloads

> **一句话总结**：固定 P/D 资源池可能因请求长度变化而失衡；Libra 在统一实例池内选择请求切分点，并结合局部批处理与分块 KV 传输，在所测负载和 token 延迟目标下提高有效输出吞吐。[^paper]

**版本与阅读状态**：依据 NSDI 2026 会议版 PDF 和 MinerU 全文，回看图 5、8–10 和表 3–8；其他图表与源码尚未逐项复核。此前以 DynaServe 为名的预印本与本论文作者和研究方向相同，机制与数字以这里核对的会议版为准。未复现实验。[^paper]

## 问题与动机

当负载在长输入短输出与短输入长输出之间切换时，固定 P/D 池的较慢阶段决定整体吞吐，另一侧可能有空闲。把所有请求都共置，又可能因长 prefill 拖慢正在生成的请求。仅在两种实例级配置之间切换，会受模型加载、阶段配比和切换时间限制（§2–3）。[^paper]

Libra 从请求级重新表达资源分配：一组统一实例都可以处理 prefill 和 decode；某个请求可以在 token 边界切成协作的片段，分配给不同实例执行。切分既可能发生在 prompt 内，也可能发生在 decode 内；如果片段落到不同实例，KV 仍需交接（§3）。[^paper]

## 关键观察 / 隐含假设

- **瓶颈随负载变动。** 两张 A100、Qwen2.5-14B 的受控实验显示，固定 1P1D 在不同输入输出长度下可能让不同 GPU 成为瓶颈；共置配置虽然可共享资源，也可能增加 token 间延迟（§2.3–2.4、表 1）。[^paper]
- **切分位置影响两侧工作量。** 两张 A100、Qwen2.5-32B、输入输出各 1024 token 的实验中，以 prompt 结束位置 1024 切分时总体约 1.7 请求/秒；在位置 1358 切分时两侧约各 2.5 请求/秒（§4.1、图 5）。这是特定受控配置，不是通用切分点。[^paper]
- **混合批次的干扰取决于上下文和批组成。** prefill token 数、decode 请求数与现有 KV 长度共同影响一次迭代延迟；仅用固定块大小不能覆盖所有组合（§4.2、图 6）。[^paper]

## 核心方法

### 从一个请求看资源分配

设一个请求输入 1024 token、预计输出 1024 token。传统阶段分离在位置 1024 切分：第一实例处理输入，第二实例处理后续生成。Libra 可以选择位置 1358：第一实例处理输入并继续生成一段输出，随后将状态交给第二实例完成剩余部分。这个例子对应图 5 的测量；输出长度和两侧速度改变后，最佳位置也会改变。[^paper]

切分不意味着两个片段可以无依赖地同时生成同一序列：后续片段需要接收前面产生的状态。系统依靠多个请求之间的并发保持实例忙碌。请求全部放到同一实例可退化为共置；恰在 prompt 结束处切分对应常见的 P/D 分离（§3.1–3.2）。[^paper]

### 全局调度：选切分点和实例

全局调度器收集各实例的负载、队列与性能信息，为新请求选择实例和切分位置。算法以 P/D 边界为起点，预测两个片段及现有工作的完成时间，再用有上限的二分搜索调整位置，使两侧预测执行时间接近；实验设置最多六次搜索。论文采用最轻负载路由，并在负载相同时轮转（§4.1、算法 1）。[^paper]

预测器结合离线画像、近期批次信息与运行状态估算未来执行。它是启发式近似：每个请求的局部均衡不能自动保证集群全局均衡，输出长度、排队和干扰的预测误差也会改变实际结果。论文对低估加入 20 token 安全余量；这仍不是所有长度分布下的硬实时证明（§4.1、§5）。[^paper]

### 局部调度：在一次迭代中控制干扰

每个实例的局部调度器先安排已运行的 decode，再结合此前测量、decode 数量及上下文长度查询画像表，决定本轮允许加入多少 prefill token。系统根据实际批次延迟持续更新画像，目标是在提高利用率的同时控制 P99 TBT（§4.2、算法 2）。[^paper]

这个策略要同时满足显存与延迟约束。允许的 prefill 预算随上下文和活跃 decode 批量变化；若新模型、注意力实现或硬件使画像失准，就可能出现预算过大或 GPU 空闲。需要分别评估预测误差和调度器对延迟的反馈速度。[^paper]

### 跨实例 KV 传输

若两个片段位于不同实例，执行后续片段前需要前面形成的 KV。论文将 KV 按块传输，与后续计算重叠以降低不能隐藏的等待。更细的切分也可能增加传输量；作者举例称某个推理任务中的切分可导致比普通阶段分离多三倍的 token cache 传输，收益依赖互连和能否重叠（§3.3、§4.3）。[^paper]

## 设计取舍

- **弹性与调度复杂度**：请求级切分比固定 P/D 角色更灵活，但增加预测、路由和状态交接决策。
- **较高利用率与延迟**：允许混合批次可使用空闲算力，但过多 prefill 会增加 decode 的 token 间隔。
- **负载均衡与传输**：把一部分工作移到较空闲实例可能缩短瓶颈，却会产生额外 KV 传输与网络竞争。

## 实验与结果

主实验使用 Qwen2.5-14B/32B/72B，两台各四张 A100 80 GB 的服务器，另有 H100 实验。BurstGPT、Azure Code、arXiv 摘要和 Mini Reasoning 提供长度分布，请求到达由泊松过程生成。对照采用 vLLM 0.7.2 的共置及作者扩展的分离配置，主实验 GPU 数按模型为 2、4、8（§6.1）。[^paper]

论文将 goodput 定义为满足延迟目标的输出 token 速率，并另外报告满足 P99 TBT 约束的最大请求速率。主实验采用 100 ms TBT 目标；这与其他论文使用的“同时满足 TTFT 和 TPOT 的请求比例”口径不同，不能直接比较倍数（§4、§6.1）。[^paper]

- 图 8 的多个模型和负载下，作者报告相对共置配置最高增加 91% goodput，相对分离配置最高增加 61%。这些最高值来自不同实验点，不能视为所有负载的固定增益（§6.2）。[^paper]
- 表 3 的 Qwen2.5-14B 混合负载中，共置、分离和 Libra 的服务容量分别为 4.6、5.9、7.4 请求/秒；goodput 分别为 316.32、399.31、473.84 输出 token/秒。混合负载由 BurstGPT 和 Azure Code 各占一半构成（§6.4）。[^paper]
- 图 10 的消融在指定 Azure Code 负载下，关闭与启用 SLO 感知组批时，100 ms 内生成的 token 比例约为 52% 与 99%；这是 token 间隔分布，不能直接说成 99% 请求同时满足 TTFT 与 TPOT（§6.5）。[^paper]
- H100、50 ms TBT 目标下，表 8 的 Azure 负载中分离基线与 Libra 分别为 397.2 和 608.0 token/秒；Mini Reasoning 分别为 3816.8 和 5930.5 token/秒（§6.8）。结果取决于这些负载与实现配置。[^paper]

### 消融和预测误差

作者以固定预计输出 1467 token、实际输出服从不同方差的正态分布进行敏感性实验。标准差从 0 增至 100 时，goodput 从 3606.93 降至 3501.85 token/秒，约下降 2.9%（表 5）。这一结果只覆盖指定均值和方差，并不能证明对重尾或系统性预测偏差同样稳健。[^paper]

表 6 在另一组混合负载下比较不同非对称 TP 配置，Libra 的单位 GPU goodput 为 86.8，所列分离配置为 33.1–73.2。不同基线使用的 P/D GPU 数和并行度不同，应使用表中的单位 GPU 口径，不把它们误写成同一固定卡数的总吞吐（§6.6）。[^paper]

表 7 的推理任务中，分离、Libra 两段和三段切分分别为 260.01、336.16、366.43 token/秒。三段方案利用可区分的中间思考与可见输出的不同延迟要求；论文说明执行时使用精确 token 标签，这一条件需要在实际应用中得到支持（§6.7）。[^paper]

## 批判性分析

### 论证链条

论文以固定配比失衡和混合批次干扰为动机，分别引入全局切分和局部预算，再以端到端、非对称配置及局部组批消融支撑。整体收益包含多个组件，不能只归因于切分点搜索。图 5 展示两卡均衡的直观例子，不足以证明多请求、多节点全局最优。

### 假设压力测试

更长上下文、输出长度重尾、错误的负载信息或跨节点拥塞，会改变切分点预测及 KV 交接代价。若实例都接近满载，迁移工作不一定能创造额外容量；这一判断需要在不同网络和流量下测量。

### 实验可信度

主对照是 vLLM 共置和作者扩展的 vLLM 分离模式，未独立运行 DistServe 或 Sarathi-Serve。数据集提供长度分布，但请求到达多为合成；真实部署版本、强前缀缓存及大规模多租户结果不能由这些实验直接推出。

### 系统性缺陷

请求片段和 KV 状态跨实例移动增加生命周期管理与失败处理要求；论文对控制面故障、迁移中途失败、取消和多租户隔离的系统验证有限。TTFT 结果应单独检查：表 2 中 Mini Reasoning 标注的绝对值非常小，且正文把 TTFT 与 100 ms decode 目标并列讨论，不能将其作为完整双指标 SLO 保障。[^paper]

## 局限与后续工作

- 固定模型、GPU 总数和互连，比较固定 P/D、可切换实例角色及 Libra 请求切分；分别报告 TTFT、P99 TBT、达标请求数与输出 token 速率。
- 扫描输出长度预测偏差、长上下文、重尾分布和网络拥塞，记录额外 KV 字节与不可重叠等待。
- 注入跨实例传输失败、请求取消和调度器故障，检查状态所有权、重试和最终输出正确性。
