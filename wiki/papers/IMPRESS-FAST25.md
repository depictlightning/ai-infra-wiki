# IMPRESS：以重要性组织 SSD 上的前缀 KV（FAST 2025）

> **原题**：IMPRESS: An Importance-Informed Multi-Tier Prefix KV Storage System for Large Language Model Inference

> **一句话总结**：IMPRESS 面向磁盘保存大量共享前缀的推理服务，用少数 attention head 估计重要 token、按重要性重排磁盘块，并将访问频率与块内重要 KV 比例一起用于缓存管理；作者在指定实验下报告 TTFT 相比最优对照降低最多 2.8 倍，代价是前缀的部分 KV 不参与后续计算，因此不保持原始完整注意力。[^paper]

**阅读状态**：已归档 FAST 会议 PDF，以 MinerU 解析全文并核对系统图、主要结果和消融图；以下数字均为论文实验，未独立复现。[^paper]

## 问题与动机

多条请求可能带有相同的文档、系统提示或示例。把前缀算过的 KV 留下来，可以避免每次重新 prefill；但当前缀集合大于 GPU 和 CPU 内存时，完整副本需要放在 SSD。此时缓存命中只说明系统找到了 KV，不说明读取一定比重算快。作者在 OPT 测试中观察到，SSD 到 GPU 无法被计算隐藏的加载时间占 TTFT 的 51%–98%；他们测试的前缀长度是 128–8K token，不能将这一比例外推到所有硬件和服务（§2.2、图 3）。[^paper]

只读取重要 token 看起来能减少 I/O，但要知道哪些 token 重要，常见选择方法本身需要先读取大量 Key。另一个矛盾来自磁盘块：即使只需要一个 token，也可能把与它同块的不重要 KV 一起读入。IMPRESS 同时处理选择成本、块布局与 GPU/CPU 缓存分配，而不是只引入一层 SSD 缓存。[^paper]

## 关键观察 / 隐含假设

- **观察 1：SSD 命中不必然比重算快。** 图 3 中，所测前缀从 GPU 或 CPU 读取可缩短 TTFT，从 SSD 读取却可能慢于重算；I/O 占 TTFT 的比例随前缀长度上升（§2.2）。[^paper]
  - **依赖假设**：服务存在足够多重复前缀，且容量压力使相当一部分命中落在 SSD。若前缀短、GPU prefill 更快或 SSD 命中率低，多级缓存的查找和加载未必值得。
- **观察 2：静态记录重要 token 会漏掉后来查询需要的内容。** 在 OPT-6.7B/RTE 和 OPT-30B/SQuAD 的测试中，即使静态方案重要 token 召回率超过 80%，任务准确率或 F1 仍可分别下降最多约 5% 和 3.3%（§3.2、图 4）。[^paper]
  - **依赖假设**：新查询可以在有限 I/O 下提供足够信号来重新判断重要性。不同查询关注文档不同位置时，不能保证以前的热度或三头投票覆盖所有必要信息。
- **观察 3：同一层不同 head 的重要 token 集合有可利用的相似性，但并非始终相同。** OPT-6.7B 中间层的一个例子平均 Jaccard 相似度超过 0.95；OPT-30B 全层平均在选择 40% 和 10% token 时分别为 0.68 和 0.48（§4.2、图 7–8）。[^paper]
  - **依赖假设**：三个 probe head 的相互相似性足以代表其余 head，而且所用模型和任务保留类似关系。probe 之间相似并不证明未观察到的 head 也相似；特别是 GQA、不同模型或少数关键 head 需要单独验证。
- **观察 4：按原顺序成块会把重要和不重要 KV 混在一起。** OPT-6.7B/RTE 的例子中，读取块内平均仅 46% KV 重要，约产生 2.2 倍读放大；块访问频率与重要 KV 占比也并不等价（§3.2、图 5）。[^paper]
  - **依赖假设**：重要性在相邻一段时间内足够稳定，重排和额外写入的成本小于后续节省的读流量。重要性随查询剧烈改变或复用次数较少时，重排可能增加写放大而难以摊销。
- **观察 5：只按访问频率放置缓存可能浪费 GPU 空间。** 论文构造的两个块分别以 1.5:1 的频率访问，但重要数据比例为 50% 和 100%；将后者留在 GPU，可使示例中的 CPU→GPU 传输从 20 个重要 Key 降到 15 个（§4.4、图 14）。[^paper]
  - **代价假设**：过去访问频率及移动平均重要度能够预测将来的访问，而且块大小和层间搬运成本足以用该分数近似。多租户变化、不同介质速度与排队时间不在这个简化示例中。

## 核心方法

### 1. 三层存储和一次请求的数据路径

所有前缀 KV 在磁盘保存副本；GPU 与 CPU 缓存尽量互斥，减少重复占用。CPU 维护 radix tree 定位最长共享前缀，运行区还必须容纳模型权重和推理中间数据。控制面由重要 token 识别和前缀 KV 管理组成（§4.1、图 6）。[^paper]

一次请求先查找已有的最长前缀。对可复用部分，系统判断哪些 token 重要，并从当前驻留层加载所需 KV；没有命中、尚未生成的前缀部分和当前查询继续由模型计算，新增前缀 KV 写入磁盘以供后续请求复用。**已有前缀中被判为不重要的 KV 不进入后续计算**，不是加载失败后无损补回；论文所称较高准确率是实验结果，不是与原模型逐位等价的保证。[^paper]

### 2. 用三个 probe head 降低选择本身的读取量

基础办法要为各 head 加载前缀 Key，计算注意力分数，再选重要位置。IMPRESS 在每层先读前三个 probe head 的 Key，计算它们各自的重要 token 集合和两两 Jaccard 相似度。如果平均相似度超过阈值，用 probe 的投票结果近似其他 head 的选择；否则该层回退到常规选择。三个 probe 的依据是一个 head 易偏、两个 head 遇到分歧难以投票，而更多 head 会增加读取成本（§4.3、图 9–11）。[^paper]

对选择率 `p=k/n`，论文先以随机选集的交并集期望之比 `j=p/(2-p)` 作为参考，再取阈值 `t=j^α`，实验中 `α=0.6`。这里 `E(|A∩B|)/E(|A∪B|)` 严格说是两个期望的比，不能不加说明地等同于 `E[J(A,B)]`。阈值下降会使更多层采用近似，减少 Key 加载，但可能漏掉关键位置。PIQA 的图 11 中阈值从 1 降到 0，加载量约减少 4 倍，准确率从 79.1% 降到 77.5%。[^paper]

论文示例使用 32 个 head、4 个前缀 token 和 3 个 probe：先读 12 个 probe Key 向量，再为统一选择的位置加载各 head 的 K/V，共报告 76 个向量；常规方案报告 160 个。这里是示意性计数，原图对常规方案的 Key/Value 计数表述需要结合实现核实，不能据此断言所有模型都恰好减少相同比例。[^paper]

### 3. 节点内重排和元数据映射

系统定期根据平均重要性重排 token，把重要 KV 尽量装进相同 chunk。比如一个 chunk 中原本只有 `t0` 重要、另一个中只有 `t3` 重要，两个 chunk 都需要读；重排为 `[t0,t3]` 后，读一个块即可。论文描述重排可异步进行，例如每 10 分钟一次（§4.4.1、图 12）。[^paper]

物理重排不能破坏逻辑前缀匹配。IMPRESS 只在 radix tree 的同一节点内部重排，并附加位置映射，查找时恢复原始 token 顺序；不跨共享前缀节点混放不同分支。论文在实验中报告映射查询占 TTFT 不到 2%，但后台重排仍会读写磁盘，异步不等于没有设备争用。[^paper]

### 4. 重要性与访问频率联合决定驻留层

系统给块计算与访问频率和重要 KV 比例相关的分数，重要比例通过访问后的移动平均更新。GPU 与 CPU 各由一个最小堆维护低分候选；在 GPU 命中时直接使用，在 CPU 命中时比较是否提升至 GPU，在 SSD 命中时先加载并比较两层候选。磁盘保留全量副本，因此驱逐 CPU 块本身不需再同步写回（§4.4.2、图 14）。[^paper]

这一方法与只按前缀深度及复用信号管理替换的 [[Buoy-SIGMOD27]] 回答的问题不同：IMPRESS 把模型内部的重要 token 选择引入存储和准入，而它的当前计算是近似的；Buoy 的缓存缺失可以通过重算处理，不能将两者的精度语义等同。[^paper]

## 设计取舍

- **少读数据换计算语义变化**：probe 选择和丢弃不重要前缀 KV 都可能改变结果；回退只关闭当前层的跨 head 近似，并不自动变成完整前缀注意力。
- **读放大换写入和元数据**：重排提升重要 KV 密度，却需要后台排序、数据重写和逻辑位置映射；SSD 耐久度及前台 I/O 竞争应计入部署成本。
- **GPU 命中率换预测状态**：分数同时考虑频率和重要度，但必须维护统计与堆；预测偏差可能让冷块长期占据较快层。
- **存储空间换搬运时间**：磁盘保存完整副本、probe head Key 另存一份，缓存驱逐更简单；这些副本和写流量不能从容量成本中省略。

## 实验设置

作者在一台机器上使用 2×AMD EPYC 7763、128 GB 主存、一张 80 GB A100，以及读带宽约 5 GB/s 的 2 TB Intel SSD；CPU–GPU 是 PCIe 4.0 ×16。系统基于 FlexGen 修改，运行缓存限定为 10 GB GPU 和 32 GB CPU，块为 64 token，余下内存用于权重和推理（§5–6.1）。[^paper]

主要测试 OPT-6.7B、13B、30B，在 PIQA、RTE、COPA、OpenBookQA 上用 few-shot 示例构造共享前缀；平均前缀约 4.8K–5.7K token，复用频率按正态分布构造。作者另对 Llama2-7B/13B 测试 TTFT。对照包括完整重算、作者尽力复现并调整的 AttentionStore-like，以及在该基线上加入 H2O 和 LRU/LFU 的版本；AttentionStore 原实现未开源且其调度优化被关闭，因此不是原系统的原样比较。[^paper]

## 批判性分析

### 论证链条

IMPRESS 的核心链条是“SSD 读取比重算慢 → 只取部分前缀 → 选择本身仍要读 Key → 用跨 head 相似性减少这部分读 → 重排和缓存补足存储效率”。实验分别测试了各环节，但主结果来自三项合用；不能把 2.8 倍完全归因于 probe head 或重排。[^paper]

### 假设压力测试

对重要性预测尤其要分清两个错误：probe 对未读取 head 选错，导致本应使用的 KV 不参与计算；即便 probe 推断完全一致，系统依旧按保留比例裁掉其他 token。两者都可能影响输出，回退分支只能减少第一类风险。以平均准确率为唯一指标会掩盖少量长尾问题，例如某个查询依赖一个低频但决定答案的证据片段。

### 实验可信度

论文将重排放到后台、让磁盘保留完整副本，降低了请求关键路径上的处理量；但较慢 SSD、多模型共享盘、频繁写入和重排过程中的读写竞争会改变结论。可复现实验应同时记录 SSD 写入字节、块重写次数、混合负载下 P95/P99 TTFT，以及缓存从冷态预热的时间。

还值得比较“直接重算、完整加载、近似加载”三条路径随前缀长度、模型大小和 SSD 带宽的交叉点。相同 token 预算下，应逐项评估 needle 检索、跨文档推理和真实多轮会话，报告最差任务及每请求变化，而不只比较平均分。

## 局限与后续工作

- 能否对用户、任务或前缀设置质量预算，在近似回载与完整重算之间动态选择？
- GQA、原生稀疏模型及跨模态前缀的 head 相关性是否仍支持三个固定 probe？
- 能否用预测收益抵扣后台重排 I/O 和 SSD 写入成本，决定什么时候不重排？
- 当多个请求并发争抢相同 SSD、CPU 缓存和 PCIe 时，缓存替换、读取与调度是否需要共同优化？
