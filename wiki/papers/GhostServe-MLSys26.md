# GhostServe：用纠删码保护推理中的 KV cache（MLSys 2026）

> **原题**：GhostServe: A Lightweight Checkpointing System in the Shadow for Fault-Tolerant LLM Serving

> **一句话总结**：GhostServe 将多 GPU 上的 KV cache 按 token 块编码，只把校验分片保存到主机内存；设备内存状态丢失后，它结合存活分片、校验数据和部分重算恢复推理。[^paper]

**阅读状态**：已通读与会议正式 PDF 一致的 MinerU 全文，核对系统流程、故障模型和主要实验图。摘要与结论对两个加速倍数的指标归属相反，暂标待复核。[^paper]

## 问题与动机

长上下文推理持续积累 KV cache。设备状态丢失后，重新执行大量历史 token 会延长恢复；将完整 KV cache 复制到主机又会占用内存和 GPU–CPU 带宽（§1–3）。[^paper]

GhostServe 面向单节点内的多 GPU TP 服务：利用各 GPU 上仍然存活的 KV 分片，只额外保存纠删码校验分片，以减少检查点写入量。它解决的是 KV 数据保护，恢复 GPU 运行时、重建通信组等仍需要其他机制（§4、§8）。[^paper]

## 关键观察 / 隐含假设

- **存活数据是恢复条件**：校验分片并非完整 KV 副本；必须保留足够的 GPU 数据分片和可用校验分片，才能恢复丢失数据（§4.1）。[^paper]
- **故障域主要限于节点内设备状态**：校验保存在同一节点的主机内存；节点断电或主机内存丢失不在当前保护范围内（§4.2、§8）。[^paper]
- **并行度影响收益**：编码与汇集有固定开销。论文报告 TP=2 时，相对 CPU 完整复制的收益消失（§6.3）。[^paper]
- **检查点不是零等待**：GPU 在块完成后需要汇集和编码，再同步进入下一块；校验数据到主机的传输可异步执行（§4.2、图 3）。[^paper]

## 核心方法

### 分块编码与轮流执行

每次生成一个 KV 块后，系统将各 TP worker 对应的 KV 分片汇集到指定 GPU。该 GPU 计算校验分片并异步写入主机内存；下一个块由另一张 GPU 负责，轮流分配编码工作以减少固定热点。实现仍需临时汇集缓冲，不能理解成完全没有 GPU 内存开销（§4.2、算法 1）。[^paper]

在 8 个数据分片、2 个校验分片的设置下，校验数据约为原始分片总量的四分之一；论文因此报告相较完整复制节约 75% 主机检查点空间。这个比例不包含其他运行时元数据，也不意味着同节点主机内存失效后仍可恢复（§4.1、图 2）。[^paper]

### 位模式编码与恢复

纠删码按整数位模式操作。实现将 FP16 KV 的位模式可逆地解释为整数，使用融合 CUDA kernel 计算 XOR、RDP 或 Reed–Solomon 校验，而不是对浮点值做有损数值转换。理论上可容忍的同时分片丢失数取决于编码和校验分片配置（§4.1、§5）。[^paper]

故障后，系统估计应重算的前缀块数；较短序列可以全部重算，较长序列则在重算前段的同时搬运校验数据，再用存活数据和校验恢复剩余块。恢复完成后才能继续推理；论文假设故障 GPU 已可重新加入并恢复通信环境（§4.2、算法 2）。[^paper]

## 设计取舍

- **少存副本换汇集与编码**：节省主机检查点容量，但每块仍有 GPU 间同步、临时缓冲和校验计算。
- **更强容错换校验成本**：增加校验分片可覆盖更多数据分片丢失，也会增加编码与传输量。
- **异步写回换保护窗口**：校验尚未持久写入主机时发生故障，最新块是否受保护取决于写入完成和一致性管理；论文未给出完整崩溃一致性协议。
- **重算换恢复并行度**：部分重算可隐藏校验搬运，但最佳分界依赖上下文长度、互连和 GPU 负载。

## 实验与结果

原型基于 SGLang 0.5.1，使用 8 张 H200、NVLink 和 1 TB 主机内存，评测 LLaMA、GPT-OSS 与 DeepSeek 模型。在线实验使用合成请求到达和故障注入；故障通过清空指定 worker 内存并暂停其他 worker 模拟（§5–6.1）。[^paper]

| 结果 | 条件与边界 |
|---|---|
| 检查点空间 | LLaMA-3-70B、TP=8、8:2 编码时，相比完整 CPU 复制，校验分片占用减少 75%（§4.1、图 2）。 |
| 故障下请求延迟 | 合成在线负载、15% 故障率下，LLaMA-70B 相对重算基线的 P50 约加速 1.2×、P99 约 1.1×；无故障时编码本身仍有成本（§6.2、图 5）。 |
| 恢复与重算 | 论文报告部分重算与编码恢复组合最多降低恢复时间 42.9%；图 8 的恢复指标定义为恢复 50% KV，不能当成完整请求恢复时间（§6.3）。 |
| 百万 token | LLaMA-3-70B、batch 1、2K chunk、1M 输入的实验中，正文报告 GhostServe 的 prefill 额外开销约 9 秒，CPU 复制约 2.6 分钟（§6.3、图 9）。 |

摘要将 2.7× 和 2.1× 分别归给检查点和恢复，结论却将二者交换；正文又给出不同基线和阶段的指标。由于无法仅凭这两个概括数字确定统一口径，此处保留可定位的实验条件，不把它们写成通用加速比。[^paper]

## 批判性分析

### 论证链条

论文先比较完整复制的带宽和容量成本，再用按块编码、异步写回以及部分重算降低这些开销。不同校验比例、TP 度和重算比例的实验支持其取舍，但检查点和恢复的概括倍数在摘要与结论之间不一致。[^paper]

### 假设压力测试

若失败同时损坏主机内存、存活分片或通信环境，保存的校验可能不可用；若错误是静默数据损坏而非已知位置的擦除，还需要可靠的检测和定位，论文未证明编码机制本身可发现所有错误。持续 decode、P/D 分离和跨节点网络会改变块生成与恢复路径。[^paper]

### 实验可信度

作者比较重算、CPU 复制和 SSD 检查点，也展示无故障与注入故障的成本；故障是模拟的，设备重启、NCCL 重建与 CUDA Graph 重捕获未被该 KV 恢复机制自动解决。图 4 和图 8 的恢复时间只覆盖 50% 的 KV，应避免将其当成全栈恢复时间。[^paper]

## 局限与后续工作

- 在真实设备错误与节点故障下测量检测、运行时恢复、校验写入完成以及完整请求恢复时间。
- 对 decode 密集请求、跨节点及 P/D 分离环境测量校验放置、资源争用和尾延迟。
