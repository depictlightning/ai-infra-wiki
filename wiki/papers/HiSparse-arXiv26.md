# HiSparse：以分层 KV cache 扩展稀疏注意力解码（arXiv 2026）

> **原题**：HiSparse: Scaling Sparse-Attention Decoding with Hierarchical KV Cache Management

> **一句话总结**：稀疏注意力每步只读取少数历史位置，完整 KV 却仍占用 HBM；HiSparse 将完整历史保存在主机，以 GPU 热缓存、融合召回内核及可选的共享索引预取控制解码驻留，在 Qwen3+Quest、GH200、200K 输入的峰值吞吐测试中从 111 提高到 520 token/s（约 4.7 倍），收益主要来自可容纳更大批次（§4.2、图 5）。[^paper]

**版本与阅读范围**：依据 2026-08-07 发布的 [arXiv:2608.07009v1](https://arxiv.org/abs/2608.07009v1)，已用 MinerU 解析 20 页全文，回看图 2–8，并核对附录 A 的 SGLang 集成说明。HiSparse 是运行时 KV 放置系统；已有的 [[HySparse-arXiv26]]、[[HySparse2-arXiv26]] 则改变模型注意力与跨层 KV 构造。本文与 [[vLLM-Hybrid-HiSparse]] 资料页讨论的是相邻的系统路线，实验实现需要分别看待。[^paper]

## 问题与动机

DSA、NSA 与 Quest 等稀疏选择器先给出本层会访问的历史位置，再让注意力读取对应 KV。被跳过的位置以后仍可能重新入选，因此减少一次注意力读取，并不意味着可以永久删除这些 KV。完整历史若继续驻留 HBM，容量仍受“上下文长度 × 并发请求数”限制（§2.1–2.2）。[^paper]

论文的 GLM-5.1 部署在 8×H200 上运行。32K 输入、8K 输出时，完整 KV 基线约在 60 个并发请求附近饱和，约占用 240 GB 的 KV 空间；模型权重、激活和 CUDA Graph 状态已占用其余空间。128K 历史的单请求 BF16 KV 约 13.09 GB，容量先于稀疏注意力计算成为瓶颈（§1–2.2）。这些是特定模型与部署的预算，不能据此估算任意模型。[^paper]

HiSparse 保留历史的可访问性，把大部分记录移到主机。GPU 只需在注意力真正读取前备齐所选 KV。系统要同时解决热数据保留、未命中传输与缓存管理开销，否则省出的显存会被较高 TPOT 抵消（§2.3）。[^paper]

## 关键观察 / 隐含假设

- **观察 1：所测选择结果存在时间局部性。** GLM-5.1 的一条 100,384-token LongBenchV2 请求中，图 6 统计前 1,000 生成步：2,048 槽平均未命中率约 30%；4,096 槽的 LRU 为 13.4%，同容量 FIFO 与随机分别为 17.2% 和 16.1%（§4.3）。容量和策略同时变化，不能把全部差距算成 LRU 收益。[^paper]
  - **依赖假设**：其他请求、模型和层也有足够重用，缓存能够在下次访问前保留热记录。局部性弱或 GPU 预算过小时，召回量会增大；单条轨迹不能保证普遍成立。
- **观察 2：部分模型的后续层复用精确索引结果。** GLM-5.2 的 78 层中，21 个锚点层运行索引器，其余 57 层沿用前一锚点的选择；没有共享索引时，相邻层猜测预取没有可测端到端收益（§3.5、§4.6）。[^paper]
  - **依赖假设**：模型结构已经给出后续层的准确选择，预取窗口能够覆盖一部分传输。仅有跨层相似性不能保证精确选择；各层仍须搬运自己的 KV。
- **观察 3：实验用大量主机内存换取更大的历史容量。** H200 节点有 2 TB DRAM，最大测试点的 pinned KV pool 约占 1 TB（§4.1、§5）。[^paper]
  - **依赖假设**：主机提供足够容量及可用 PCIe／NUMA 带宽，且活跃请求足够多以利用额外并发。多模型争用或主机内存不足时，收益和成本会改变。
- **观察 4：有界缓存只覆盖被分层管理的注意力 KV。** 索引器状态、页表和 LRU 元数据仍在 GPU；NSA 的其他注意力分支也保留自己的状态（§3.1–3.2、§4.1）。[^paper]
  - **代价假设**：这些未被同样限制的状态不会先耗尽显存。论文容量公式不能解释为整个请求的 GPU 内存严格与上下文长度无关。

## 核心方法

### 主机完整历史与逐请求、逐层热缓存

pinned DRAM 保存活动请求的完整 KV，作为可召回的后备副本。GPU 为每个请求、每层保留 `B` 个记录槽，要求 `B` 不小于该层选中的记录数 `k`。当前选择必须全部装入；余下槽位保留过去访问过的记录。页表把逻辑位置映射到设备槽，或标为仅在主机；GPU 上的 LRU 元数据决定下次未命中时替换谁（§3.1–3.2、图 2）。[^paper]

若有 `N` 个解码请求、`L` 个分层管理的注意力层，每条 KV 记录占 `w` 字节，**这部分**设备预算约为 `N × L × B × w`，完整历史的主机预算仍随上下文长度增长。GLM-5.1 在 `B=4096` 时报告约 0.4 GB 单请求注意力 KV 驻留，相比 128K 历史的 13.09 GB 缩小约 30 倍；索引器、元数据、权重和其他工作区需要另外计入（§3.3）。[^paper]

### 生命周期与替换次序

预填充逐层产生 KV 并写入主机池；调度器收到传输完成确认，且设备缓存与元数据已分配后，才允许请求进入解码。新生成 token 的 KV 先写入保留的 GPU 槽，再由备份流写穿到主机。CUDA event 保证后续从主机召回前，该副本已经完成（§3.3、附录 A）。[^paper]

替换采用带细化次序的 LRU：本轮已经命中的记录排在新取回记录之前，使反复命中的记录优先保留；新取回但只用一次的记录更容易被逐出。GPU 淘汰无需再把旧记录写回，因为主机已经保存完整历史。`B` 在论文实验中是部署时固定的参数，按请求动态调整仍属后续工作（§3.2、§4.5）。[^paper]

### 一次内核完成命中、替换与召回

RESOLVE 每个稀疏层启动一次，以一个 CUDA block 处理一个请求，依次完成五步（§3.4、图 3）：[^paper]

1. 把当前所选逻辑位置建成共享内存哈希表。
2. 并行检查 `B` 个已驻留槽，标记命中和可替换记录。
3. 扫描标记，为未命中记录选槽，并更新替换顺序。
4. GPU 线程从 pinned DRAM 直接读取对应 KV，填入槽位。
5. 发布页表和按选择顺序排列的物理槽向量，供注意力内核读取。

召回沿用 [[Strata-OSDI26]] 的 GPU 辅助 I/O 思路，以 `ld.global.nc.v2.b64` 等向量化读取处理离散的主机地址，减少大量小 DMA 提交。哈希、槽位扫描、I/O 与结果发布融合后可以进入解码 CUDA Graph，避免每层重新依靠 CPU 决策（§3.4）。元数据扫描量随 `B` 增长，因此扩大缓存也会增加管理成本。[^paper]

### 共享索引时的精确跨层预取

锚点层确定选择并完成槽位规划后，记录“从哪些主机位置搬到哪些槽位”的计划。侧流把这个计划用于同组后续层，提前搬入**各层自己的 KV 记录**，并让它们保持与锚点一致的槽位布局。共享层等待预取 event 后直接沿用槽位表，省去本层重复解析（§3.5）。[^paper]

这里共享的是选择与槽位计划，各层 KV 的值仍然不同；它不等同于 [[HySparse-arXiv26]] 中的跨层 KV 共享。预取只是提前发生传输，没有消除流量；锚点层自己的选择事先未知，仍需同步处理未命中。附录 A 还说明，在 PP 或推测解码等组合下实现会退回同步召回，不能把共享索引实验的收益视为所有功能组合均可获得。[^paper]

## 设计取舍

- **小缓存换并发，大缓存换命中率**：扩大 `B` 会减少召回，却占用更多 HBM、增加槽位扫描，并挤掉可运行的请求。论文在所测模型与平台上认为约 `2k–4k` 实用，更快的主机互连使较小缓存更有吸引力（§4.4–4.5）。[^paper]
- **完整主机副本换容量和传输成本**：GPU 中的冷记录可随时丢弃，但大规模 pinned DRAM、预填充写出和生成写穿仍消耗系统资源。实验没有把这些资源折算成云成本（§3.3、§4.1）。[^paper]
- **融合和 GPU 管理换移植工作**：接口只要求逻辑选择位置，但不同 KV 布局、后端、数据类型与图捕获需要相应适配；“不依赖索引器算法”不等于接入新模型完全无需工程修改（附录 A）。[^paper]
- **精确召回保持原有稀疏计算语义**：不会为了省显存永久丢弃可能再次被选择的位置；这里的精确性相对于既定稀疏选择器。Quest 本身的近似选择，以及动态批处理是否逐位确定，是另外的问题（§2.1、§3.1；可对照 [[LLM-42-SOSP26]]）。[^paper]

## 实验与结果

**配置与口径**：基线是未修改的 SGLang v0.5.11，保持相同模型、并行方式、精度与调度设置，完整 KV 驻留 HBM。所有模型的 KV 都为 **BF16**；模型名中的 FP8 指权重。DSA、Quest 每次选 2,048 个 token；DeepSeek-V4-Flash 按 4-token 压缩记录选 512 条，覆盖 2,048 个 token，记录粒度不能混用。并发扫描使用闭环请求，32K 输入、8K 输出；长度扫描报告峰值生成吞吐（§4.1）。[^paper]

| 测量 | 配置与基线 | 结果和解释 |
|---|---|---|
| 端到端吞吐与延迟 | DeepSeek-V4-Flash，2×B200，32K/8K，64 并发 | 生成吞吐 600→1,257 token/s，约 2.1 倍；平均 TTFT 829→171 s。在 16 并发的重叠区间，TPOT 为约 16.0/15.9 ms；不能据此说更大并发也维持相同 TPOT（图 4） |
| 长上下文峰值 | Qwen3-30B-A3B+Quest，GH200 | 32K 输入 511→1,824 token/s；200K 输入 111→520 token/s，约 4.7 倍。它是容量受限时的峰值吞吐比（图 5） |
| 其他模型与短上下文 | GLM-5.1-FP8，8×H200 | 160K 输入 232→680 token/s，约 2.9 倍；4K 时 2,288→2,280，基本无收益（图 5） |
| 主机互连敏感性 | GLM-5.1，`B=2k`，微基准 batch 16 | H200 PCIe 到 GH200 NVLink-C2C 的平台比较中，每次召回内核的 I/O 部分从 112 降至 29 μs；这是平台相关的微基准，不能视为完整系统加速（图 7） |
| 精确预取消融 | GLM-5.2-FP8，8×H200，32K/8K，`k=2048`、`B=4096` | 峰值为完整 KV 基线 618、无预取 1,515、有预取 1,727 token/s；有预取相对基线约 2.8 倍，相同并发下比无预取降低平均 TPOT 13%–15%（图 8） |

图 4 的解码阶段单独统计为 1,511→4,308 token/s，图 8 的类似曲线也排除了预填充。作者没有运行物理 P/D 分离集群，而是把这些曲线作为解码池性能的代理；不能将其标为分离部署的端到端实测（§4.2）。[^paper]

**无 I/O 上界不能作为可用系统**。图 8 的对照跳过实际主机召回，在未命中时读到旧 KV，输出无效。固定输出长度下可用它估计 I/O 优化的性能上界：峰值 2,034 token/s，精确预取达到约 85%。相同并发下，无预取暴露约 7.7–22.0 ms/token 的 I/O，精确预取降至约 3.0–11.2 ms。它说明测量点上的剩余瓶颈，不能证明正确实现的缓存管理普遍零成本（§4.6）。[^paper]

**负结果**：用本层选择猜下一层所需位置，只略增命中率，没有可测端到端收益。容易猜中的位置通常已被 LRU 保留，真正新进入选择集的记录才难预测，额外预取反而占用同一主机链路（§4.6）。[^paper]

## 批判性分析

### 论证链条

容量测量、热缓存轨迹、融合内核分解与共享索引消融分别支撑了“多容纳请求、少召回、低管理开销、隐藏残余 I/O”这条路径。最容易外推过度的是把吞吐收益解释成单次解码更快。图 5 的短输入几乎不改善，图 8 又直接测到额外 I/O；能否加速取决于省出的 HBM 是否真正转化成有效批次。[^paper]

### 假设压力测试

局部性不足时，缓存会把容量瓶颈转成带宽瓶颈。图 6 只有一条选择轨迹，尚不能给不同任务、长输出和高并发组合提供稳定命中保证。更快链路也需和可用主机容量一起看：§5 指出部分 Grace 平台的主机内存与所配 GPU HBM 接近，不能沿用 2 TB H200 服务器的容量倍数。多租户、NUMA 跨节点访问和 pinned memory 配额对结果的影响需要另外测量。[^paper]

### 实验可信度

三类选择器、三种设备和容量/策略/预取消融覆盖了设计的主要组成。基线仅为完整 KV 驻留的 SGLang，**没有与 ECHO 等卸载系统做同条件比较**。闭环吞吐与平均 TTFT/TPOT 也不能替代到达率变化下的 P99、SLO 达标率或成本。§5 对超出 HBM 的极端上下文只给容量推导，没有单独实测，不能把“支持更长上下文”写成已完成百万 token 端到端验证。[^paper]

### 系统性缺陷与实现边界

host KV 是完整历史的后备副本，备份流、预取流、计算流之间的 event 次序，以及请求撤回/暂停时的资源释放都影响正确性。附录 A 描述了集成路径，但没有故障注入或高竞争条件下的正确性实验。论文约 2,200 行新增 Python、CUDA 头文件及调度/后端改动说明了适配范围；当前笔记未据此声称已独立复现这些实现。[^paper]

## 局限与后续工作

- **静态缓存大小**：在混合长度和并发变化时比较固定 `B` 与受显存、主机带宽预算约束的动态 `B`，同时测峰值吞吐、P99 和每请求召回量。
- **预取机会依赖模型**：分别测独立索引、共享索引及提前生成索引的模型，区分减少传输量、提前传输和新增错误预取流量。
- **主机预算必须计入**：固定 pinned DRAM 与 NUMA 亲和性，测并发、上下文和其他任务争用对命中率、链路负载与 SLO 的影响。
- **低压力路径**：可对照 [[vLLM-Hybrid-HiSparse]] 所述按显存压力才逐页卸载的策略，测它相对固定主机后备路径在轻载和突发期间的收益；两者的数字需在同模型、硬件和版本下重新比较。[^hybrid]

## 相关

- **同类系统**：[[ECHO-OSDI26]] 也以主机完整 KV 和 GPU 热缓存服务原生稀疏注意力，并以提前预测加最终召回保持原选择；[[DirectKV-OSDI26]] 则研究高速互连上的直接读取。各自的硬件、工作负载和基线不同，不能排列其最高加速比。
- **缓存与 I/O**：[[Strata-OSDI26]] 是本文 GPU 辅助 I/O 的引用来源。附录 A 说明 HiSparse 复用 HiCache 主机基础设施，但 HiCache 侧重跨请求的前缀复用，HiSparse 管活动请求的解码工作集。[^paper]
- **模型与系统**：[[HySparse-arXiv26]]、[[HySparse2-arXiv26]] 与本工作使用不同的跨层共享对象；[[vLLM-Hybrid-HiSparse]] 汇集后续 vLLM 实现资料，原论文实验主要在 SGLang 上。
