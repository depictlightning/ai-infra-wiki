# TaiChi：统一混合和分离的阶段调度（arXiv 2025）

> **原题**：Prefill-Decode Aggregation or Disaggregation? Unifying Both for Goodput-Optimized LLM Serving

> **一句话总结**：不同 TTFT 和 TPOT 约束会改变混合与分离的收益，TaiChi 用不同块大小的实例和请求调度在两端之间调整；所测配置下相比分离基线的 goodput 提高 29%–77%（§4.2）。[^paper]

## 问题与动机

较大的 prefill 块可改善预填充能力，却增加对 decode 的干扰；严格隔离则可能让预填充资源不足。论文研究在不同阶段 SLO 组合下，能否让实例承担不同程度的混合执行，并按请求余量调度。

## 关键观察 / 隐含假设

- 论文观察到其所测环境中，较紧的 TTFT 和较宽松的 TPOT 有利于混合，反向约束则有利于分离（§2.3）；结论依赖实验基线与配置。
- 部分请求离 SLO 尚有余量，调度器可让它们承担额外延迟，为接近违约的请求释放资源（§2.4–2.5）。这依赖余量估计和后续执行时间预测。

## 核心方法

系统配置偏 prefill 和偏 decode 两类实例，分别设置 prefill 块大小和实例比例；两类实例仍可承担两个阶段（§3.1–3.2）。decode 调度优先使用低干扰实例，并选择有余量的请求转移；prefill 调度参考请求长度和排队状态，在请求间移动延迟（§3.3–3.4）。

## 设计取舍

### 三个配置量及两层混合

系统暴露 P-heavy 与 D-heavy 实例比例，以及两类实例各自的 prefill 块大小。P-heavy 用较大块换取更高 prefill 能力，D-heavy 用较小块限制对 decode 的干扰；两类实例都可以处理两阶段（§3.1）。配置搜索在负载明显变化时重新执行，论文称重配置以分钟计；因此请求级调度是快路径，实例配比调整是慢路径。[^paper]

批次层面，一个实例可混合不同请求的 prefill 与 decode；请求层面，同一请求的两个阶段可以在不同实例执行。这两个“混合”不等价。前者让实例利用多余能力，后者允许按请求余量迁移，代价是可能发生 KV 传输（§3.2）。[^paper]

### Decode 如何流动

请求先在低干扰的 D-heavy 实例开始 decode。若该侧显存达到水位线，调度器优先选择当前已生成 token 较多的请求转移到 P-heavy 实例，以释放空间；当 P-heavy 上请求的 TPOT 接近目标时，再考虑迁回 D-heavy（§3.3）。较长的已生成历史被用作可承受额外平均延迟的线索，系统不需要预知最终输出长度，但这个线索不能保证短尾请求或未来突变都安全。[^paper]

反复回流本身也说明配置可能不匹配：块太大或 D-heavy 数量不足时，调度器持续在实例间搬运请求，可能放大传输与调度开销。论文将回流视为保护机制，频繁触发时应调整配置，而非依靠迁移无限修复（§3.3）。[^paper]

### Prefill 如何分配延迟预算

代理为每个候选实例估算排队、执行和必要的 KV 传输时间，筛出预测 TTFT 满足目标的实例，再在可行集合中按排队 prefill token 数选择（§3.4）。较短请求更可能在 D-heavy 上仍能达标，从而把 P-heavy 能力留给长请求；但选择取决于现有队列，不能仅由输入长度决定。估算依赖离线画像与当前实例状态；如果所有候选都不可行，算法返回空结果，具体上层处理应结合实现核对。[^paper]

### 图 18 的组件分解

Qwen2.5-14B 的摘要实验以四个 256 token 块的共置实例为起点：基线达成率为 66.6%，改为两类实例后图示为 66.4%，随后加入 decode 流动和长度感知 prefill 达到 79.5%、91.2%（图 18）。因此架构本身在该点并未直接提高达成率；主要变化来自随后加入的调度，且这是单一负载点而非普适比例。[^paper]

混合实例利用本地处理能力减少固定阶段池的空闲，但更难预测干扰和请求级延迟。请求迁移引入 KV 传输，收益依赖互连和状态信息。

## 实验与结果

- 单机 8 张 A100，Qwen2.5-14B/32B；ShareGPT 与 arXiv 摘要数据采用泊松到达，分别过滤超过 2048 和 16384 token 的请求（§4.1）。
- 以至少 90% 请求达标时的最高请求速率衡量，所测实验相对混合基线提高 9%–47%，相比分离基线提高 29%–77%（§4.2）。
- Qwen2.5-14B 摘要任务的组件分解中，SLO 达成率从 66.6% 增至 91.2%；各组件贡献是在该配置中顺序加入时测得（§4.4、图 18）。
- 同一模型和任务的开销分解报告 KV 传输占请求总时间 0.20%；单机高速互连条件不代表跨节点性能（§4.5、图 19）。

### 请求余量的具体边界

论文在示例配置中将 D-heavy 的显存水位设置为 95%，P-heavy 请求当前 TPOT 达到目标的 0.96 倍时触发回流（§3.3）。这些是实验参数，不是通用安全边界。回流请求会被逻辑上视为新请求并重置输出长度，用于调度判断；用户实际经历的历史 token 间隔并不会因此消失。对每个 token 的尾延迟有约束时，依靠平均 TPOT 余量的策略还需单独验证。[^paper]

图 18 的 66.6% 到 91.2% 是同一组逐步加入组件后的达成率变化，单位是百分点；它不能直接与其他实验在不同负载下测得的 goodput 相对增长百分比相加。基线分离方案在这台机器上只能选择有限的 P/D 配比，而跨节点 KV 传输成本未被本实验充分覆盖（§4.1–4.4）。[^paper]

## 批判性分析

### 论证链条

作者先比较不同 SLO 下的两类配置，再以两类实例和请求级调度构造中间方案；结果支持所测配置收益，不证明对所有 SLO 和集群都最优。

### 假设压力测试

请求余量预测失准、长尾输出和延迟突变会降低延迟转移策略的可靠性；跨节点带宽受限会改变传输成本。

### 实验可信度

实验局限于单节点、两种 Qwen 模型和两类公开数据长度分布；到达过程是合成的，未验证跨节点拥塞和大规模失衡。

### 系统性缺陷

论文未充分评估故障恢复、多租户公平性和频繁调整实例配置的运维成本。

## 局限与后续工作

- 在多节点和可控网络拥塞下复测相同 SLO 曲线与 KV 传输占比。
- 对比预测偏差、输出长度重尾和突发流量对违约率及公平性的影响。
