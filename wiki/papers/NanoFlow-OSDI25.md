# NanoFlow：利用 GPU 内并行提高大模型服务吞吐量（OSDI 2025）

> **原题**：NanoFlow: Towards Optimal Large Language Model Serving Throughput

> **一句话总结**：在大批量且整体计算受限的条件下，NanoFlow 把批次拆成更细的 nano-batch，搜索并执行计算、访存和通信操作的重叠；论文在 8 张 A100 上的离线实验中报告，相对 TensorRT-LLM 的平均总 token 吞吐为 1.91 倍，但若干正文数字与图表存在差异。[^paper]

**阅读状态**：依据本地 OSDI 2025 会议版全文和 MinerU 文本，核对了图 5、7–9、11 以及 §3–6；PDF 另含封面，共 18 页。原文的理论上限、在线容量和消融结果有数值口径未对齐之处，本页标为 `needs-review`，具体差异见下文。没有复现实验。[^paper]

## 问题与动机

一次 Transformer 推理既包括矩阵乘法，也包括读取请求各自的 KV cache 和跨 GPU 集合通信。不同操作会占用不同资源：大批量矩阵乘法通常更依赖计算单元，解码注意力可能受显存带宽限制，张量并行中的同步则消耗互连带宽。若它们在一张 GPU 内先后执行，每种操作使用自己所需资源时，其他资源可能闲置（§2、图 1、图 4）。[^paper]

论文关注的是**提高每张 GPU 的总处理吞吐**，不是只缩短一次解码注意力的耗时。它将 prefill 的输入 token 和 decode 的输出 token 都计入总 token；该口径对不同输入、输出比例的工作负载有影响，不能直接当成输出 token 吞吐，或满足 TTFT 与 TPOT 的请求比例（§3.1）。[^paper]

[[SarathiServe-OSDI24]] 按请求和阶段组织分块 prefill，使新请求与已有解码请求能够混合组批。NanoFlow 同样使用分块和混合批次，但进一步拆分批次内部的操作：一个子批次执行矩阵乘法时，另一个子批次可执行注意力或通信。它关注单设备内的资源重叠；在不同 GPU 池间分配 prefill 和 decode 资源是 [[DistServe-OSDI24]]、[[Splitwise-ISCA24]] 一类工作的另一层问题。[^paper]

## 关键观察 / 隐含假设

- **整体瓶颈可能与单个操作不同。**

作者的代价模型比较一个迭代的计算、显存和网络需求。较大的批次让更多 token 共用权重读取；GQA 通过多个查询头共享 KV，降低每个请求的缓存占用，从而容纳更多请求。论文据此推断，所研究的大模型和工作负载在最大可容纳批量附近通常整体受计算限制（§3.2–3.4、图 2–3、表 2）。[^paper]

这是有条件的判断：最大批量必须放得进模型和 KV cache，且有足够请求填满；模型结构、上下文长度、量化精度、硬件算力与带宽、互连拓扑都会改变比例。图 3 的 LLaMA-3-8B 长输出配置已接近显存与计算的分界，不能据此说所有解码负载都计算受限。[^paper]

- **整体计算受限时，计算单元仍可能空闲。**

论文测量 LLaMA-2-70B、8 张 A100 和 2048 token 的稠密操作批量：按操作累加得到估计计算时间 114.17 ms、显存时间 45.09 ms、网络时间 31.33 ms（表 2）。这些是分别对资源需求估算后相加的时间，用于比较总体压力，并不是同一迭代的三个独立实测墙钟时间。部分单项实测也高于理想估计；尤其 prefill 注意力受到启动开销影响。[^paper]

作者观察到基线按操作顺序运行时，在访存或通信期间计算资源出现空档。若不同子批次没有数据依赖，就有机会把空档交给其他计算操作。但拆分会让权重被多次读取，小矩阵乘法也可能更低效；重叠的收益必须超过这两类成本（§3.6–3.7）。[^paper]

- **并发 kernel 的竞争需要估计。**

GPU 没有为计算、显存和网络分别提供论文所需的直接份额控制。NanoFlow 用矩阵乘法相对其独占运行的性能作为资源份额的代理指标 `R`，再测量同时运行的访存或网络操作能达到多少相对性能 `P`。图 5 的例子显示：让 GEMM 保留约 80% 的独占性能时，另一 GEMV 可达到约 30% 的独占性能；这些数字是测得的一组权衡，不代表 GPU 真正将三种资源按固定比例硬隔离（§4.1.1）。[^paper]

画像主要测量计算与访存、计算与网络的两两组合，并假设所得关系适用于三个操作重叠。作者在所测 GEMM 形状和 64 组批量组合中报告该映射的标准差不超过均值的 5%；这不能证明所有模型、长上下文、硬件或三方竞争都满足同样误差（§4.1.1）。[^paper]

## 核心方法

### 从完整批次拆出可独立推进的操作

NanoFlow 将原批次划成多个 nano-batch，并为每个子批次生成对应的 nano-operation。例如一个 2048 token 的矩阵乘法可以拆成处理前 768 和后 1280 个 token 的两个操作。它们对相同权重执行相同运算，但不同子批次的数据独立，因此可以把其中一个的计算与另一个的注意力或通信排在同一时间窗口（§3.7）。[^paper]

这不等于同一 token 的依赖消失。若后续投影依赖注意力结果，且两个操作处理的输入区间相交，就必须保留执行顺序；若处理的区间不相交，论文的搜索器才允许按其他资源约束重排。重复读权重是获得重叠机会的代价，而不是免费的优化。[^paper]

### 两阶段搜索执行流水线

自动搜索使用混合整数线性规划，输入模型操作依赖、可用批量和 kernel 画像，输出子批次大小、操作顺序及对应实现。它分两阶段控制搜索空间：[^paper]

1. **先找结构。** 忽略并发竞争，从每个操作拆成两个子操作开始，选择大小和顺序，使计算操作的空档尽量少。如果仍有计算空档，尝试进一步拆分邻近操作。搜索保留数据依赖，不把同一种资源受限的操作作为有益重叠；对部分集合通信也尝试等价变换。作者称优先找到可行解时约需 10 分钟，并未宣称取得全局最优（§4.1.2）。
2. **再考虑竞争。** 固定第一阶段得到的操作数、批量和顺序，利用独占及两两并发画像，将 `R` 映射到各 kernel 的性能，搜索一组使流水线更短的资源代理份额和 kernel 实现（§4.1.3）。

例如，论文给出的 70B 模型流水线在一层开头为更多计算、解码注意力和通信重叠机会使用四个子操作，其他部分主要使用两个；单卡 8B 模型没有跨 GPU 集合通信，搜索结果主要重叠计算与解码注意力（§4.1.4、图 6）。这是具体模型和硬件上的搜索结果，不是固定的最优拆分数。[^paper]

### 固定稠密批量与异步组批

运行时优先处理尚未完成的 decode 请求，再将等待中的 prefill 按 token 切块，填入预选的稠密操作批量。随着解码请求增多，留给 prefill 的 token 预算减少；解码请求完成后，预算又会释放。论文假定外部控制平面负责扩缩容、负载均衡及优先级路由；实例内部假定有足够请求并以相同优先级处理（§4.2.1）。因此它自身没有解决集群级 P:D 配比或按请求等级分配资源。[^paper]

CPU 在 GPU 执行当前迭代时提前准备下一批。代价是调度器不能立即识别本轮生成的结束标记：论文的流程可能为已结束请求额外运行一次 decode，然后再将其移出。作者认为评测负载的平均输出长度超过 100 token，因而额外工作的占比低于 1%；短输出请求的代价需要另测（§4.2.1、表 4）。[^paper]

系统还根据已生成 token 和平均输出长度预测显存峰值，只在预测可容纳时接纳新 prefill；若仍然耗尽显存，则把请求状态移到 CPU 并在有空间后恢复。输出长度预测不准可能增加换入换出或排队，论文没有提供任意长尾分布下的显存安全保证。[^paper]

### 多轮 KV cache 的复制与恢复

为复用多轮对话的上下文，NanoFlow 将运行中请求逐层生成的 KV 向主机侧复制，再用 CPU 内存与 SSD 组成分层缓存。复制尽量与 FFN 计算重叠；主机侧以 LRU 管理，内存压力大时可转到 SSD。恢复时先连续复制到 GPU 缓冲区，再散布到分页 KV 的目标位置。论文报告这种复制再散布的方法在其设置下比直接写入碎片化位置获得 7–10 倍主机到设备带宽（§4.2.2）。[^paper]

该路径需要额外主机内存、SSD、传输带宽及缓存管理。它优化多轮上下文复用，不是 prefill 实例向独立 decode 实例传递 KV，也不意味着能省掉所有重新计算。[^paper]

## 设计取舍

- **重叠收益与拆分成本**：子批次越细，潜在并发窗口越多，但权重重复读取和小批量 kernel 的效率损失也可能越大。图 9 中只拆分而不重叠的基线低于不拆分的基线。
- **固定大批量与延迟**：固定稠密批量便于套用已搜索流水线并提高吞吐；负载不足时可能填不满，在较低请求率下也可能比延迟优先设计更慢。
- **搜索成本与迁移能力**：两阶段搜索减少组合空间，但依赖模型、批量、kernel 和机器画像；kernel 库或硬件变化后，已有配置不一定仍然合适。
- **抽象资源份额与真实隔离**：`R` 是由 GEMM 性能定义的代理量，并发操作仍可能争用缓存、内存控制器或功耗；它不等于对 SM 或显存带宽的硬切分。
- **上下文复用与数据移动**：提前复制 KV 可减少后续轮次重算，但占用主机资源并引入竞争；对没有上下文复用的单轮请求未必划算。[^paper]

## 实验与结果

### 设置和指标

主要实验在 8 张 NVLink 互连的 A100 80GB SXM 上运行 LLaMA-2-70B，权重和激活使用 FP16，张量并行度为 8。单卡 LLaMA-3-8B 是其他模型实验中的例外。基线为 vLLM 0.5.3.post1、DeepSpeed-FastGen 0.2.3 和 TensorRT-LLM 0.8.0；这些是论文评测时的版本，不代表当前版本的性能（§6.1、图 7、脚注）。[^paper]

工作负载使用完整 Splitwise 轨迹，并从 LMSYS-Chat-1M 和 ShareGPT 各随机采样 5 万条请求。表 4 中输入/输出平均长度分别为 Splitwise 1155/211、LMSYS 102/222、ShareGPT 246/322 token；论文也评估固定输入输出长度。离线吞吐以输入与输出 token 总数除以执行时间，再按 GPU 数归一。[^paper]

### 离线吞吐

图 7(b) 中，8 张 A100、LLaMA-2-70B 的 Splitwise、LMSYS 和 ShareGPT 实验，NanoFlow 分别为 **1305、1306、1324 token/s/GPU**；TensorRT-LLM 分别为 **831、560、639 token/s/GPU**。按图中数值计算，三组比值分别约为 **1.57、2.33、2.07 倍**。这些是输入加输出 token 的总吞吐，不能直接等同于生成 token 的速率。[^paper]

正文报告这三类数据集负载下相对 TensorRT-LLM、DeepSpeed-FastGen、vLLM 的平均倍率为 **1.91、3.45、4.18 倍**（§6.2）。按图 7(b) 的三组 TensorRT-LLM 柱值计算算术平均倍率约为 1.99 倍，论文未在该处解释汇总方式；两者暂不视为可互相验证的同一数字。[^paper]

### 在线延迟与容量

论文根据数据集中的请求长度生成 5 分钟轨迹，并用指数分布模拟请求到达间隔。指标是**每个请求的端到端延迟除以其输出 token 数，再对请求取平均**；实验以该平均值 200 ms/token 为 SLO。这个指标包含排队和 prefill 等时间，不是逐 token 的实际间隔，也不是独立的 P99 TTFT 或 TPOT（§6.3）。[^paper]

作者称 LMSYS 负载下，NanoFlow 在该限制内的可承载请求率是 TensorRT-LLM 的 1.64 倍；但图 8(b) 在阈值处标注的两个请求率为 32.1 和 17.1 请求/秒，直接相除约为 1.88 倍。图中标注、正文倍率或它们的计算口径之间存在未解释差异，应分别引用，不能把其中一个改写成另一个。低请求率下，NanoFlow 因面向大批量吞吐而有略高延迟（§6.3、图 8）。[^paper]

### 消融与开销

图 9 的四组输入/输出配置都显示：只拆 nano-batch 而不重叠的吞吐低于不拆分基线。作者汇总为平均下降 13.2%；例如输入 512、输出 0 时，图中不重叠、只拆分、NanoFlow 分别为 **1273、1171、1446 token/s/GPU**。[^paper]

同一图中，输入 512、输出 0 的 NanoFlow 与不重叠基线之比约 **1.14 倍**；输入 512、输出 1024 时为 **1277/1048，约 1.22 倍**。正文却分别写 **1.07 倍**和 **1.17 倍**（§6.4）。即便实验方向一致，图文倍率也未能直接对齐，因此本页保留图中分子、分母，不把正文倍率当作已复算结果。[^paper]

论文另报告开启 KV 卸载使流水线变慢约 **3.0%**，同时在多轮 LMSYS-Chat 负载中将计算量降低 **3.02 倍**；这两项来自不同衡量对象，不能直接相减。图 10 的资源轨迹显示计算、内存和网络活动重叠，但并发仍有竞争（§6.4–6.5）。[^paper]

### 其他模型

固定输入 1024、输出 512 的其他模型实验中，图 11 给出 LLaMA-3-70B、Qwen2-72B、Deepseek-67B、Mixtral 8×7B、LLaMA-3-8B 的 NanoFlow 吞吐分别为 **1306、1213、1147、5188、12756 token/s/GPU**；最后一项运行在单张 A100，其余使用 8 张。图中相对各自理论值的比例依次为 **70.6%、67.4%、59.1%、50.4%、78.5%**。论文摘要和 §6.6 将范围写为 50%–72%，但图 11 的 8B 柱和图注写 78.5%；不能将正文范围当成覆盖该图全部模型的精确范围。[^paper]

## 批判性分析

### 论证链条：理论上限的适用条件和数值

论文在计算整体受限、稠密矩阵运算占主要 FLOPs 的简化下，用单 GPU 有效计算能力除以两倍模型参数量估计理论总吞吐，即 `Compute / (2 × P_model)`（式 5）。它用于判断资源重叠能否接近理想计算上界，不是对所有 SLO、批量和模型结构都可达到的性能保证。它省略或简化了注意力、采样、运行时开销、显存容量和竞争的影响；对稀疏激活的 MoE，还需辨别总参数和每 token 激活参数的口径。[^paper]

§3.5 给出的示例是每 GPU 280 TFLOPS、模型约 70B 参数，并报告理论值 **1857 token/s/GPU**。若直接将这两个近似数代入上述公式，结果约为 **2000 token/s/GPU**。原文未说明如何得到 1857；更精确参数或其他假设可能影响结果，但目前不能确定差异来源。图 7(b) 的最高柱值 1324 除以标注的 1857 约为 **71.3%**，而 §6.2 称最好达到 **68.5%**。论文 §6.5 也报告 68.5% 平均计算利用率；两种百分比的对应关系没有在文中得到足够解释。[^paper]

### 实验可信度：基线、负载与公平性

论文覆盖三个请求长度数据集、固定长度和多种模型，图 9 还使用共享异步调度与 kernel 库的内部基线，有助隔离拆分和重叠的作用。主结果的框架版本来自 2024 年前后的评测设置；不同框架的 kernel、调度、编译和参数配置均可能影响结果。作者对部分参数做了调优，但这些对比无法单独把全部端到端差距归因于 nano-batch。[^paper]

在线实验采样真实请求长度，却用合成的指数到达间隔生成 5 分钟请求流；它不等于在原生产到达轨迹或全天突发负载上部署。平均归一化延迟能反映吞吐与等待的变化，但不能替代逐请求 TTFT、逐 token TBT、P99 和双 SLO 达成率。论文提到近峰值时 P99 延迟与平均延迟的关系，却没有在摘要层面给出足以审计所有分布的完整实验矩阵（§6.3）。[^paper]

### 与 PD 混合、分离工作的边界

NanoFlow 的分块策略使一个批次可以同时包含 prefill 和 decode token；自动搜索重叠的是**不同子批次的异构操作**。这些子批次可以包含不同阶段的工作，但论文没有把它实现成按阶段固定划分 SM 的调度器，也没有把不同阶段部署到独立实例。[^paper]

[[MuxWise-ASPLOS26]] 和 [[DuetServe-ICML26]] 关注同一 GPU 上两阶段的资源划分与延迟目标；NanoFlow 更强调大批量下的操作流水和总吞吐。后者论文比较 NanoFlow 时使用了各自的负载、批量和指标，不能把两篇摘要中的倍率直接排名。[[PD-Serving]] 讨论的实例数量和跨实例 KV 传输，也不能用 NanoFlow 的 `R` 值代替。[^paper]

### 假设压力测试与系统性缺口

论文实现依赖 NVIDIA GPU、多个 CUDA stream 和 event，以及针对模型、kernel 和硬件的画像。两两干扰模型对三方重叠的近似、长上下文时的 KV 带宽、输出长度预测误差，以及请求不足时固定大批量的效率，都需要独立测量。论文没有给出多租户隔离、长时间运行的故障恢复、异构集群大规模控制或严格逐 token 尾延迟保证；这些不能由单节点吞吐结果推断出来。[^paper]

## 局限与后续工作

- 在同一硬件、模型和服务负载下，对比 NanoFlow、分块 prefill 及 GPU 内阶段划分方案，同时记录输入/输出吞吐、TTFT、逐 token 延迟、P99 和双 SLO 达标率。
- 分别改变批量、请求到达突发、输入输出长度、前缀命中率和量化精度，测量何时重复读取权重与竞争开销超过重叠收益。
- 在新的 GPU 和 kernel 版本上重建两两与三方竞争画像，记录预测误差、画像时间及流水线切换成本。
- 核实式 5 的 1857 数值来源、图 8 的请求率与正文倍率、图 9 的柱值与正文倍率，以及图 11 的比例范围；在来源解释前保留上述差异。
- 用真实生产到达时间或更长的突发轨迹验证显存预测、异步结束检测和空闲实例缩减，避免仅用固定请求长度的短实验推断生产效果。
