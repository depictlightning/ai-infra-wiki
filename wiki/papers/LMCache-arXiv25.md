# LMCache：连接推理引擎和多级存储的 KV cache 层（arXiv 2025）

> **原题**：LMCache: An Efficient KV Cache Layer for Enterprise-Scale LLM Inference

> **一句话总结**：LMCache 在推理引擎与异构存储之间提供 KV 提取、加载、传输和管理接口，并以批量搬运和计算重叠减少开销；在单机多轮问答设置中，它在相同 TTFT 下的请求吞吐为各模型最强基线的 2.3–14 倍（§5–8、图 8）。[^paper]

**版本与阅读范围**：使用本地已有的 19 页 PDF 与 MinerU 全文，其 PDF 的 SHA-256 与 [arXiv:2510.09665v2](https://arxiv.org/abs/2510.09665v2) 相同。已阅读架构、接口、评测与部署经验，核对图 6、7、15 和表 5。本文是作者技术报告／预印本，报告的版本与今天的软件功能不必完全相同；未复现实验。[^paper]

## 问题与动机

一次请求中生成的 KV 原本可以留在 GPU，用于后续解码。重复文档问答、多轮对话和智能体请求还可能在不同请求之间复用同一前缀；P/D 分离则需要把当前请求的 KV 交给另一推理实例。两类场景都要求引擎将 KV 暴露给外部组件，但缓存的生命周期和目的不同（§2）。[^paper]

仅把数据搬离 GPU 并不足以获得收益。推理引擎的页可能很小且地址分散；存储和网络偏好较大的传输；引擎接口、模型 KV 布局和后端也会变化。LMCache 在引擎与存储之间提供一层管理和传输接口，并支持请求调度器查询缓存位置（§3–4）。[^paper]

## 关键观察 / 隐含假设

- **观察 1：缓存命中并不总比重算快。** 图 15 在所测 B200 条件下，32 Gbps 加载路径约在 256K token 以后才优于重算；64、128 Gbps 的曲线在该测试范围内更快（§8.7）。[^paper]
  - **依赖假设**：所选前缀足够长，实际可用链路带宽和 GPU prefill 速度接近画像，加载和布局转换没有额外排队。短前缀、链路拥塞或更快的 prefill 可能使重算更合适；256K 不是通用阈值。
- **观察 2：碎片化的小页传输难以充分利用链路。** 论文列举常见模型的页大小约为 20–63 KB；在 CPU 加载微基准中，chunk 搬运达到 400 Gbps，所测 vLLM 原生 CPU 卸载为 88 Gbps（§3.1、§8.6、表 5）。[^paper]
  - **代价假设**：合并页的 GPU 缓冲、聚合与拆分开销小于节省的小 I/O 开销，且显存有空间容纳暂存区；小请求、缓冲不足或 GPU 忙碌时需要重新测量。
- **观察 3：请求上下文的保留方式改变前缀命中。** 作者报告一份企业轨迹在截去较早上下文后，命中率约从 85% 降至 45%（§9）。[^paper]
  - **依赖假设**：应用确实存在稳定的共享前缀，并以相同 token 序列提交；会话截断、模板改写或个性化内容可能让实际命中显著下降。这组数字只适用于论文轨迹。
- **观察 4：跨实例复用需要位置和生命周期信息。** 论文的控制器汇总各实例接纳和淘汰通知，返回命中位置，也提供迁移接口；这些是所述系统设计而非容错实验结果（§7）。[^paper]
  - **依赖假设**：控制器的状态更新足够及时，查询结果在加载时仍有效，查询和维护开销不会抵消复用收益。节点失败、并发淘汰与元数据规模上限需要单独验证。

## 核心方法

### 引擎、缓存层和后端的关系

推理引擎负责调度请求和执行模型；连接器在调度阶段报告额外命中的 token，在模型执行阶段发起加载和保存；LMCache 实例内部有 token 处理、缓存引擎、存储管理和传输组件。后端可为本机 CPU 内存、磁盘或远端服务，论文也讨论 P/D 和点对点路径（§4、图 5–6）。[^paper]

沿着一次前缀命中请求看，连接器先提供 token 和 GPU 页地址，token processor 确定后端已有的连续前缀，再由 storage manager 查找位置、经 transfer channel 把数据送回正确的 GPU 页；事件管理器负责异步加载状态。存储新 KV 时方向相反：先确定尚未保存的 token，再通过传输组件写入后端。查找结果必须能对应请求前缀、模型和实际缓存内容，单纯知道“存过一些 token”不足以决定哪些计算可以跳过（§4、图 6）。[^paper]

这是一条可组合的路径：引擎负责计算，LMCache 提供引擎与缓存的接入、搬运及管理，[[Mooncake-FAST25]] 的存储服务可以承担外部共享存储。实际部署是否采用这种组合取决于版本和配置；并非所有 LMCache 部署都使用 Mooncake。[^paper][^docs]

### 批量搬运与计算重叠

论文将逻辑缓存组织成比引擎物理页更大的传输单元，在不同设备之间批量保存和加载，减少重复的小 I/O。新生成的 decode KV 可以先积攒到一定数量再写出；多个目标读取同一段数据时通过引用计数共享缓冲区，避免为每次操作复制整份数据（§5.1、§5.3）。[^paper]

以写出为例，论文的默认 chunk 对应 256 token：定制 CUDA 内核先把分散的 GPU 页聚合到连续的中间 GPU 缓冲区，再通过 DMA 将其写向慢层；读取时先把 chunk 送进缓冲区，再拆回引擎分配的页。聚合减少小传输调用，但这条路径仍有页与缓冲区之间的数据搬运。引用计数减少的是多目的地并发传输时不必要的**额外副本**，不能理解为 GPU、CPU 和远端之间完全没有拷贝（§5.1、§5.3）。[^paper]

按层流水线中，当前层计算时可以加载下一层 KV；请求排队时也可以预取慢层数据。真正执行前仍须等待所需数据完成搬运。是否能隐藏全部延迟取决于层计算时间、数据大小与带宽；异步接口本身不保证重叠充分（§5.2、图 6、13）。[^paper]

按层加载先把第 1 层的数据放入页，计算第 1 层时复用暂存空间加载第 2 层；论文因此只要求可容纳一层 KV 的固定大小中间缓冲区。对于排队请求，预取可以先把远端数据移动到本地 CPU 等更快的层，不必等到模型运行时才启动。前者利用层间计算窗口，后者利用请求等待窗口；两者都必须在最终消费相应页之前同步（§5.2）。[^paper]

### 连接器如何协调调度与执行

论文将接口分为调度器侧和模型执行侧，分别解决“跳过哪些 token 的计算”和“数据何时真正到位”：[^paper]

| 阶段 | 论文中的接口及作用 |
|---|---|
| 查询命中 | `get_num_new_matched_tokens` 返回后端可额外复用的前缀长度；也可返回 `None`，让请求先回等待队列，给异步 I/O 留出时间。 |
| 分配与准备 | `update_state_after_alloc` 更新哪些页需要外部加载，`build_connector_meta` 准备页地址和传输元数据。 |
| 按层读取 | `start_load_kv` 启动读取；每层执行前调用 `wait_load_kv` 等待本层，并触发后续层的加载。 |
| 按层写出 | `start_store_kv` 启动写出，`wait_store_kv` 在复用相关缓冲或推进写出前等待必要操作完成。 |

这样调度器看到的命中会影响待处理 token 数，而执行侧仍要确保缓存已装入正确的物理页。论文也描述了非逐层模式：先同步加载完整缓存、运行本轮计算，再同步写出；这是不同的调度路径，不能把两种模式的缓冲需求混为一谈（§6、表 2）。[^paper]

### 动态写出和控制接口

论文描述 GPU 空闲页的动态写出：系统维护已复制与待复制范围，在页面再次分配前尽量保存可复用 KV。复制窗口太小可能使分配等待，太大则提高 GPU 与 CPU 的重复存储比例；论文只描述将这一策略用于 GPU 和 CPU 层（§5.3、图 7）。[^paper]

图 7 用 `start`、`current`、`end` 三个指针记录空闲页区间、已完成写出的位置和计划写出的边界。后台推进 `current`；新请求分配页时，如果所需页尚未被复制，分配必须等待。比如只有一页完成复制，而请求需要回收三页，就需等待另外两页写出。扩大提前复制窗口能减少等待，却同时增加 GPU 与 CPU 保存同一数据的时间和容量（§5.3）。[^paper]

在论文版本的控制面，集中式管理器接收各实例的缓存接纳和淘汰通告；外部接口提供位置查询、迁移、清理、固定和压缩等能力。路由器可以用查询结果辅助选择实例，但位置命中、排队、传输竞争和元数据时效都影响最终收益（§7）。[^paper]

控制器由集中管理进程和各实例的 worker 组成：worker 通过 `batched_admit` / `batched_evict` 上报本地变化；路由器调用 `lookup` 可得到实例、设备和命中 token 数；缩容或重新平衡时，可通过 `move` 请求源端向目标位置转移。缺页实例还可经控制器查找 peer。这些 API 描述了可执行的协调动作，但论文没有据此证明陈旧位置、并发淘汰和节点故障下的强一致性（§7、表 3）。[^paper]

### 前缀复用与 P/D 交接的区别

两条路径都使用 KV 搬运，但触发条件不同。前缀复用发生在请求到达时：先检查一段已有历史是否匹配，加载成功后跳过相应 prefill。P/D 交接发生在当前请求的两个计算阶段之间：prefill 为该请求生成状态，decode 端必须拿到所需状态才能继续，不要求这段前缀曾被其他请求使用。前一种路径可以在加载慢于重算时选择重算；后一种路径还要承担跨实例交接和目标页分配的依赖。[^paper]

论文的 P/D 实验将 prefill 产生的 chunk 先聚合到 prefill GPU 缓冲，再传到 decode GPU 缓冲并拆回目标页；所测 vLLM 原生方案由 NIXL 按分散页地址直接搬运。图 12 的差异因此与**当时两种实现的传输粒度和路径**有关，而不仅是“分离”本身的收益。论文使用 NVLink 连接两侧，并按模型分别配置实例的 GPU 数，不能直接当成跨机低带宽网络的结果（§8.5、表 4）。[^paper]

## 设计取舍

- **慢层容量换加载开销**：更多前缀可保留，CPU、存储和网络带宽也会被占用；低速链路上重算可能更快。
- **大块传输换缓冲和粒度**：批量 I/O 减少小页开销，但需要页与 chunk 的转换及暂存。
- **预取换潜在浪费**：提前读取可隐藏部分等待，未被使用的数据会占据容量与链路。
- **独立接口换版本维护**：引擎与后端解耦依赖连接器适配；论文中的接口不保证后来所有版本都兼容。
- **缓存保存和模型近似分开判断**：普通前缀复用可保存完整 KV；接口也允许压缩，是否有损取决于具体编码与配置。

## 实验与结果

论文单机测试使用最高 8×H100，按模型需求选择 GPU 数，CPU 缓存上限 500 GB；多轮问答一般每次约 10K 输入、最多 100 输出。基线包括 GPU 前缀缓存、论文评测时 vLLM 原生 CPU 卸载和两个商业接口。所有结果受模型、版本、缓存大小与请求复用结构影响（§8.1–8.2）。[^paper]

具体版本为 LMCache 0.3.6、基础 vLLM 0.10.2 和原生 CPU offload 对照 vLLM 0.11.0。多轮模拟先有 40 个用户，再按给定请求率加入用户；常见模型使用约 10K 输入，Llama-3.1-8B 设置为 20K，输出最多 100 token。不同模型使用可启动该模型的最少 H100 数，不能仅看图中曲线就假定它们的 GPU 预算相同（§8.1–8.2）。[^paper]

| 实验 | 对照与结果 |
|---|---|
| 单机多轮问答 | 同 TTFT 下，LMCache 在五个所测模型上的请求吞吐为各自最强基线的 2.3–14 倍；商业服务为黑盒，未必支持所有模型（图 8、§8.2）。 |
| CPU 加载微基准 | LMCache 为 400 Gbps，所测 vLLM 原生 CPU 卸载为 88 Gbps；反映特定实现和传输粒度，不代表所有版本或硬件的普遍上限（表 5、§8.6）。 |
| 远端存储 | TriviaQA、15 Gbps 远端路径下，在相同 TTFT 的比较中吞吐为基础 vLLM 的 1.3–3 倍；远端容量、命中和传输同时影响结果（图 11、§8.4）。 |
| P/D 数据传输 | 随机输入 8K、输出 200 token，四个模型中平均 TTFT 降为所测 vLLM 原生 P/D 方案的约 1/1.53–1/1.84，平均 ITL 降为约 1/1.12–1/1.66（图 12、§8.5）。 |
| 何时重算 | B200 上 32 Gbps、所测长度下约 256K token 才出现加载优于重算的交叉；64/128 Gbps 的加载曲线低于所测重算曲线（图 15）。 |
| 另一引擎 | Qwen3-32B、2×H100 时，LMCache 与 SGLang 原生 CPU 卸载的表现接近；这一结果不能概括所有模型或最新版本（图 16、§8.8）。 |

对比这些实验时应当分清变化的变量：单机实验既扩大了 CPU 缓存也换了搬运实现；远端实验还引入 15 Gbps 网络；P/D 实验比较的是两侧之间的状态交接。表 5 的 400 / 88 Gbps 是 CPU 加载微基准，不是这三种端到端场景都获得的有效网络带宽。商业服务缺少内部实现信息，作者对其缓存能力的解释只能作为推测。[^paper]

企业轨迹部分还有一处表述不清：§8.3 称原始轨迹持续数天，调整时间后实验在一小时内完成，但同时使用了“stretch”一词；文中没有给出足以消除这一措辞矛盾的完整重放规则。这里仅记录时间尺度经过调整，不推断原始请求到达率和缩放因子。[^paper]

## 批判性分析

### 论证链条

报告把缓存容量、传输粒度和引擎接口放在同一系统中分析，既提供端到端曲线，也测试 CPU 加载与异步重叠。容量扩大和搬运优化同时变化，端到端倍数不能单独归因于某个内核。[^paper]

### 假设压力测试

短前缀、低复用、高网络拥塞和高更新速率下，保存与查询的代价可能超过复用收益。长对话中插入、截断或改变历史 token 会影响前缀匹配；需要分别记录逻辑命中、可用命中、加载成功率和实际节省的 prefill。[^paper]

### 实验可信度与系统性缺陷

商业基线内部实现未知；作者对其原因的推测不是可验证事实。企业轨迹来自长度分布，论文为了实验可行调整了时间尺度，不能将其直接当成原生产负载。论文报告部分案例和平均指标，缓存一致性、隔离、故障恢复和控制面规模上限仍需独立验证（§8–9）。[^paper]

## 局限与后续工作

- 同一模型和轨迹下比较 [[Strata-OSDI26]] 的分层加载与 LMCache，报告缓存预算、命中率、带宽、TTFT 分位数和版本。
- 测量从 CPU、SSD、远端加载与重算的交叉点，将链路竞争和缓存淘汰纳入实验。
- 区分历史前缀复用与当前请求 P/D 交接；两条路径可以共用传输组件，但生命周期和延迟约束不同。
