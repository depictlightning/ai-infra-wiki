# LMCache：连接推理引擎和多级存储的 KV cache 层（arXiv 2025）

> **原题**：LMCache: An Efficient KV Cache Layer for Enterprise-Scale LLM Inference

> **一句话总结**：LMCache 在推理引擎与异构存储之间提供 KV 提取、加载、传输和管理接口，并以批量搬运和计算重叠减少开销；在单机多轮问答设置中，它在相同 TTFT 下的请求吞吐为各模型最强基线的 2.3–14 倍（§5–8、图 8）。[^paper]

**版本与阅读范围**：使用本地已有的 19 页 PDF 与 MinerU 全文，其 PDF 的 SHA-256 与 [arXiv:2510.09665v2](https://arxiv.org/abs/2510.09665v2) 相同。已阅读架构、接口、评测与部署经验，核对图 6、7、15 和表 5。本文是作者技术报告／预印本，报告的版本与今天的软件功能不必完全相同；未复现实验。[^paper]

## 问题与动机

一次请求中生成的 KV 原本可以留在 GPU，用于后续解码。重复文档问答、多轮对话和智能体请求还可能在不同请求之间复用同一前缀；P/D 分离则需要把当前请求的 KV 交给另一推理实例。两类场景都要求引擎将 KV 暴露给外部组件，但缓存的生命周期和目的不同（§2）。[^paper]

仅把数据搬离 GPU 并不足以获得收益。推理引擎的页可能很小且地址分散；存储和网络偏好较大的传输；引擎接口、模型 KV 布局和后端也会变化。LMCache 在引擎与存储之间提供一层管理和传输接口，并支持请求调度器查询缓存位置（§3–4）。[^paper]

## 关键观察 / 隐含假设

- **复用是否有益取决于加载成本。** 远端缓存可能容量大、命中多，但如果链路慢、前缀短或模型 prefill 快，读取 KV 可能慢于直接重算。图 15 在所测 B200 条件下，32 Gbps 路径约在 256K token 以后才优于重算；64、128 Gbps 的曲线在该测试范围内更快（§8.7）。交叉点不是通用阈值。[^paper]
- **小页便于分配，碎片传输却难以吃满链路。** 系统将多个页组织为较大的 chunk 批量搬运，并在层间或请求间重叠计算与读取；更大粒度也需要缓冲、布局转换与额外显存（§3.1、§5）。[^paper]
- **高前缀命中依赖真实请求结构。** 作者报告一份企业轨迹在截去较早上下文后命中率约从 85% 降到 45%。这是该轨迹的观察，不是任何窗口截断都会造成的固定降幅（§9）。[^paper]
- **控制面需要看到缓存位置。** 论文以集中式管理器聚合各实例通告，并提供查找、迁移等接口；其元数据一致性、故障和扩展行为需要在目标部署中另测（§7）。[^paper]

## 核心方法

### 引擎、缓存层和后端的关系

推理引擎负责调度请求和执行模型；连接器在调度阶段报告额外命中的 token，在模型执行阶段发起加载和保存；LMCache 实例内部有 token 处理、缓存引擎、存储管理和传输组件。后端可为本机 CPU 内存、磁盘或远端服务，论文也讨论 P/D 和点对点路径（§4、图 5–6）。[^paper]

这是一条可组合的路径：引擎负责计算，LMCache 提供引擎与缓存的接入、搬运及管理，[[Mooncake-FAST25]] 的存储服务可以承担外部共享存储。实际部署是否采用这种组合取决于版本和配置；并非所有 LMCache 部署都使用 Mooncake。[^paper][^docs]

### 批量搬运与计算重叠

论文将逻辑缓存组织成比引擎物理页更大的传输单元，在不同设备之间批量保存和加载，减少重复的小 I/O。新生成的 decode KV 可以先积攒到一定数量再写出；多个目标读取同一段数据时通过引用计数共享缓冲区，避免为每次操作复制整份数据（§5.1、§5.3）。[^paper]

按层流水线中，当前层计算时可以加载下一层 KV；请求排队时也可以预取慢层数据。真正执行前仍须等待所需数据完成搬运。是否能隐藏全部延迟取决于层计算时间、数据大小与带宽；异步接口本身不保证重叠充分（§5.2、图 6、13）。[^paper]

### 动态写出和控制接口

论文描述 GPU 空闲页的动态写出：系统维护已复制与待复制范围，在页面再次分配前尽量保存可复用 KV。复制窗口太小可能使分配等待，太大则提高 GPU 与 CPU 的重复存储比例；论文只描述将这一策略用于 GPU 和 CPU 层（§5.3、图 7）。[^paper]

在论文版本的控制面，集中式管理器接收各实例的缓存接纳和淘汰通告；外部接口提供位置查询、迁移、清理、固定和压缩等能力。路由器可以用查询结果辅助选择实例，但位置命中、排队、传输竞争和元数据时效都影响最终收益（§7）。[^paper]

## 设计取舍

- **慢层容量换加载开销**：更多前缀可保留，CPU、存储和网络带宽也会被占用；低速链路上重算可能更快。
- **大块传输换缓冲和粒度**：批量 I/O 减少小页开销，但需要页与 chunk 的转换及暂存。
- **预取换潜在浪费**：提前读取可隐藏部分等待，未被使用的数据会占据容量与链路。
- **独立接口换版本维护**：引擎与后端解耦依赖连接器适配；论文中的接口不保证后来所有版本都兼容。
- **缓存保存和模型近似分开判断**：普通前缀复用可保存完整 KV；接口也允许压缩，是否有损取决于具体编码与配置。

## 实验与结果

论文单机测试使用最高 8×H100，按模型需求选择 GPU 数，CPU 缓存上限 500 GB；多轮问答一般每次约 10K 输入、最多 100 输出。基线包括 GPU 前缀缓存、论文评测时 vLLM 原生 CPU 卸载和两个商业接口。所有结果受模型、版本、缓存大小与请求复用结构影响（§8.1–8.2）。[^paper]

| 实验 | 对照与结果 |
|---|---|
| 单机多轮问答 | 同 TTFT 下，LMCache 在五个所测模型上的请求吞吐为各自最强基线的 2.3–14 倍；商业服务为黑盒，未必支持所有模型（图 8、§8.2）。 |
| CPU 加载微基准 | LMCache 为 400 Gbps，所测 vLLM 原生 CPU 卸载为 88 Gbps；反映特定实现和传输粒度，不代表所有版本或硬件的普遍上限（表 5、§8.6）。 |
| 远端存储 | TriviaQA、15 Gbps 远端路径下，在相同 TTFT 的比较中吞吐为基础 vLLM 的 1.3–3 倍；远端容量、命中和传输同时影响结果（图 11、§8.4）。 |
| P/D 数据传输 | 随机输入 8K、输出 200 token，四个模型中平均 TTFT 降为所测 vLLM 原生 P/D 方案的约 1/1.53–1/1.84，平均 ITL 降为约 1/1.12–1/1.66（图 12、§8.5）。 |
| 何时重算 | B200 上 32 Gbps、所测长度下约 256K token 才出现加载优于重算的交叉；64/128 Gbps 的加载曲线低于所测重算曲线（图 15）。 |
| 另一引擎 | Qwen3-32B、2×H100 时，LMCache 与 SGLang 原生 CPU 卸载的表现接近；这一结果不能概括所有模型或最新版本（图 16、§8.8）。 |

## 批判性分析

### 论证链条

报告把缓存容量、传输粒度和引擎接口放在同一系统中分析，既提供端到端曲线，也测试 CPU 加载与异步重叠。容量扩大和搬运优化同时变化，端到端倍数不能单独归因于某个内核。[^paper]

### 假设压力测试

短前缀、低复用、高网络拥塞和高更新速率下，保存与查询的代价可能超过复用收益。长对话中插入、截断或改变历史 token 会影响前缀匹配；需要分别记录逻辑命中、可用命中、加载成功率和实际节省的 prefill。[^paper]

### 实验可信度与系统性缺陷

商业基线内部实现未知；作者对其原因的推测不是可验证事实。企业轨迹来自长度分布，论文为了实验可行调整了时间尺度，不能将其直接当成原生产负载。论文报告部分案例和平均指标，缓存一致性、隔离、故障恢复和控制面规模上限仍需独立验证（§8–9）。[^paper]

## 局限与后续工作

- 同一模型和轨迹下比较 [[Strata-OSDI26]] 的分层加载与 LMCache，报告缓存预算、命中率、带宽、TTFT 分位数和版本。
- 测量从 CPU、SSD、远端加载与重算的交叉点，将链路竞争和缓存淘汰纳入实验。
- 区分历史前缀复用与当前请求 P/D 交接；两条路径可以共用传输组件，但生命周期和延迟约束不同。
