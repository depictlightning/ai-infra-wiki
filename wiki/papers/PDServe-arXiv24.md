# P/D-Serve：大规模分离部署的阶段组织与配比调整（arXiv 2024）

> **原题**：P/D-Serve: Serving Disaggregated Large Language Model at Scale

> **一句话总结**：P/D-Serve 将同类请求组织到分离式实例组，用阶段能力匹配调整 P/D 配比，并结合按需转发与连续缓冲的 KV 传输，处理大规模部署中的排队、失衡和网络问题。[^paper]

**阅读状态**：依据 2024 年 arXiv v1 的本地 PDF 和 MinerU 全文，已回看图 12–14；作者报告的商业部署规模和评测不能独立验证，代码及其余图表未逐项核对。[^paper]

## 问题与动机

阶段分离后，整个服务的处理能力仍受较慢的一侧约束。如果 prefill 产出快于 decode 消费，KV 和请求可能在两侧交界处等待；反过来，decode 也可能空闲。不同业务的 prompt 前缀、输出长度和流量周期不同，把所有请求混合在同一资源池，可能同时造成缓存命中下降和阶段配比失衡（§2.2）。[^paper]

论文还指出两个部署问题：全局调度器周期性观察到的队列或连接数不一定反映某个 prefill 是否能及时处理新请求；将分页 KV 的离散小块逐一通过设备间网络传送，也可能被控制开销和多跳竞争拖慢。作者围绕业务组织、配比、转发和传输提出一套系统设计（§1–3）。[^paper]

## 关键观察 / 隐含假设

- **容量要按阶段能力匹配，而非只看卡数。** 实例批量、执行时间、前缀缓存和输出长度都影响有效处理速度；两侧资源数之比必须结合这些条件估计（§2.1、§3.3）。[^paper]
- **把相似请求组织在一起可能增加前缀复用。** 这依赖业务请求具有重复前缀，且组内 HBM 足以保留有用 KV；前缀变化又可能改变合适的 P/D 配比（§2.2.1）。[^paper]
- **观测到的生产规模与受控实验需要区分。** 作者报告系统在数万 NPU 上商用超过八个月，但 §4 的受控评测使用来自真实服务的数据，并非直接回放完整生产集群；结果做了归一化处理（摘要、§4.1）。[^paper]

## 核心方法

### 先建立阶段能力的近似模型

论文以实例数量、批量和每批处理时间估计两个阶段的处理能力：prefill 侧约为 `n_p × b_p / T_p`，decode 侧约为 `n_d × b_d / T_d`。其中 `T_p` 受首 token 时间和前缀缓存影响；`T_d` 由 KV 传输和输出 token 的平均生成时间共同影响。实际吞吐同时受到输入流量与两侧能力的较小者约束（§2.1）。[^paper]

例如根据画像，若每个 P 实例每秒能完成 8 个请求，而每个 D 实例能持续消费 4 个请求，忽略网络与离散约束时，1P2D 可以让两个阶段能力都接近每秒 8 个请求。这是帮助理解速率匹配的教学例子，实际批量、长尾和 SLO 可能使可用能力不同。[^paper]

这也是 P/D 数量比例不能直接等于输入 token 与输出 token 比例的原因：每侧速度由批量、缓存、设备和执行方式决定。系统可以先画像求目标配比，再随实际业务变化重新估计（§3.3）。[^paper]

### 以业务场景组织实例组

P/D-Serve 将服务内相似场景映射到由 prefill、decode 和 RoCE 网络组成的实例组。相似前缀更可能在少量 prefill 实例中复用；按组管理也为滚动升级、扩缩容和故障替换提供边界。容器是资源分配单位，每个实例可以包含多个 NPU 或 GPU，因此实例比例与设备比例不一定相同（§3.1–3.3）。[^paper]

扩缩容可以增减整组。若仅改变配比，系统逐步更新组和 RoCE 连接：固定总实例数时可能从部分组释放实例、再加入其他组；总量可变时也可能在中间步骤引入新实例。论文强调逐组调整以维持服务，但这并不证明每个在途请求在故障和重配置下都能无损迁移（§3.3）。[^paper]

### 如何发现比例失衡

监控器观察场景的平均端到端延迟和 prefill 时间占比。当两者一起上升时，论文建议检查 prefill 容量；当端到端延迟上升而 prefill 占比下降时，建议检查 decode 容量。进一步画像可以按阶段能力匹配计算目标比例，也可以在观察到变化后逐步调整（§3.3）。这是瓶颈诊断启发式，多个指标同时受网络和排队影响时仍可能产生歧义。[^paper]

### 负载转发和 KV 传输

旧版本让请求排在选中的 prefill 本地队列，网关依据连接数选择实例；连接在 decode 期间仍保持，因而未必代表 prefill 当前繁忙程度。新设计让 prefill 在不具备处理能力时拒绝请求，网关再尝试其他实例，以便发现空闲容量（§3.5、图 9）。重试策略是否会在整体过载时造成额外流量，取决于具体限制和部署。[^paper]

KV 发送侧将待传数据组织为连续缓冲区，接收侧通过 RecvScatter 恢复成目标的离散块。目的是减少逐块控制与传输的空隙；多跳路径冲突仍可能造成传输时间波动（§3.6、图 10）。[^paper]

### 失败恢复的边界

系统通过设备健康检查和元数据更新隔离故障实例，再准备新容器、建立连接并加载模型。论文明确不讨论迁移正在流式输出的请求；某些失败路径会终止连接并返回默认文本或其他替代响应。因此“服务继续运行”不能等同于受影响请求无损恢复（§3.4、图 8）。[^paper]

## 设计取舍

- **细分组与资源碎片**：相似场景分组可提高前缀局部性，却可能让小组的阶段容量难以整除或共享。
- **重试与排队**：拒绝后转发可以寻找空闲 prefill；超载时重试也需要限制次数和观察额外排队。
- **连续传输与缓冲开销**：合并块可能提高网络利用率，但需要额外缓冲及接收侧恢复，效果依赖数据大小和链路竞争。

## 实验与结果

作者报告 P/D-Serve 基于 Ascend 和 MindSpore，在数万 NPU 的商业部署中使用超过八个月；论文没有给出足以独立复核整个生产服务的细节。§4 的实验使用从真实服务的微调数据集中取得的请求，设备是生产设施的一个子集；图表中不少轴和模型名称经过归一化或匿名化。[^paper]

- 固定并发请求并按完成补充的实验中，作者基于阶段能力匹配选择配比，报告所选配比的吞吐比图中其他对照至少高 60%（§4、图 12–13）。这是所选场景的相对结果，不是任意 P/D 配置下的固定收益。[^paper]
- 转发实验中，旧策略随着负载增长的成功率最低约为 57%；作者报告使用新转发策略后，在所测更高负载下保持至少 99%，相同负载下最大差距为 42.3 个百分点。图 14a 的曲线经过拟合；成功率按超时条件定义，不能直接当作所有 SLO 的整体达成率（§4、图 14）。[^paper]
- 连续缓冲的 KV 传输对比离散块传输，作者报告平均传输时间减少 46%（§4、图 14）。这针对该微基准和路径条件，不能等同于端到端时间减少 46%。[^paper]
- 图 13 的故障替换示例涉及新容器和模型加载，作者描述加载为分钟级；论文的生产规模声明、单次替换过程和用户级恢复保证应分别理解（§4、图 13）。[^paper]

## 批判性分析

### 论证链条

论文先用两侧处理能力解释配比，再描述组级重配置、转发与传输，并分别提供归一化结果。模型强调平均能力，无法单独预测请求长尾和排队；生产数据匿名化也使外部复现具体绝对收益较难。

### 假设压力测试

同类前缀的热度变化、需求突发、RoCE 竞争和不均匀输出长度都会改变原有画像。E2E 和 prefill 占比是粗粒度信号，网络或排队变化也可能影响它们；仅靠比例推断瓶颈可能误判。

### 实验可信度

作者给出商业部署背景和相应系统路径，但评测请求来自真实业务数据而非完整线上回放，且模型、流量及许多性能轴匿名化。受控配比实验使用固定并发闭环，不能直接代表开放到达的突发尾延迟。生产规模属于作者声明，不能由本文笔记独立验证。

### 系统性缺陷

论文没有迁移正在输出的失败请求；按需重试和逐组重建可能引入额外延迟或短期容量下降。更细的失败语义、重试上限、跨租户隔离和在线观测精度需要具体实现和故障实验验证。

## 局限与后续工作

- 用开放到达与闭环请求分别测量相同 P/D 配比，记录队列、违约率和缓存占用。
- 在网络拥塞和不同前缀命中率下测量阶段能力，比较简单速率匹配与在线压力指标。
- 注入 decode 故障和配比重建，记录正在输出请求的终止、重试、恢复时延与额外资源。
