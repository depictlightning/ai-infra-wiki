# Vidur：大模型推理系统的大规模模拟框架（MLSys 2024）

> **原题**：Vidur: A Large-Scale Simulation Framework for LLM Inference

> **一句话总结**：Vidur 用算子实测画像、运行时间预测和分层离散事件调度重现推理过程，再搜索模型、负载与硬件组合下的部署配置；模拟精度受画像覆盖、工作负载及接近饱和时的排队误差影响。[^paper]

**阅读状态**：依据 MLSys 2024 论文全文，回看架构图 2、静态评测图 3 及动态评测图 4；没有运行模拟器或复现实验。论文描述的是 2024 年版本，当前代码能力需另行核对。[^paper]

## 问题与动机

部署一个 LLM 服务需要决定 GPU 类型、张量并行（TP）、流水线并行（PP）、副本数、批量和调度策略。用真实 GPU 穷举这些组合，既昂贵又慢；而只测单个 batch 的算子时间，无法直接得到动态请求到达后的排队、批次变化和尾延迟。[^paper]

Vidur 试图回答的是条件明确的反事实问题：**如果使用某组硬件、模型和调度参数处理这条请求轨迹，延迟、吞吐和资源消耗可能是多少？** 它不生成模型回答，也不评估输出质量；它模拟影响执行时间与资源分配的事件。[^paper]

## 关键观察 / 隐含假设

- **迭代不是固定耗时。** 不同请求的输入长度、已生成长度和批组成不断改变，prefill 与 decode 的运算特征也不同；固定平均迭代时间很难表达这些变化（§3）。[^paper]
- **局部误差会改变后续调度。** 一次迭代预测快慢不同，会改变此后哪些请求进入批次、何时释放 KV；接近容量时，轻微偏差可能把一个系统推入持续排队。模拟器不仅要估计算子，还需重现这些状态转移（§3、§7.2）。[^paper]
- **算子可以按依赖因素分类。** 论文将算子划为与本轮 token 数有关的 token 级算子、依赖序列长度的 attention、以及与数据量和拓扑有关的通信算子，以减少画像维度。该简化依赖所测模型、kernel 与并行实现，不是对所有新架构的保证（§4.1–4.3）。[^paper]

## 核心方法

### 从模型规格到可查询的耗时

首先输入模型的层数、隐藏维度、注意力头等规格。离线 profiler 按不同形状与 TP 切分测量算子；线性、归一化等主要依据本轮 token 数建模，attention 分别考虑 prefill 和 decode。通信操作独立按大小和拓扑画像，例如 all-reduce、all-gather 与流水线 send/recv（§4.2–4.3、图 2）。[^paper]

穷举所有批组合不可行。对于 prefill attention，论文用序列长度平方和构造等效预测输入；decode attention 近似由批中需读取的 KV 总量决定。对极端长度偏斜，该近似依赖所用 attention kernel 能较好地并行读取不同请求的 KV，换 kernel 后应重新验证（§4.3）。[^paper]

Runtime estimator 用实测数据训练随机森林回归，生成算子耗时查找表。其价值是以有限画像覆盖更多形状；它的输出依旧继承画像中的硬件、软件版本和测量噪声。未覆盖区域的泛化不能仅由训练集内精度证明（§4.4）。[^paper]

### 把预测值放进动态调度

Vidur 的事件模拟器包括三层：全局调度器把请求路由到副本；副本调度器决定批处理和 KV 内存分配；流水线阶段调度器安排微批次。用户给出请求到达、输入输出长度、硬件及策略后，模拟器推进请求、批次和阶段完成等事件，并输出请求和资源指标（§4.5、图 2）。[^paper]

例如，两个请求在不同时间到达：先到者的 prefill 进入批次；下一轮调度时，新请求可能与先前请求的 decode 同批。迭代耗时由当前批形状和查表结果决定；这个完成时间又影响下一批有哪些请求以及 KV 何时释放。这种反馈是平均吞吐公式遗漏的部分。[^paper]

论文中的策略包括 vLLM、Orca、FasterTransformer、Sarathi-Serve 与 LightLLM 的模拟实现；这是作者根据当时系统构建的策略模型，不意味着能够自动跟随这些系统之后的所有版本。论文当时的流水线阶段调度为同步策略（§4.5）。[^paper]

### Vidur-Bench 与 Vidur-Search

Vidur-Bench 整理不同输入、输出长度特征的数据集和请求到达方式，并记录 TTFT、token 间延迟、归一化端到端延迟、批量与 KV 使用等指标。轨迹包含的长度分布决定评测问题；数据集真实文本不等于到达时间也来自真实生产流量。[^paper]

Vidur-Search 枚举 GPU 类型、TP/PP、调度器等候选；对每个配置通过反复模拟、二分请求速率估计容量，论文以 P99 调度等待小于 5 秒作为容量搜索条件，并结合 TTFT/TBT 约束与成本筛选配置（§6）。这不是解析求出绝对最优：结果取决于候选空间、到达模型、阈值和预测误差。[^paper]

## 设计取舍

- **画像与搜索成本**：一次画像可供多组调度和负载复用，但更换设备、模型或算子实现需要额外校准；搜索时间不包含所有可能的模型接入成本。
- **抽象与保真度**：把批次压缩为算子输入特征减少状态空间，也可能遗漏长度偏斜、kernel 变体和重叠造成的性能差异。
- **速度与系统覆盖**：离散事件模拟能廉价扫描配置，但论文版本并未对后续各种分离部署、缓存分层、MoE 和硬件竞争建立完整实证，不应从本文推断当前仓库全部能力。

## 实验与结果

作者以扩展过的 vLLM 作为实际系统，使用 A100/H100、LLaMA2-7B/70B、InternLM-20B、Qwen-72B，以及 Chat-1M、Arxiv-4K、BWB-4K 三类长度分布。动态请求的到达由泊松过程生成，并非直接重放生产到达时间；长度受 LLaMA2 上下文限制截断至 4096（§7.1）。[^paper]

- **静态执行时间**：图 3 在四种模型、三种数据集下比较按输出 token 数归一化的执行时间；P95 最大绝对误差为 3.33%。静态实验把所有请求视为开始前到达，并排除排队等待，不能当成在线 P95 总延迟误差（§7.2）。[^paper]
- **动态延迟**：在各场景最大容量的 85% 到达率下，图 4 的归一化端到端延迟多数配置误差小于 5%；LLaMA2-7B 的中位数误差在 Arxiv-4K 上为 −8.50%。该指标是请求端到端时间除以输出长度，不是逐 token 的 TBT（图 4）。[^paper]
- **接近饱和**：附录在 95% 容量的测试中，LLaMA2-7B 最大误差达到 12.65%，作者将其与 CPU 开销相关的误差级联联系起来。摘要的“低于 9%”不能覆盖这一更高负载附录结果（附录 A.1）。[^paper]
- **配置搜索成本**：论文估计 LLaMA2-70B 一项搜索约需一小时 CPU 模拟，而逐配置实机探索预计约 4.2 万 GPU 小时；这是作者对穷举实机方案的成本估算，不是两套方案完整实际消耗的测量（摘要、附录表 2）。[^paper]

## 批判性分析

### 论证链条

作者没有只报告算子回归精度，而是把预测接入批次形成、排队和内存管理，并比较真实 vLLM 的请求延迟。这证明了模拟器在所测条件下可以用于配置探索；它没有证明未画像的硬件、不同运行时或新模型同样准确。图 3 排除排队，图 4 才覆盖动态等待，两者需要分开读。[^paper]

### 假设压力测试：配置选择比单点误差更难

即使两个候选配置各自的平均延迟误差不大，只要真实性能很接近，误差仍可能改变排序；在 SLO 阈值附近，误差还会改变可行与不可行的判断。论文展示搜索结果和模拟成本，但不能仅凭每点平均误差证明被选配置在现实中总是最优。[^paper]

### 实验可信度：与后续系统的关系

[[SarathiServe-OSDI24]] 使用 Vidur 辅助选择离线预算；[[Charon-MLSys26]] 与 [[LLMServingSim2-ISPASS26]] 在各自论文中将 Vidur 用作模拟对照。它们各自更新了模型和基线配置，不能把不同论文的误差数字直接排成通用精度榜。[^paper]

## 局限与后续工作

- 为目标 GPU、模型和推理框架版本重新画像，以真实运行轨迹校验 TTFT、逐 token 延迟、队列和 KV 占用。
- 对比低载、接近饱和与突发流量下的误差，并检查最优配置的排序是否稳定。
- 对分离部署显式验证 KV 传输、链路竞争和 P/D 队列反馈；论文版本不能直接作为完整验证。
- 追踪代码版本和数据集处理方法，复核新 kernel、长上下文、前缀缓存和 MoE 的覆盖情况。
