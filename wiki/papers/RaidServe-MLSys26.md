# RaidServe：GPU 故障后保持张量并行推理服务（MLSys 2026）

> **原题**：RaidServe: High-performance Resilient Serving

> **一句话总结**：RaidServe 在节点内 GPU 失效后，以非均匀张量并行继续服务，结合 KV 循环放置、混合 attention、负载感知调度和主机备份降低不均衡与恢复成本。[^paper]

**阅读状态**：已通读与会议正式 PDF 一致的 MinerU 全文，核对状态恢复图、消融图和恢复表；会议页面未列独立补充材料。[^paper]

## 问题与动机

张量并行（TP）把模型和 KV 分布在多张 GPU 上，一张卡故障会丢失其权重与请求 KV。恢复后如果只剩 7 张卡，常见仅支持 1、2、4、8 卡的配置可能退回 4 卡；即便允许 TP7，attention head 数量不能被 GPU 数整除，也可能造成显存和计算不均衡（§2）。[^paper]

论文同时处理两个问题：故障发生时如何恢复状态，以及恢复后如何让剩余 GPU 长时间高效工作。前者改善中断，后者改善故障后的稳态吞吐，不能把两项收益合成一个无条件加速比。[^paper]

## 关键观察 / 隐含假设

- **故障局限于节点内部分 GPU**：剩余 GPU、主机内存和 NVLink 仍可用；不覆盖整个节点掉电或驱动故障导致所有 GPU 无法运行（§4.1、§6）。[^paper]
- **剩余设备能容纳模型与请求状态**：论文中 LLaMA-3.1-70B 至少需 3 张 GPU，Mixtral-8x22B 至少需 5 张；失败过多后无法继续使用同一部署（§4.1）。[^paper]
- **主机备份可用**：运行时异步把请求 KV 复制到主机，权重也保存在主机；容量、PCIe 带宽及备份完成时机都会影响效果（§3.2）。[^paper]
- **通信拓扑有利于迁移**：方案用 NVLink 搬运 GPU 间状态、PCIe 从主机恢复，其他互连或跨节点场景需重新测量。[^paper]

## 核心方法

### 循环放置：均衡跨层 KV 占用

当 attention head 数不能整除存活 GPU 数时，朴素放置可能让同一 GPU 在每层都承担多出的 head。RaidServe 按层循环改变多余 head 与 KV 的放置位置，使各层累积显存占用更均衡。它改善跨层容量，但单层内部仍可能有部分 GPU 等待其他 GPU（§3.1、图 1）。[^paper]

### 混合 attention：处理单层计算长尾

系统将可均匀划分的 head 按 TP 分配；剩余 head 的权重复制到各 GPU，再按请求以数据并行方式分担计算。以 8 个 KV head 和 7 张 GPU 为例，7 个 head 分别分给 7 张卡，剩余 head 的请求计算分布到各卡；实际收益仍受批量、请求长度和额外通信影响（§3.1、图 2）。[^paper]

### 按负载路由和分块

新请求分配给预计剩余工作量较小的 DP rank；prefill 根据 token 预算和各 rank 的预计计算量组织批次，尽量避免一个长请求让某张卡成为同步瓶颈。负载估计是近似值，不能保证动态工作负载完全均衡（§3.1、算法 1）。[^paper]

### 主机 KV 备份与按需恢复权重

运行时异步、增量地把活跃请求 KV 备份到主机。故障后保留幸存 GPU 上仍有效的状态，只从主机取回丢失部分，并按新的布局进行 GPU 间迁移。FFN 权重先按固定小分片管理，故障后尽量保留原有分片，仅分配和加载丢失分片；attention 权重也由幸存 GPU 分担读取并交换（§3.2、图 4）。[^paper]

图 4 显示 GPU 3 故障后幸存的是 GPU 0–2，丢失的 FFN 分片 9–11 分别分配给它们。正文对应示例却写成保留 GPU 1–3 并重新分配 0–2，与图示不一致；这里按图解释设计，不将该示例当成严格实现证明。[^paper]

## 设计取舍

- **恢复速度与常态成本**：提前备份减少故障后重算，但占用主机内存和后台传输带宽；若故障发生时最新备份尚未完成，还需确保状态一致性。
- **复制与利用率**：复制额外 head 权重可分散计算，却增加驻留与通信；小批次或极端负载下可能无法充分并行。
- **细粒度恢复与复杂度**：保留幸存分片可减少重新读取，但要求恢复后的权重、KV 布局与并行计算保持一致。

## 实验与结果

实验平台为 8×H100 80 GB 单机、NVLink 和 PCIe 5.0；模型为 LLaMA-3.1-70B 与 Mixtral-8x22B，系统采用作者实现的轻量推理引擎（§4）。[^paper]

| 结果 | 实验条件与边界 |
|---|---|
| 模拟故障下离线吞吐 | 将云可用性轨迹缩放到 64 张 GPU，并用一台 8 卡机器模拟 8 个独立节点；相比标准 TP，LLaMA 和 Mixtral 的平均吞吐分别为 1.28× 和 1.71×。每次重配置时间对所有系统固定为 10 秒。 |
| 故障后稳态 | Mooncake 轨迹、LLaMA、7 卡配置下，在 10 秒 TTFT 约束的 prefill 和 40 ms TBT 约束的 decode 中，相比退回 4 卡的标准 TP 均最高约 2×；这是固定剩余 GPU 数下的性能曲线。 |
| 恢复阶段 | 表 3 中重算为 22 秒，主机 KV 备份方案为 530 ms，结合按需权重恢复为 120 ms，理想 oracle 为 15 ms；22 秒 / 120 ms 约 183×。这是论文测量的 GPU 状态恢复，不代表完整故障检测、重配置和服务恢复时间。 |
| 请求尾延迟 | 500 请求 Mooncake 片段中注入一次故障；按需恢复使每请求最大 TBT 的 P99 从主机备份方案的 572 ms 降至 229 ms（§4.3.3）。 |
| 均衡消融 | 图 12 的 decode 吞吐相对 TP4：非均匀 TP7 为 1.29×、加内存均衡为 1.63×、再加计算均衡为 2.06×。两次增量分别是 TP4 基线的 0.34× 和 0.43×，不是相对前一阶段分别提升 34% 和 43%。 |

论文正文以“34%”“43%”描述图 12 的两步增量，但图中数值是统一相对 TP4 归一化；按前一阶段计算的相对提升约为 26% 和 26%，需区分百分比与基线归一化增量。[^paper]

## 批判性分析

### 论证链条

论文将短暂恢复和长期不均衡拆开，分别用状态恢复表、请求尾延迟与稳态吞吐曲线验证。模拟多个节点的实验实际复用一台 8 卡机器，且固定重配置开销；它不能直接证明跨节点并发故障下的集群表现。[^paper]

### 假设压力测试

主机内存不足、PCIe 饱和、备份滞后或第二次故障发生在恢复期间，都会改变恢复时间和正确性。复制 head 的收益还取决于请求规模、头数与活跃 GPU 数；论文未对所有组合给出保证。[^paper]

### 实验可信度

状态恢复与实际用户看到的最长 token 间隔均有报告，但后者使用一段 500 请求轨迹和单次注入场景。需要进一步测量正常运行时备份造成的吞吐、主机内存、能耗及连续故障影响。[^paper]
