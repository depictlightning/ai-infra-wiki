# 跨层共享 KV cache 的混合稀疏注意力（arXiv 2026）

> **原题**：HySparse: A Hybrid Sparse Attention Architecture with Oracle Token Selection and KV Cache Sharing

> **一句话总结**：HySparse 让少数完整注意力层给后续稀疏层提供重要块索引和 KV cache，同时给稀疏层保留独立的局部滑窗分支；80B MoE 模型的 49 层中仅 5 层使用完整注意力，在 32K RULER 上得到 87.4 分，高于全注意力的 82.1 分和 Hybrid SWA 的 69.5 分，但论文没有测量服务吞吐或延迟（表 1、表 3）。

**版本与证据**：依据 [arXiv:2602.03560v1](https://arxiv.org/abs/2602.03560) 的 17 页全文。本文是模型架构与预训练实验，不是已经发表的会议论文，也没有提供线上推理系统的性能实验。

## 问题与动机

动态稀疏注意力只读取每步选中的历史 token，降低注意力计算量；如果未来生成的 token 可能重新选中当前未读的历史位置，系统仍要保存完整 KV cache。另一条路线是用专门的索引器或近似评分器先选 token，但索引器本身需要训练和执行，选错的 token 也无法参加后续注意力（§1、§2.1）。

HySparse 从模型结构入手：每组先安排一层完整注意力，再跟若干层稀疏注意力。完整层既看到了全部历史位置，也已经生成了 KV；后续层使用它给出的重要块索引和 KV。这让稀疏分支减少自己的长期缓存，同时保留跨长距离检索的机会（图 1、§3.1）。

## 关键观察 / 隐含假设

- **跨层沿用选中位置**：论文援引既有研究中相邻层显著 token 较稳定的观察，据此让完整层的 TopK 块索引服务后续多层（§2.3）。本文没有直接报告索引在后续层的命中率；1:11 的大跨度能否适用于其他模型与任务，主要靠端到端模型质量间接支持。
- **共享 KV 的范围需要受限**：跨层共享可减少每层重复存储；表 4 显示，稀疏分支共享完整层 KV、滑窗分支保留自己的 KV 时，7B 模型 MMLU-Pro 为 29.0，而两条分支都共享时为 23.2。这说明局部表示不能简单由完整层 KV 代替，但实验没有分离所有训练动态与门控作用。
- **必须重新训练模型**：HySparse 改变了层结构、QKV 投影与门控，实验模型均按新架构训练（§3、§4.1）。因此结果不能直接外推为已有全注意力模型的无训练部署优化。

## 核心方法

**混合层组**：7B dense 模型有 36 层，完整层与稀疏层比例为 1:3；80B-A3B MoE 模型有 49 层，比例为 1:11。两者最后一层都是完整注意力，80B 因而共有 5 层完整注意力（表 1、§4.1）。

**重要块选择**：完整层在 FlashAttention 的分块计算中额外输出每个键块的最大注意力分数，不落盘完整的 token 对 token 分数矩阵。每块 64 token，默认选出总计 1024 token 对应的块；同一 GQA 组的头共享选择结果。后续稀疏层复用这些块索引（算法 1、§3.2）。这里的“oracle”是前一完整层的真实注意力分数，仍只是**后续层**重要位置的跨层代理。

**两条注意力分支**：稀疏分支用自身 query 读取前一完整层共享的 KV，只访问选中块；局部滑窗分支使用 128-token 窗口，另存自己的少量 KV。两个输出分别经 sigmoid 门控后相加（图 1、式 4–9）。独立滑窗分支回应表 4 中“全共享会损害局部建模”的现象。

## 设计取舍

- **减少完整层数量，保留少数全局扫描**：每组的完整层仍对全部历史做注意力；后续层的全局稀疏分支依赖这层产出的索引。因此计算和缓存收益随层组比例变化，无法从本文推断完全取消完整层后的表现。
- **共享全局 KV，另存局部 KV**：与全注意力架构相比，80B 的完整层数从 49 降到 5，论文据此给出接近 10 倍的 KV cache 节省；与相同比例的 Hybrid SWA 相比，KV cache 成本基本相同。局部滑窗缓存、块索引和评分输出也有开销，论文没有给出完整 HBM 占用分解（§1、§3、表 1）。
- **用预训练换部署时的结构收益**：该方案可以在模型架构阶段联合学习索引复用和门控，却需要训练新模型；论文没有验证对已发布模型的迁移成本。

### “约 10 倍”究竟省了什么

按表 1 的 80B 配置做一个**本站推算**。假设每个完整层都为全部 `L` 个 token 保存 KV，每个稀疏层只为自身的 128-token 滑窗保存 KV，且各层 KV 宽度相同，则全注意力与 HySparse 的长期缓存条目数之比为 `49L / (5L + 44×min(L,128))`。这个式子没有计入块索引、临时分数、分配器和模型权重。

| 上下文长度 `L` | 按上述假设估算的长期 KV 条目减少倍数 |
|---|---:|
| 128 | 1.0 倍 |
| 1,024 | 约 4.7 倍 |
| 16,384 | 约 9.2 倍 |
| 32,768 | 约 9.5 倍 |

上下文越长，比例越接近 `49/5 = 9.8`。因此论文的“接近 10 倍”是长上下文下相对 **49 层全注意力**的结构性 KV 容量比较；它不表示相对 Hybrid SWA 也再省 10 倍，更不等于进程 HBM 峰值或吞吐改善 10 倍。按相同简化口径，32K decode 每个 token 访问的键位置数约从 `49×32,768` 降到 `5×32,768 + 44×(1,024+128)`，约为 7.5 倍差距；实际时间还受块索引生成、稀疏访存和 kernel 效率影响，论文没有测量。

## 实验与结果

- 7B dense 的基础训练使用 1T token、8K 序列，长上下文阶段另用 200B token、32K 序列；80B-A3B MoE 使用 500B token、32K 序列。三种对照架构是 Full-Attn、相同完整层比例的 Hybrid SWA 与 HySparse（§4.1、表 1）。
- 在 7B 模型上，HySparse 的 MMLU 为 58.8，Full-Attn 为 56.9，Hybrid SWA 为 57.5；但 BBH 为 53.5，低于 Hybrid SWA 的 54.0。80B 上，MMLU 为 62.2、61.8、54.9；DROP 为 56.5、56.7、47.8，HySparse 并非每项都超过全注意力（表 2）。
- 32K RULER 总分：7B 为 HySparse 89.3、Full-Attn 88.2、Hybrid SWA 84.2；80B 分别为 87.4、82.1、69.5。80B 的 HySparse 比全注意力高 5.3 分，约为 6.5% 的相对增幅；16K 总分则是 90.6、93.6、72.7，说明“超过全注意力”取决于上下文长度与任务（表 3）。
- 消融只在 7B 上进行：加入独立滑窗分支后，DROP 从 46.4 升至 52.2、GSM8K 从 29.7 升至 37.7；仅让稀疏分支共享 KV 而让滑窗分支独立，MMLU-Pro 从双分支共享的 23.2 升至 29.0（表 4）。

## 批判性分析

**论证链条**：消融支持“全局稀疏读取应共享 KV、局部滑窗应独立”的设计选择；表 2–3 支持模型质量在所测 7B 和 80B 规模上维持或改善。作者没有直接测量跨层索引与各后续层真实重要位置的重合度，因此“完整层是 oracle”更准确地说是设计动机，而非逐层选择正确性的证明。

**“Oracle”的两层含义**：完整层对自己的 query 确实计算了全注意力分数，无须额外学习索引器。但稀疏层有自己的 query 和隐藏状态，沿用前一层的块索引只是跨层预测；相隔 11 层时预测偏差可能扩大。此外，算法按块内**最大**注意力值排序，某块只有一个极高分 token 也可能压过整体贡献较大的块。表 2–3 说明这种选择在已测任务上可用，尚不能说明它覆盖了每层的真实注意力质量。可离线计算后续层对全部共享 KV 的反事实分数，按层距报告所选块覆盖的注意力质量，再比较最大值、块总量和混合评分。

**表示共享的另一面**：44 个稀疏层虽然各自生成 query，却反复读取组首完整层产生的全局 K/V。后续层无法通过自己的全局 K/V 投影改变历史 token 的表示，只能靠 query、滑窗分支和门控适配。这解释了为什么独立的局部 K/V 可能特别重要，也提示应比较“共享索引但不共享全局 KV”与“索引和 KV 都共享”在不同层距上的能力。当前表 4 没有把这两个因素在 80B 配置中分别测量。

**系统证据边界**：论文没有展示 GPU kernel 耗时、索引生成与存储开销、完整 HBM 使用量、batch 上限、吞吐或尾延迟。完整层的块级评分输出随 query 数和历史块数增长；长 prefill 若落盘整张评分矩阵，临时空间仍随 `L²/64` 增长。稀疏层还要读取非连续 KV。这些开销是否被注意力计算节省覆盖，须在实际推理引擎里测量。第 5 节提出把完整层 KV 卸载到外存，但这只是后续方向，没有实验。

**收益会转移瓶颈**：稀疏层仍计算供局部窗口使用的 K/V 投影，长期缓存减少不等于投影计算等比例减少。完整层需要扫描长上下文并产出块索引；推理服务若改用更大 batch，其瓶颈可能从 KV 容量移到这些完整层的计算、块索引整理或稀疏读取。应同时测 prefill、decode 和端到端请求，而非只报告缓存条目数。

**对照限制**：同完整层比例的 Hybrid SWA 是比较“增加稀疏全局检索能否恢复能力”的合适基线；全注意力基线在 80B 配置中另用了 gated attention 来稳定训练（§4.1），结构并非只差稀疏化。表 4 比较的是滑窗分支和 KV 共享范围，没有在相同预算下对比其他块选择器，因此单独的“oracle 选择”收益仍未隔离。让滑窗分支保留独立 KV 也改变了可学习的局部 K/V 表示，可能同时改变参数与训练自由度；分数提升无法只归因于缓存摆放。RULER 属于合成的长上下文能力测试，最长只到 32K；它不能替代多轮 Agent 请求、长输出或线上负载评估。

## 局限与后续工作

- 在相同模型与硬件上测量完整层评分输出、TopK、稀疏读取及门控的端到端耗时，同时报告 prefill、decode、HBM 峰值与并发上限；再与相同 KV 预算的 Hybrid SWA 比较。
- 测量 1:3、1:11 及更大层组内的选择重合率，区分全局检索收益来自更准确的块索引、独立局部 KV，还是训练结构本身。
- 在固定完整层比例、训练 token 和缓存预算下，加入“每个稀疏层自行重算 TopK”“继承完整层 TopK”“随机块”三组对照，并按与完整层的距离报告选择召回率；这样才能检验跨层选择的有效范围。
- 在更长上下文和长时间生成中验证索引稳定性；若跨层漂移增加，尝试缩短层组或让部分层更新索引。
