# BatchLLM：面向离线大批量推理的前缀共享与调度（MLSys 2026）

> **原题**：BatchLLM: Optimizing Large Batched LLM Inference with Global Prefix Sharing and Throughput-oriented Token Batching

> **一句话总结**：离线任务通常能预先看到大量提示，BatchLLM 先识别共享前缀、按组重排请求，再按 KV 显存预算混合预填充与解码；在一个搜索摘要生成负载中，相比启用前缀缓存和分块预填充的 vLLM，A100 上吞吐从 6.71 增至 8.67 请求/秒（§4.2.2、表 1）。[^paper]

## 问题与动机

大批量信息处理常以整批吞吐为目标。例如多个查询需要针对同一网页生成摘要时，提示包含重复的长文档前缀。在线服务的 LRU 前缀缓存能复用已出现的内容，但不知道完整批次后面有哪些请求，可能在下一次复用之前提前淘汰缓存（§2）。[^paper]

论文测得某工业负载的理论前缀 token 节省率为 58.1%，vLLM 隐式缓存达到 35.8%；差距来自所测输入顺序和缓存条件，不能直接推广到已经按前缀排序的所有任务（§2.2）。[^paper]

## 关键观察 / 隐含假设

- **请求可以提前汇总和重排**：批次越完整，系统越能识别跨请求共享内容；实时到达且有严格单请求时延约束的任务不一定允许这样等待（§3、§4.4）。[^paper]
- **共享内容集中在一个较长前缀**：将多级前缀简化为单级可减少依赖管理与内核开销，但在共享结构更加分散的负载上可能放弃更多复用（§3.2）。[^paper]
- **同类任务输出长度相对集中**：作者将未知的解码长度统一近似，以输入长度对请求组排序；输出重尾或任务类型混合会削弱该近似（§3.3.2）。[^paper]

## 核心方法

### 先找前缀，再组织请求组

BatchLLM 在执行前构建紧凑前缀树，并以动态规划比较把子前缀并入父组的收益和代价，尽量扩大第一层共享前缀。具有同一共享前缀的请求成为一个调度组；组完成后可更早释放公共 KV。该方案并未完全取消 LRU：主要共享前缀显式管理，其他可能重复的子前缀仍由 vLLM 缓存机制处理（§3.2–3.3.1、图 3–4）。[^paper]

### 重排、混合与内核融合

系统优先调度预估解码占比较高的组，让其后续 decode 与其他组的 prefill 块重叠。论文在同类任务中将未知输出长度近似为常数，因而实际上主要依据组输入长度排序。调度器优先处理已开始请求的解码和独有提示，并在内存预算允许时加入新的预填充块；仍保留每批 token 上限（§3.3.2–3.3.3）。[^paper]

注意力内核把共享前缀和各请求独有部分的计算横向融合，并分别选择分块配置，以减少多个内核的启动和尾部开销（§4.3.3）。[^paper]

## 设计取舍

- **全局复用换等待和预处理**：先看完整批次有助于合并前缀，但可能增加单请求等待，不适合直接替代低延迟在线调度。
- **单级前缀换系统简单**：减少多层管理，但某些多级共享机会无法通过显式主前缀覆盖。
- **吞吐调度换预测误差**：固定输出长度的近似并不掌握实际生成长度；输出重尾会改变混批效果和资源占用。
- **更多并发换显存压力**：按 KV 预算决定批次，而非简单提高请求数上限，但预算失准仍可能造成换入或重算。

## 实验与结果

系统基于 vLLM 0.6.4 实现；对照启用前缀缓存与分块预填充，硬件包括 A100 80 GB、双 A100 张量并行和 AMD MI200。论文另在工业负载上对比了截至 2026-01-16 的较新 vLLM 代码（§4.1–4.2）。[^paper]

| 结果 | 条件与基线 |
|---|---|
| 8.67 对 6.71 请求/秒 | A100、微调 Qwen-2.5-7B、8000 条搜索摘要请求，较最佳 vLLM 0.6.4 配置约快 1.30 倍；MI200 为 4.24 对 3.36，约 1.26 倍（§4.2.2、表 1）。 |
| 最高 10.8 倍 | Llama-3.1-8B、共享前缀 16000 token、共享度 16 的微基准对照 vLLM；不能当作工业负载的代表速度（§4.2.1、图 7）。 |
| 简单按前缀排序本身有帮助 | 一组微基准中 vLLM 吞吐从 6 提高到 13.02，BatchLLM 为 18；需与未排序基线区分（§4.2.1）。 |
| 重尾输出 17.02 对 5.26 请求/秒 | 320 条合成请求、每组 16 条共享 2000 token 前缀，输出长度按有界 Pareto 分布生成；对照 vLLM，约 3.2 倍（§4.2.3、表 2）。 |
| 完整前缀预处理 1.51 秒 | 工业负载 8000 条请求，作者报告后续执行约 919.54 秒；这一完整预处理计时与文中单独报告的动态规划开销不是同一计时范围（§4.3.1）。 |

## 批判性分析

### 论证链条

论文将收益分为全局前缀识别、调度混批和注意力融合，并提供各自消融；工业任务的增益小于共享度很高的微基准最大值。比较时应同时记录前缀长度、共享度、输入顺序和基线版本。[^paper]

### 假设压力测试

多租户前缀共享会带来隔离和授权要求；论文的全局分组策略是否适用于这些部署，需要另行验证。输出长度跨任务差异大时，统一近似可能影响重排效果，重尾合成实验虽显示整体收益，不能单独证明重排策略在所有长尾下最优。[^paper]

### 实验可信度

作者对比了旧版及一个较新 vLLM 版本，并给出真实任务样本和合成压力测试；工业数据分布、前缀相似度和离线任务提交方式仍决定可迁移性。最新 vLLM 的对照仅覆盖论文所述工业负载，不能据此断定所有新版本和配置均有相同差距。[^paper]

### 系统性缺陷

全局前缀树、显式组及融合内核增加实现复杂度。论文明确指出单请求延迟可能恶化；在线与离线模式动态切换只被提出为后续工作。[^paper]

## 局限与后续工作

- 在混合任务与不同共享度下，测量批次等待、完工时间、吞吐和用户级尾延迟。
- 固定同一引擎版本，逐项比较原始顺序、前缀排序、全局分组和融合内核的贡献。
