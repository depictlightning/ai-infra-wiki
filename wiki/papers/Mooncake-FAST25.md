# Mooncake：以共享 KV cache 支撑分离式推理服务（FAST 2025）

> **原题**：Mooncake: Trading More Storage for Less Computation — A KVCache-centric Architecture for Serving LLM Chatbot

> **一句话总结**：Mooncake 将 P/D 分离与跨节点 KV cache 池结合，利用缓存感知调度减少重复计算；在工具与智能体轨迹、200 ms TBT 门槛下，有效请求占比相对启用前缀缓存的 vLLM 提高 42%（§5.2.2）。[^paper]

**阅读范围**：MinerU Flash 已解析会议论文全文，但未导出图像；已另行回看原 PDF 图 1–15、公式、调度算法和工作负载表。本文报告的是论文中的系统版本及作者实验，未运行代码或复现生产环境。[^paper]

## 问题与动机

长上下文和多轮交互可能反复使用共同前缀。只用单机缓存会受容量和请求路由影响；但跨机读取旧 KV 也消耗网络。Mooncake 同时安排计算阶段和缓存位置，以满足 TTFT、TBT 目标。

## 关键观察 / 隐含假设

- **观察 1：单节点缓存可能装不下工作负载的可复用历史。** 图 9 中，约 300 万 token 容量在多数所测轨迹上达不到理论最大命中率的一半；工具与智能体轨迹则有不同分布。该分析仅模拟请求顺序，不计计算时间和热点复制（§5.3.1）。[^paper]
  - **依赖假设**：请求确实反复使用相同前缀，且其他节点有足够容量保存这些块。若前缀很少重复或副本占据大量空间，共享容量不一定换来相应命中提升。
- **观察 2：取回命中 KV 需要足够快的传输路径。** LLaMA3-70B、8192 token 前缀的简化模型给出 8×A800 约 6 GB/s、8×H800 约 19 GB/s 的加载带宽条件；图 13 的合成负载在低带宽时出现明显拥塞（§2.2、§5.4.2）。[^paper]
  - **依赖假设**：数据传输、计算和网络拥塞接近模型设定，加载时间小于省去的计算时间。不同模型、前缀长度和多租户流量会改变交叉点；理论阈值也不自动保证实际 TTFT。
- **观察 3：最长本地命中与最低排队时间可能分布在不同节点。** 对话轨迹中，全局缓存感知调度的平均 TTFT 为 3.07 秒，本地缓存感知为 3.58 秒（图 5、§4.2）。[^paper]
  - **依赖假设**：缓存位置、队列、prefill 与远端传输时间能够足够准确地估计。热点迁移和副本会占网络与容量；负载快速变化时，预测最短的实例未必实际最短。
- **观察 4：P/D 资源配比会同时改变两阶段等待。** 图 15 的 16 节点合成实验中，增加 prefill 节点使平均 TTFT 降低，但 decode 的 TBT 上升；最高有效请求占比出现在约 1:1 附近（§5.5）。[^paper]
  - **依赖假设**：输入／输出长度分布、SLO、负载及硬件与实验相近。突发请求或另一种前缀复用率下，需要重新测量最佳配比。

### 什么时候取回前缀比重算划算

设输入长 $n$、可复用前缀长 $p$，模型有 $L$ 层，隐藏维度为 $d$。论文用 $L(an^2d+bnd^2)$ 近似 prefill 的浮点运算量，其中常数 $a,b$ 由模型结构决定。复用前缀约省下 $L(ap^2d+bpd^2)$ 的计算，但需要加载约 $pL(2d/\mathrm{gqa})s$ 字节的 KV；$\mathrm{gqa}$ 是查询头与 KV 头的分组比，$s$ 是每元素字节数（§2.2、式 1–2）。[^paper]

令平均计算吞吐为 $G$、有效 KV 加载带宽为 $B$，论文比较上述两个成本，得到复用有利的近似条件：

$$
\frac{B}{G}>\frac{2ds}{\mathrm{gqa}(apd+bd^2)}.
$$

这个表达式说明：需要同时看**省去的计算量**和**实际可用的搬运带宽**，不能只看命中率。论文以 LLaMA3-70B、8192 token 前缀为例，估算 8×A800 需要约 6 GB/s、8×H800 需要约 19 GB/s；这是简化条件下的模型结果。实际流水线未必完全重叠，排队和网络拥塞也会抬高要求，数字不能直接作为其他模型或集群的门槛。[^paper]

## 核心方法

全局调度器为请求选择 prefill 与 decode 实例。Mooncake Store 汇集节点的 CPU 内存与 SSD 存储 KV，并以拓扑感知传输引擎跨节点取回；调度器兼顾缓存位置和负载，复制热点块（§3–4）。prefill 按块和层发送新 KV 给 decode，长输入还可利用分块流水线并行。旧 KV 的外部读取与 P/D 交接是两类不同数据流，[[DualPath-SIGCOMM26]] 进一步讨论前者的网卡瓶颈。

### 一条请求经过哪些位置

Conductor 在请求进入后选择 prefill 和 decode 节点：先根据块键寻找可复用前缀，将命中的旧 KV 装入 prefill 侧；然后只对新增 token 执行 prefill。prefill 侧的 KV 按层异步发送到 decode 节点的 CPU 内存，与后续 prefill 计算重叠；完整 KV 到达后，请求加入 decode 的连续批处理（§3.1、图 3）。没有命中时会跳过旧 KV 加载，但仍要完成 KV 的阶段交接；发生前缀复用时，decode 也需要能访问构成完整上下文的旧 KV。[^paper]

这里有两个不同的网络动作：旧 KV 从共享缓存池读回 prefill，新的请求状态从 prefill 发往 decode。前者能省计算，后者服务于阶段交接；测量时应分别统计字节、排队和可见等待。[^paper]

### 缓存如何组织和淘汰

Store 将 KV 分成分页块，键同时包含当前块内容及其前缀信息，以便识别可复用前缀；热点块可有多个副本。缓存池满时采用 LRU，正在被请求访问的块不会作为淘汰对象（§3.2.1）。块大小与模型及传输粒度有关，实验设置为 256 token；块过小会增加元数据和传输操作，过大则可能减少部分前缀的复用机会。最后一句是基于设计的推断，需要实测。[^paper]

把前缀信息纳入块键，是因为同样的 token 出现在不同历史后面时，其 KV 可能不同。Store 维护块键到内存位置的元数据，对外提供 `put`、`get`、`change_replica` 等对象接口；下层先注册本地内存，再提交批量传输并查询完成状态。接口允许 DRAM 和 GPU 显存之间的路径，并在合适时使用 GPUDirect RDMA；这不意味着所有请求都绕过主机或都使用同一种链路（§3.2.1–3.2.2）。[^paper]

传输引擎根据源、目的内存的 NUMA 和 PCIe 拓扑选择本地或远端网卡，把一次传输切成 16 KB 的片以使用多条路径。连接按需建立并受连接池大小约束；检测到临时网卡或链路问题时，系统尝试其他可达路径（§3.2.3）。这些机制减少单路径瓶颈，但网络重试不能代替完整节点故障恢复。[^paper]

### 路由为何不能只追求最长前缀

对于每个 prefill 候选，调度器估计排队、剩余 prefill 和可能的缓存传输时间，选择预测 TTFT 最短的实例；若估计无法达到 SLO，则提前返回 HTTP 429（§4.1–4.2）。短队列可能比最长本地命中更有价值。热门前缀被其他实例取回后会形成副本，进而分散后续请求，但预测误差与链路拥塞会改变实际收益。[^paper]

算法 1 的具体过程是：先计算请求各块的前缀键并查找全局最长匹配；对每个候选实例，比较全局匹配长度和本地匹配长度。超过缓存均衡阈值时，将远端可补齐的部分计入传输；否则保留本地命中、重算余下部分。候选的预测 TTFT 为传输、排队和 prefill 估计时间之和，其中 prefill 时间来自离线数据拟合；选择最小值后还要挑选 decode 节点，检查 TTFT 与 TBT 约束。若预测无法同时满足要求，则拒绝该请求（§4.1–4.2、算法 1）。[^paper]

请求被导向原本没有热点的实例后，远端块的读取也可能在该实例产生新副本。这样后续请求不必全部排到同一个持有者或同一条链路，但副本会挤占其他缓存容量。论文用启发式阈值和实际请求触发迁移，没有证明未来热点可预测，也没有在伪代码中充分展开本地命中为零等实现细节。图 5 的对话轨迹实验中，全局缓存感知调度的平均 TTFT 为 3.07 秒，本地缓存感知为 3.58 秒，约下降 14%；该结果仍包括负载和工作负载条件（§4.2、图 5）。[^paper]

### 长输入的流水线

Mooncake 将多个 prefill 节点组织为流水线组，长输入切成块，由不同节点处理不同层组；节点间主要在流水线边界传递状态。论文选择此方式以避免跨节点 TP 在每层进行频繁集合通信（§3.3）。多个块在依赖允许时重叠，收益取决于块数、流水线填充及网络竞争，不能简单视作节点数倍加速。[^paper]

更大的共享缓存用内存、网络与副本维护换取较少重复计算；热点复制缓解读取拥塞，也占用容量。P/D 分离允许单独配置资源，但需要匹配阶段比例。

## 设计取舍

- **集中共享容量与分布式传输**：共享池可复用其他节点的历史，代价是缓存位置查询、远端带宽和潜在拥塞。
- **多副本与有效容量**：热点副本增加并发读取能力，但副本越多，能够容纳的不同前缀可能越少。
- **缓存命中与排队时间**：最长前缀不一定对应最低 TTFT；远端取回也可能不如就近重算。
- **P/D 分离与交接**：两阶段各自优化批次和资源，但 KV 交接和资源配比成为新的约束。

## 实验与结果

- 重现实验使用 LLaMA3-70B 架构的 dummy 模型、16 个八卡 A800 节点；对比 vLLM 0.5.1 及单独启用前缀缓存或分块预填充的配置（§5.1–5.2）。两项 vLLM 功能未同时启用。
- 工具与智能体轨迹在 200 ms TBT 门槛下，图 6 的有效请求占比相对前缀缓存 vLLM 提高 42%；TBT 定义为最长 10% token 间隔的平均值（§5.1、§5.2.2）。这不是吞吐量提高 42%。
- 10 个 prefill 节点的隔离实验中，全局缓存相对本地缓存命中率最高增加 136%，prefill GPU 时间最高减少 48%；输出固定为 1 token（§5.3.2、图 10）。
- 16 节点合成负载的比例实验中，约 1:1 的 P/D 比例得到最高有效请求容量；该比例不应推广到其他负载（§5.5、图 15）。

### 工作负载和指标

论文表 2 的对话、工具与智能体、合成工作负载平均输入分别为 12035、8596、15325 token，平均输出分别为 343、182、149 token；对应前缀缓存比例为 40%、59%、66%。前两者来自 Kimi 各一小时轨迹并使用原始到达时间，合成负载组合公开数据集并使用泊松到达（§5.2.1）。缓存比例与最终缓存命中率不是同一个量：位置、容量和淘汰策略都会影响实际命中。[^paper]

§5.1 将有效请求定义为同时满足 TTFT 与 TBT 门槛的请求，并把其占比称为有效请求容量；相关图的纵轴是请求比例。论文也讨论服务最大吞吐，阅读时应结合图轴，不能把某个阈值下占比增长直接说成同等幅度的最大请求速率增长。[^paper]

## 批判性分析

### 论证链条

容量分析、缓存隔离实验和端到端比较分别支持共享缓存的动机与作用；端到端差距同时包含调度、缓存和阶段分离，不能全部归因于单个组件。

### 假设压力测试

低前缀复用、共享链路拥塞、缓存热点变化或更小 KV 表示都可能改变收益；带宽门槛是特定实验条件的结果。

### 实验可信度

作者使用生产轨迹和合成负载；历史生产统计与 dummy 模型回放应分别看待。基线版本较旧且缓存和分块没有联合启用。

### 系统性缺陷

论文未充分量化大规模节点故障时缓存恢复、调度元数据一致性与拥塞尾部的成本。

## 局限与后续工作

- 固定模型与 GPU 预算，扫描前缀复用率、网络带宽与缓存容量，记录 TTFT 和网络排队。
- 对比不同动态 P/D 配比在突发流量下的恢复时间。
