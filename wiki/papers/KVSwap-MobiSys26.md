# KVSwap：面向端侧磁盘的分组 KV 卸载（MobiSys 2026）

> **原题**：KVSwap: Disk-aware KV Cache Offloading for Long-Context On-device Inference

> **一句话总结**：KVSwap 把完整 KV 放在磁盘，用低秩 Key 表示预测下一层需要的 token 组，并以组对齐读取、跨步复用和计算重叠减少端侧 I/O；其主要代价是对完整注意力做近似，紧内存和慢盘下部分任务的精度损失明显。[^paper]

**阅读状态与会议范围**：已取得 MobiSys 2026 正式论文 PDF 并阅读全文、核对部分原图；MinerU 转换待补，暂保留待复核状态。MobiSys 为 CCF B 类会议，此条作为端侧 SSD 卸载的补充，与本专题中 CCF A 工作明确区分。论文结论来自作者实验，未独立复现。[^paper]

## 问题与动机

长上下文推理中，KV cache 随请求长度和批次线性增长。论文以 Qwen3-4B 为例：权重约 7.5 GiB，16K context、batch 4 时 KV 已约 9 GiB；32K、batch 12 时约 54 GiB。端侧系统除总内存较小，还可能限制单应用可用内存，即使权重能放入设备，活跃请求的 KV 也可能放不下（§2.2、图 1）。[^paper]

服务器方案通常把 GPU KV 卸到 CPU 内存；端侧 CPU、GPU 或 NPU 可能共享受限内存，因此只在 CPU/GPU 之间移动不能增加总容量。KVSwap 使用磁盘作为完整 KV 的后备层，针对每步 decode 按需选择一部分回载。论文实测 NVMe 和 eMMC；作者明确说其实验平台不支持 UFS，因此对 UFS 的讨论不是 UFS 实测结果（§2.3、脚注 2）。[^paper]

## 关键观察 / 隐含假设

- **观察 1：细粒度随机读取不能发挥端侧磁盘带宽。** 所测 NVMe 峰值约 1.8 GB/s、eMMC 约 250 MB/s，而 512 B 读取的有效带宽低于各自峰值的 6%（§2.3、图 2）。[^paper]
  - **依赖假设**：相邻 token 可按组连续存放且组内至少有一部分值得读取。组太大虽然改善带宽利用率，也会读取更多无关 KV，增加误选并挤占有限缓冲。
- **观察 2：既有服务器卸载器在严格内存预算下可能连索引都放不下。** Llama3-8B、16K、batch 8 的例子里，InfiniGen 与 ShadowKV 的管理内存分别约 4 GiB 和 2.7 GiB（§2.4、图 3a）。[^paper]
  - **依赖假设**：压缩后的 Key 索引仍保留足够预测信息，且模型权重、临时缓冲和操作系统保留的内存已单独计入。管理内存降低并不说明全系统内存也按相同比例降低。
- **观察 3：相邻 decode 步骤选择的组有复用，但热门组并非固定不变。** Qwen3-8B/QMSum 的层 8、16、25 上，少于 22% 的组贡献 80% 的出现次数，相邻步骤又有较高重叠（§3.4.2、图 8）。[^paper]
  - **依赖假设**：预测出的工作集在相邻步骤足够稳定，FIFO 复用缓冲不会频繁被无关组替换。任务、层或生成阶段变化可能使缓存命中下降，慢盘尤其敏感。
- **观察 4：相邻层输入在较深层通常更相似。** 作者测得 Llama3-8B 前两层相邻隐藏状态余弦相似度仅约 25%、67%，更深层超过 90%，因此前两层用精确输入、之后用前一层输入提前预测（§6.1）。[^paper]
  - **依赖假设**：论文使用的相似性在目标模型和 workload 上仍成立；余弦相似不保证 top-k 顺序不变。预测错误既会引入无用读取，也可能让模型缺少重要历史 KV。
- **观察 5：更紧预算和更大组大小会恶化部分质量指标。** 表 2 中极紧预算的 eMMC 配置在 RULER 的 MQ、MV 子任务分别低于 Full-KV 54.3 和 55.8 个百分点；这比其 LongBench 平均下降 2.7 个百分点严重得多（§5.1、表 2）。[^paper]
  - **依赖假设**：部署方可以为目标任务选择可接受的内存、组大小和精度折中。平均分接近并不保证所有请求或关键子任务都可用。

## 核心方法

### 1. 磁盘保存完整数据，内存保存低秩索引

prefill 按层生成完整 KV 并写入磁盘，同时将 K 压缩为较小的预测表示留在内存。作者将多个 KV head 的 Key 拼成矩阵，通过离线样本 SVD 得到低秩投影矩阵 `A`，令 `K_low = flatten(K) A`。推理时投影查询并与低秩 Key 计算近似分数；这个压缩表示用于**选位置**，真正注意力使用从磁盘取回的原始 KV（§3.1–3.2）。[^paper]

离线 adapter 的一次性训练和样本获取仍有成本；“在线不做 SVD”不等于整体没有离线准备。低秩 Key 本身并非完整注意力需要的全部 Key：它漏掉或排错重要组时，后续 attention 不会自动看见未选中的磁盘数据。[^paper]

### 2. 将预测对齐到磁盘读取组

论文把连续 `G` 个 token 的全部 head KV 放在一起。预测时先将各 query head 的分数相加得到每个 token 的重要性，再取每组内的最大分数，以 top-k 选出组。一个组只要有重要 token 就可能整组读取；这可增加单次 I/O 大小，但组里其他 token 的搬运也是开销（§3.3、图 6）。[^paper]

当前层计算时，系统用前一层输入近似下一层输入，预测下一层组并提前发起 I/O；前两层改用精确输入以控制误差。需要区分**选择近似**和**调度重叠**：即使预取成功，未被组选择的 KV 仍不参与这次注意力；预取不是随后精确选择的无损补丁。[^paper]

### 3. 新生成 KV、复用缓冲与映射

滚动缓冲保存新生成 KV，直到它们积累成完整组后写入磁盘；这样新 token 在成组前仍能参与注意力。另一个复用缓冲保存从磁盘读取过的历史组，按 FIFO 替换。每步预测后先查 slot table，只对未命中组发起读取；逻辑映射把复用命中、新加载块和滚动缓冲组合成 attention 看到的 KV 视图（§3.4、图 7）。[^paper]

实现基于 FlexGen 扩展，使用 PagedAttention kernel、PyTorch 和 Linux `io_uring`，以少量 pinned CPU 内存暂存磁盘数据，并把 miss 批量搬到连续 GPU 空间。磁盘格式按组排列各 head 的 K/V；论文没有声称通用 SSD 无需经过主机就可直接由 GPU 读取。[^paper]

### 4. 离线选择组大小和内存分配

用户给出目标模型、最大上下文、最大 batch 和 KV 内存预算，离线贪心搜索组大小、Key 压缩比、选中组数和复用缓冲容量。作者报告所测调优在 30 分钟内完成，但它是启发式搜索，不保证全局最优；若硬件、任务或容量变化，也可能需要重新调参（§3.5、附录 A）。[^paper]

## 设计取舍

- **更少内存换预测误差**：低秩表示只占用部分 Key 存储，但压缩比过高可能让 top-k 排序失真；原始 KV 留在磁盘并不能修复没有被选中的 token。
- **更大 I/O 换读放大**：组对齐提高设备利用率，同时让不重要 token 被一起读取。不同 NVMe、eMMC 的最佳组大小不同。
- **预取换额外工作**：上一层输入可提前启动下一层 I/O，却需要额外 predictor 和同步，并且预测时会与模型计算争用计算资源。
- **复用换缓冲空间**：FIFO 复用可减少重复读取，但缓冲与低秩索引、滚动缓冲竞争同一内存预算。
- **吞吐换任务质量**：与完整 KV 的比较必须同时给出任务质量及实际内存；不能把稀疏方案较快视为相同语义下的免费提升。

## 实验设置

作者使用 NVIDIA Jetson Orin AGX 和 Orin Nano，测试 NVMe 和 eMMC，模型包括 Llama3、Qwen3、推理模型及视频模型；工作负载包括 RULER、LongBench、推理与 MLVU 视频任务。论文也用 Full-KV、FlexGen、InfiniGen、Loki 和 ShadowKV 进行对比，并为部分方案构造适配紧内存的变体（§4）。[^paper]

比较采用不同设置：一种按完整 KV 的 `1/13` 和 `1/34` 为卸载方案分配每 batch 内存；另一种固定总预算、让各方案选择可支持的最大 batch。vLLM 以全部可用内存给 KV 的理想化配置作为参照；FlexGen 的预算处理也不同。对照数字需要连同这些设置和准确率一起读。[^paper]

## 批判性分析

KVSwap 同时改变选择算法和磁盘访问粒度：低秩 Key 减少预测状态，跨 head 聚合与组最大值决定回载对象，复用缓冲减少重复读。其优势不是单一的“把 KV 写到 SSD”。图 12 明确揭示组大小改善吞吐与损失精度的关系，表 8 则显示复用对慢盘尤其重要，因此复现时至少需要保留这两组消融。[^paper]

质量评测中的平均数很容易掩盖风险。表 2 的 KVSwap-t/eMMC 在 LongBench 平均仅下降 2.7 个百分点，但 RULER 的部分检索任务下降超过 50 个百分点。预算不足时，选择器可能保住大多数常见输入，却漏掉需要定位的少数关键内容。对有明确正确答案或严格一致性的任务，需按任务及请求分布设最低门槛，而不是只看平均值。[^paper]

论文使用真实 Jetson 和两类存储设备，并测试并行任务，但 UFS、长期写入寿命、断电恢复、设备热降频和实际手机应用的内存配额仍需单独验证。最高吞吐来自批处理场景；batch 1 或低请求率下，额外预测和磁盘等待可能占更大比例。[^paper]

## 可继续研究的问题

1. 能否按请求质量风险调节 `G`、选择数量和复用缓冲，而不是离线固定一组参数？
2. 热点工作集突变时，FIFO 与考虑 SSD 读代价、过期时间的替换策略有何差别？
3. 在手机 UFS、热降频、电池与后台多应用条件下，长时间运行的尾延迟和写入寿命如何？
4. 对要求严格正确性的输入，能否退回完整历史读取或重算，并给出真正的质量保障？
